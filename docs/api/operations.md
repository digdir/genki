# Operations

Operator-only routes, used by the console: tenants and organisations, onboarding decisions, support sessions, platform datasets, pipelines and engine switches, knowledge endpoints, model endpoints, models and prices, the platform catalogue, shared services, platform gates, guardrail rules and hooks, plugins and building blocks, the quality matrix, usage across tenants, the whole audit log, operations health, tracing and running tasks.

## Rights

- Every route here needs an operator. Other callers get `403`.
- Operators reach a tenant's own routes only inside a support session with a reason and a time limit. The session shows in the tenant's audit log. In lockdown an operator also has every right in the platform organisation without a session (ADR 0033).
- Changes need `change-reason` and are audited; the ones that touch a tenant are also in that tenant's log.

## Typical sequence: help a tenant

1. `GET /operator/tenants`: find the tenant.
2. `POST /support-sessions` with `{ "tenant", "reason", "minutes" }`: the response has the session `id`.
3. Call the tenant's routes with `support-session: <id>`, for example `GET /tenants/{tenant}/definitions`.
4. `POST /operator/support-sessions/{id}/extend` if you need more time, and `POST /operator/support-sessions/{id}/end` when done.
5. `GET /operator/audit`: what was done, by whom, and why.

Prices name units per kind: the built-in units and any unit a descriptor names, such as `{ "ocr": { "page": 0.05 } }`; a unit name is lowercase letters, digits and hyphens.

Release a new model: `PUT /operator/models/{id}`, `POST /operator/quality/matrix/estimate`, `POST /operator/quality/matrix/runs` (an audited admin task with `change-reason`), then `POST /operator/quality/matrix/release`.

Let services use a new kind of model API: a kind comes from a descriptor alone; bind the descriptor as the model's API for that kind in `apis` (`PATCH /operator/models/{id}` or the catalogue), and a binding to an API no implementation or descriptor defines is refused. `GET /operator/apis` lists every API a model can bind. `GET /operator/operation-kinds` lists each kind with its maturity in this environment and its descriptors; the answer says `governs: "descriptor-calls"`, because maturity governs only descriptor calls (the raw and described tiers). The built-in kinds `chat`, `decide`, `embed` and `rerank` are always listed with `builtIn: true` and `typed: "production"`: Genki's own typed calls of them are production by construction. `POST /operator/operation-kinds/{kind}/maturity` with `{ "maturity": "production" }` and `change-reason` moves the kind to production at once, and `{ "maturity": "test" }` moves it back; one operator does either. The answer says `step: "promoted"`, `"demoted"` or `"unchanged"`, and `by` and `at` name who set the maturity and when. Before a service may use the kind with real data, record the model endpoint's processor record: `PUT /operator/model-endpoints/{id}/processor-record` with `{ "agreement", "subProcessors": [{ "name", "location" }], "retention": { "days", "note" } }`. `GET /operator/processor-records` shows every endpoint and `record: null` where none is recorded. Its `typedCalls` says what Genki's own chat and decide calls do on an endpoint without one: `warn` (the default) logs and lets them through, `enforce` refuses real data (`GENAI_PROCESSOR_RECORDS=enforce`). Every change is audited. Image, audio and file input to a descriptor call leaves only when the service's confirmed risk assessment records it: `spec.riskConfirmation.unmaskedInput: [{ "mediaType": "audio/*", "reason" }]` (#326). Publishing refuses a `call-operation` step whose descriptor takes media input of a type the service records no consent for, and the gate checks the same on every call (`refusal: "media"`). A synthetic try in the raw tier needs no consent. `kernel.gate.call` records each media input's `path`, `mediaType`, `bytes` and `sha256` under `mediaInput`.

Try a new kind of model API (test only): `POST /operator/operations/{descriptor}/try` with `{ "model": "<catalogue model id>", "input": <the descriptor's typed input>, "synthetic": true }` and `change-reason`. It is an audited admin task and answers `{ task, descriptor, model, result, exchange }` with a `genai-task` header for the run. `exchange` is what was sent and answered, with the input masked and media still encoded; the run keeps only its digest. Media input is given as base64 for a field of one media type, or as `{ "mediaType", "data" }` with base64 `data`; the exchange records it the same way. Outside `GENAI_ENV=test` it answers `403` (`errors[0].path: "environment"`); without `synthetic: true`, `400`; image, audio or file content in a field that is not declared media, a field the descriptor does not allow, or a URL, `data:` URL or more than 64 base64 characters in a row in a `plain` field, `400`; a model that does not bind the descriptor as its API for the descriptor's kind, `400` (`errors[0].path: "unsupported"`); in lockdown, for a login that is not admitted, `403`. Every PII category is masked before the call leaves, whatever the tenant has set.

Upload a new kind of model API without a deploy: `PUT /operator/operation-descriptors/{id}` with `{ "descriptor": "<YAML or JSON text, or a JSON object>", "fixtures": [<recorded fixtures>] }` and `change-reason`. The id is `<provider>/<api>@<version>` and may contain slashes; the descriptor's `operation` field names its kind. A fixture is `{ name, source?, deployment, input, request: { method, path, query?, body }, response: { status?, body }, result, usage, dropped? }`, the same as a file in `packages/operations/fixtures`; send 0 to 20, and at most 512 KiB in all (`413` above). An upload without fixtures can be tried at once, and its fixtures recorded from the tries: `POST /operator/operation-descriptors/{id}/fixtures` with `{ task, name, exchange }` from a try's answer and `change-reason` (test only, audited) adds the try as a fixture with the masked input, after `operation@1` passes on every fixture. It is refused unless the task is a finished try of the same descriptor and the exchange is the one it answered, for a bundled descriptor, and for a described upload. The loader rules and `operation@1`, with the masking probe, run on the fixtures before anything is stored; any failure answers `422` with every reason in `errors` (`path` is `descriptor`, `id`, `fixtures` or `fixtures.<name>`). An upload starts in `review` (a `status` other than `review` in the document is refused), so an operator can try it in the raw tier at once (`GENAI_ENV=test`). It answers `201` with `step: "uploaded"`, or `200` with `step: "replaced"` when an upload still in review is uploaded again. An id that is bundled with Genki, or an upload already `described`, answers `409`: upload a new version instead. `POST /operator/operation-descriptors/{id}/status` with `{ "status": "described" }` (or `"review"`) and `change-reason` lets services use it in a `call-operation` step, once the kind is production and the endpoint has a processor record; `typed` is never settable, since it means Genki's own code. `DELETE /operator/operation-descriptors/{id}` with `change-reason` withdraws it; a service whose step uses it is refused at its next call, as when a kind is moved back to test. `GET /operator/operation-descriptors` lists bundled and uploaded descriptors with `source`, `status`, `fixtures` and `contract` (`operation@1` run now on the fixtures), and `GET /operator/operation-descriptors/{id}` also gives its typed `input` shape, `usedBy` (the published services whose step flows call it) and an upload's `document` and `fixtureCases`. Moving an upload to `described` needs fixtures that pass `operation@1`. Every upload, status change and withdrawal is an audited admin task, and the config store keeps every version with who, when and why. Once uploaded, the kind may be given to a model with `PATCH /operator/models/{id}`.

Every bundled descriptor must pass `operation@1` in CI. A descriptor fails `operation@1` when a national id, an email or a phone number in any input string, strings inside `json` included, reaches the wire unmasked in a body, a query parameter or a header, so its free input must be `text` or `json`; the gate masks every string inside `json`, keys included.

Descriptors from primitives (ADR 0049). A descriptor is one request, as above, or a list of `steps` and an optional `finally` list; both forms load the same. Each step has `name`, `request: { method, path, encoding, body | parts, query, headers }`, `response: { encoding, headers }`, `wire: { request, query, headers, response }` and may have `bind`, `usage`, `until`, `retry`, `errors`, `checks` and `auth`:

- `request.encoding` is `json` (the default), `multipart` (map `parts`), `form`, `binary` (the body is one media value), `text` or `ndjson`; `response.encoding` is `json`, `binary`, `text` or `ndjson`. An answer whose content type is not the declared one fails the call. A binary answer becomes a media blob of the run, a text answer a text field.
- Every value that goes out or comes back has a class from the payload shapes: the body through `wire.request`, mapped query parameters through `wire.query`, mapped headers through `wire.headers`, the answer through `wire.response` and read headers through `response.headers`. A mapped value without a class is refused at load. `media` with a type (`audio/*` is allowed in input, not in output) goes out in json (as base64), multipart (as a file part named after its media type) or binary bodies.
- `bind: { <field>: { from, class } }` captures values from an answer; later steps read `$steps.<step>.<field>`. Only a value bound as a `ref` with a pattern may fill a path segment (`{steps.start.job}`), never input, and a ref that is a URL is refused, so answer URLs are not followed. `class: secret` binds a token from an exchange step; only a step's `auth: { header, scheme, secret: $steps.<step>.<field> }` (or `query`) can place it, nothing can read it and no exchange records it.
- `until: { test, equals?, intervalSeconds, longestSeconds }` repeats a step until its answer holds; a `Retry-After` on the answer is honoured. `finally` steps run whether the steps before them succeeded or failed, and are skipped when a value they read was never bound.
- `auth` on the descriptor places the connection's credential: `{ header, scheme? }` or `{ query }` (redacted from every recorded exchange); `keyHeader` still works.
- `usage` names units: the built-in ones, usage fields, or any unit name (`page`, `job`), read from the answer (`$response`) or a header (`$headers`). Usage is summed over steps. A unit the model has no price for leaves the call metered and not priced.
- `errors: [{ status, kind, message? }]` maps an error status (`429`, a list, `4xx` or `5xx`) to `invalid`, `unavailable`, `rate-limited`, `refused` or `processor`. A `429` with `Retry-After` is retried up to `retry: { attempts, longestWaitSeconds }` (default 2 and 10 s, at most 60 s); a longer wait fails the call as rate limited. Without `message`, a 4xx error's message is the provider's `error.message` or `message`, or its body when it is `text/plain`. The provider's status and the first 500 characters of its error body, with the connection's key, its named keys, every bound secret and every header a module signed replaced by `[redacted]`, are kept on the run's audit `kernel.error` event as `provider: { status, body }` and shown in the run timeline to those who manage the service; the caller is told only that the service failed.
- `checks` fail the call when an answer does not hold: `same-names: { expected, actual }`, `count: { of, sameAs?, min?, max? }`, `one-of: { value, in }`.
- The mapping language reads `$input`, `$deployment`, `$steps`, `$response`, `$headers`, `$usage` and `$dropped` where each is available, indexes lists (`$response.items.0`) and has `$concat`, `$join: [list, separator]` and `$if: { test, equals?, then, else? }`.

A fixture records one `request` and `response`, or `steps: [{ step, request, response }]` with every request in order; a request may have `headers` (the mapped ones), an answer `headers` (the declared ones); media in a recorded request is `{ mediaType, bytes, sha256 }`, a binary answer is base64. Bundled descriptors include `openai/transcriptions@1` and `openai/transcriptions-text@1` (`transcribe`), `openai/image-edits@1` (`edit-image`) and `openai/chat-audio@1` (`audio-chat`), all `described`; none has been run against a live service yet.

Media output: a descriptor marks an output field as media with `{ media: <type/subtype> }`, for example `b64: { media: image/png }`, `audio: { media: audio/wav }` or `report: { media: application/pdf }`. The value on the wire is base64; the gate decodes it, counts its bytes in `kernel.gate.call` (`mediaBytes`), refuses it whole when it is over the cap for its type (`refusal: "media"`; the call is still metered, nothing is truncated), and keeps it as a blob of the run, so the typed result, later steps, the run result and the timeline hold a reference `{ kind: "media", mediaType, bytes, sha256, tenant, path, step }` instead of the bytes. Media input needs consent as above. In `operation@1` a fixture records media output as the provider encoded it, and media input as its type, size and SHA-256.

New media kinds come from descriptors alone. No platform code names a media type: the deployment says which types are kept and how large each may be, with `GENAI_MEDIA_OUTPUT_TYPES` (comma separated, `type/subtype` or `type/*`, each with an optional `=<bytes>` cap; the default is `image/*,audio/*,video/*,application/pdf,text/csv`) and `GENAI_MEDIA_OUTPUT_MAX_BYTES` (the cap for a type without its own, default 10485760). The most specific rule wins. A descriptor call whose output declares a type the deployment does not keep is refused before anything is sent.

Any provider API by descriptor (ADR 0049, 2026-11-06). More primitives, all as data:

- Classes and placements: `{ issued: '<anchored pattern>' }` is the only class that may fill a path segment or go back out as an id; `url` binds a link for `request.follow`, which goes over https to the connection's host or an operator `allowedHosts` host, never follows a redirect and never sends the credential to another host. `credential: { place: header | query | form | basic }` is set per step; multipart `filenames` map a part's file name; `$dataUrl`, `$add`, `$sub`, `$mul` and `$coalesce` join the mapping language; `until.fail` ends a poll early. A descriptor that lets input name a URL, a host or a model is refused at load, so an API in which the provider fetches a URL the caller gives cannot be described. Price units must be spelled as the descriptor names them; an operator price for an unknown unit of a kind answers `400`.
- Streaming: a step with `response.stream` (`sse`, `ndjson` or `lines`) streams its text deltas through the gate, which masks the request and restores masked values across events. A `call-operation@1` step with `stream: true` streams in a service's `/v1/chat/completions` answer; its output is `{ result, text }`, where `text` is the streamed text, and a flow that ends on that step answers with `text`. A step without `stream` outputs `{ result, text }` too when `result` is text or has a text field `text`, and `{ result }` otherwise. The text arrives as deltas when the caller sends `genai_stream: "live"`, and otherwise as one piece.
- Provider-side objects: `resources: [{ id: "<step>.<field>", delete: "<step>", longestSeconds }]` puts every object the call creates at the provider in a ledger and deletes it in `finally`; a nightly sweep deletes the rest, and an object it cannot delete is an incident in the audit log (`platform.provider-object.incident`). A descriptor with `resources` is served only when the connection's processor record has `providerState: { allowed: true, retention: { days, note } }` (`PUT /operator/model-endpoints/{id}/processor-record`); otherwise the call is refused as `processor`.
- Allowed hosts: `allowedHosts: ["files.example.no"]` on a model connection (`POST` and `PUT /operator/model-endpoints`) lists the hosts besides `baseURL` that an answer link may lead to. Only an operator sets it, it is audited, hosts are names (no IP address) with an optional port, 20 at most, and a tenant connection cannot have it.
- Modules: `modules: { <name>: { sha256, keys: [connection, connection.<key name>] } }` in a descriptor names a WebAssembly module pinned by SHA-256; upload it with `PUT /operator/operation-descriptors/{id}` as `modules: { <name>: <base64> }` (128 KiB each, two at most). It runs with 250 ms, 16 memory pages and no imports other than the host functions for bytes, hash, HMAC with a key by name, and `hmac_sha256_derive`, which derives a new named key in the host (as AWS SigV4 does; a prefix of at most 64 bytes, at most eight derived keys, never over a given name), so neither the key nor a derived key enters the module. It reads `method`, `path` (with the base path and the query), `host`, `timestamp`, `body` (left out when it would pass the 1 MiB input cap), `body_sha256`, `headers` (the outgoing headers it signs over, `name:value` lines sorted by lower-case name, with `host` and without any credential), `header_names` (`;`-joined), `header.<name>` and `connection.<setting>`. Its emitted values go only to declared headers and must match an anchored pattern or an enum. It may set `Authorization` only when the descriptor's `auth` is `{ signedBy: module }` and the step places no exchanged secret; every other reserved header stays closed. A module signs json, ndjson, text, form, binary and multipart bodies (multipart is serialised once, and the bytes signed are the bytes sent) and requests with a streamed answer, never a session or a step whose credential is a form field. A fixture cannot prove a signature, so a module is proved by its own test; a fixture may set `at`, the signing time.
- Connection settings and named keys: `settings: { keyId: "AKID-7" }` on a model connection holds non-secret values a descriptor reads as `$connection.<name>` in `request.headers`, `request.query` and module input, never in the host, the path or the body. `keys: { signing: "secret://platform/<name>" }` names extra keys a module takes as `connection.<name>`; no request carries them. Only an operator sets either (`POST` and `PUT /operator/model-endpoints` or `PUT /operator/catalog/model-endpoint/{id}` with `change-reason`), the change is audited, a `PUT` without them keeps them, and a tenant connection cannot have them. A connection has at most 20 settings and 4 named keys, and a name is a setting or a key, not both. A call whose connection lacks a setting or key any step reads fails before the first request is sent, also when the call is a live session; a key the connection names but whose secret cannot be resolved fails at the step that signs with it, not before the first request. `GET /tenants/{tenant}/catalog` lists a shared connection without its `settings` and `keys`; only the operator routes return them. A fixture records the settings it ran with as `settings`.
- Live sessions: a `websocket` step is a session. `GET /v1/sessions?model=<service>` with `Upgrade: websocket` and the same login as `/v1/chat/completions` opens one on a service whose way of working is `live-session@1` (`config: { descriptor }`); a plain request answers `426`, and the chat route refuses such a service. Genki connects to the provider with the connection's credential and relays both ways: text is masked and restored, a binary frame is media and needs the same consent. The run is the session (transcript, usage, audit). It closes with 1000 when it is done, 1001 when cancelled, 4001 at its longest duration, 4002 when the kind is moved back to test and 1011 on an error. Fixtures record `session: { request, messages: [{ from, message, binary? }] }`.
- Bundled and `described`, never run live: `openai/chat-stream@1`, `openai/batch@1` (a batch that ends within ten minutes) and `openai/realtime-transcription@1`.
- Open units appear in a run's usage as `units` wherever usage is returned.

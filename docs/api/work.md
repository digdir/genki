# Work and quality

Running work and measuring it: service runs (tasks) and their timelines, table reviews, projects that follow document selections, batch runs over documents, triggers, test sets and evaluation runs, improvement proposals from the optimiser, test case candidates, publishing gates, guardrail rules, retrieval diagnostics, feedback, usage, the audit log and the tenant overview.

## Rights

- Reading runs, test sets, gates and feedback needs membership in the tenant. A run's timeline is open to whoever started it, or to `manage-services`.
- Projects and their runs need `use-services`; a subscription that runs a service needs `manage-services`.
- Test sets, eval runs, improvements, batch runs, gates, guardrail rules and candidate reviews need `manage-services`.
- An API key needs the `admin` scope on these routes, also on the ones outside `/tenants/{tenant}` (`/eval-runs/*`, `/eval-tasks/*`, `/testcase-candidates/*`); other keys get 403 `urn:genai:problem:api-key-scope`. A test-runner key in a locked test environment is the exception on `/tenants/{tenant}` (see [Access](access.md#test-runner-keys)).
- A rerun of a batch with the same `batchId` skips the items that already succeeded. Their entries in the new result carry status, attempts and the task that produced them, not the answer, which stays with that task and its retention.
- Editing and approving a table review (`PUT .../tasks/{task}/review/edits`, `POST .../review/approve`) needs `use-services` and is open only to whoever started the run. Both are audited admin tasks with `change-reason`; an edit that races another answers 409.
- Usage and cost need `view-usage`. `GET /tenants/{tenant}/usage` splits testing and ingestion per day, and its `quota` has `alert: true` once the calendar month has used 80 % of the monthly token quota. Each service in `byService` has `latency`: the p50 and p95 milliseconds from start to end of its runs that ended in the period (nearest rank), and how many runs that is, or `null`. Each day in `daily` gives every service in its `byService` the same `latency` for the runs started that day that have ended.
- `GET /tenants/{tenant}/service-failures?from=` groups each service's failed runs since `from`, by default the start of today in Norway, by failure code, the most common first, with the fixed reason for each code. Any member may read it; it never holds error text.
- `GET /tenants/{tenant}/tasks` pages with `limit` and `offset`, and `total` counts the matching runs. `actor=me` keeps the caller's own runs, and `actor=` an `actor.id` from a row keeps that person's (`employee:<issuer>:<subject>`) or that key's (`api-key:<key id>`) runs; both match only runs started in the caller's tenant, so a run of another organisation calling a shared service never matches and has no `actor.id`. Anything else answers `400`. Each row has `channel`: `api-key` (a key not bound to a frontend), `interface` (a key bound to a server frontend), `api` (a token that is not an API key on `/v1`, REST, MCP or A2A: a person's, or a registered Maskinporten client's; a run through a browser frontend is not told apart, since the run does not record the frontend), `playground` (a trial run), `batch` (an item of a batch run's latest attempt), or `null` when the run records none of these, such as a trigger. `q` finds runs whose id holds the text, and, for a caller with `manage-services`, whose question does; it searches the newest 2000 runs that match the other filters (`searched` says how many), and never the question of an erased run. `frontend=` a registered frontend's id keeps the runs that came in through it: genki takes the frontend from the verified login or key, never from the request, and gives it as `frontend` on runs of the caller's own tenant.
- A tenant asks for a larger quota with `POST /tenants/{tenant}/quota-requests` (`manage-services`, audited, one waiting at a time, else `409` `urn:genai:problem:quota-request-pending`); `GET` lists them with `view-usage`. An operator lists them on `GET /operator/quota-requests` and decides one on `POST /operator/quota-requests/{tenant}/{id}/decision`, audited; a request already decided answers `409` `urn:genai:problem:quota-request-decided`. A decision does not change the quota: the operator sets `usage.monthlyTokens` in a support session.
- Cancelling a running test run (`POST /tenants/{tenant}/services/{id}/eval-runs/{runId}/cancel`) needs `use-services` for whoever started it and `manage-services` for anyone else, and `change-reason`; it is the audited admin task `platform.eval-run.cancel`. No further case starts, the finished cases stay, and the run ends with status `cancelled` and no error: `200` when it has ended so within two seconds, `202` with `status: cancelling` while the instance running it stops it. A cancelled run answers `200` again without a new audit entry, and a run that ended otherwise `409` `urn:genai:problem:run-finished`. A cancelled run whose instance stopped before it could end it is settled as cancelled by the next instance, never taken up again. While a run is running or waiting for scores, the service's run list says who started it in `startedBy` and `startedByName`, and `startedByYou: true` to the person who did.
- Stopping one run (`POST /tenants/{tenant}/tasks/{task}/cancel`) needs `use-services` for whoever started it and `manage-services` for anyone else. It is an audited admin task with `change-reason`, and stops only runs started through an API entry point (ADR 0057). Others answer `409` `urn:genai:problem:run-not-cancellable`, and a finished run `409` `urn:genai:problem:run-finished`.
- `GET /tenants/{tenant}/status` is platform health as a member sees it: shared components, the tenant's own runs, ingestion and failing schedules, and the open incidents that concern it. Operators write incidents with `POST /operator/incidents` and resolve them with `POST /operator/incidents/{id}/resolve`, both audited; resolving one twice answers `409` `urn:genai:problem:incident-resolved`.
- Starting, cancelling and retrying a batch run (`POST /tenants/{tenant}/services/{id}/batch-runs`, `.../{runId}/cancel`, `.../{runId}/retry`) are audited admin tasks: each needs `change-reason` and answers with a `genai-task` header. A start can give the run a `name` of at most 120 characters, which the run and the list then show.
- Changes need `change-reason` and appear in `GET /tenants/{tenant}/audit`. With `limit` (1 to 500) or `offset` the audit log comes newest first, a page at a time, and `total` says how many entries there are.

## Typical sequence: evaluate a draft before publishing

1. `GET /tenants/{tenant}/services/{id}/test-sets`: the service's test sets.
2. `POST /tenants/{tenant}/test-sets/{setId}/cases`: add a case if one is missing. `expected` is a text, read as a criteria case's criteria and as the reference answer otherwise, or `{ referenceAnswer, criteria }` with named criteria such as `criteria` and `supporting_quotes`, kept as they are. Given as fields, a criteria case needs `criteria` and an exact case `referenceAnswer`.
3. `POST /tenants/{tenant}/services/{id}/eval-runs` for the draft: runs in the background.
4. `GET /tenants/{tenant}/services/{id}/eval-runs`, then `GET /tenants/{tenant}/eval-runs/{runId}` for case results.
5. `GET /tenants/{tenant}/services/{id}/eval-runs/compare?candidate={runId}`: the draft's run against the run of the published version, case by case. `GET /eval-runs/compare` gives the confidence interval on one metric or several.
6. `GET /tenants/{tenant}/gates`: the gates publishing must pass; then publish (see [Services](services.md)).

To follow one run: `GET /tenants/{tenant}/tasks/{task}` and `GET /tenants/{tenant}/tasks/{task}/timeline`. Both also read a playground run, and `GET /tenants/{tenant}/tasks?origin=playground` lists the tenant's trial runs instead of its service runs: playground runs and the runs the builder starts with `POST /tenants/{tenant}/definitions/test-run` (origin `trial`), never test case runs. A failed run in the list and on its own carries `failure`: the error `code`, a fixed `reason` for it, the failed `step` in a step flow, and `detail` only when every search in the run failed and that explains the failure: on `strategy_error`, or on `deadline_exceeded` when the searches timed out ("Alle søkene tok for lang tid."). A run that failed on the model, or where only some searches failed, has no `detail`. These are fixed translated sentences, never engine, provider or model text.

A run whose content was erased on purpose carries `erasure: { reason, at }` on the run, in the run list and on its timeline. `reason` is `conversation-deleted` (the conversation was deleted), `retention` (removed after the retention period) or `erased` (erased before the platform recorded why); `at` is when, if known. Such a run has no `excerpt`, and its timeline keeps only what the envelopes hold: start, status, duration, model calls with tokens and cost, and a result step that says the answer was erased.

## Two kinds of evaluation run

- A service evaluation run starts with `POST /tenants/{tenant}/services/{id}/eval-runs` and is listed by `GET /tenants/{tenant}/services/{id}/eval-runs`. It runs every case of the test set, only one split with `split` (`locked` or `open`), or only the cases named in `cases` (case ids); a case id the test set does not have is a 400. A run of only some cases (`selected`) feeds no publishing gate.
- It is an eval run of the draft or version (`platform.eval.run`), judged by `contract`, by `retrieval` when cases name sources and by `judge:criteria` when there are criteria cases, and it is stored as soon as it starts. Its `status` is `running`, `waiting-for-scores`, `completed`, `failed` or `interrupted`; a run left by an instance that stopped is taken up again (below), or reads as `interrupted` when it cannot be. A case passes on its type's own metric: the criteria judge, the exact text or the refusal. Only completed runs feed publishing gates and comparisons, and a gate finds a run under the spec it tested. Test runs from before this change are no longer listed.
- With `trace: true` each case except the holdout is sent to the tenant's trace connection that covers the service, as one experiment with a trace per case and repeat (see [access.md](access.md)); it answers 409 when no connection covers the service, when two do, or when the residency the service runs with, filled from its model when the draft leaves it out, does not allow the connection's. The traces go through the egress guard, pinned to the address it checked. Until judges map fields, the traces carry no text. A draft or version that cannot run answers 422.
- It keeps each case as it finishes: until it completes, `finished` counts the cases done and `passed` counts only those. A run that fails or is interrupted keeps the cases it finished and what they cost.
- While it runs, `current` lists the cases running now with when each started, `secondsPerCase` is how long a case has taken on average, and `endsAt` is when the run should be done at the pace it has kept. Each case result in `GET /tenants/{tenant}/eval-runs/{runId}` carries its `task`, whose timeline shows the case. The API writes one log line per case (`eval case`) with the run, the tenant, the case number, the time, the tokens and the outcome, never the question or the answer.
- A run survives a deploy. A stopping API instance starts no new case, lets the cases in flight finish (up to `SHUTDOWN_GRACE_MS`, see [development.md](../development.md)) and hands the run over. Another instance takes it up again at once, or within a few minutes of its last heartbeat when its instance stopped without handing it over, and runs only the cases it had not finished, as the person who started it and charged to the same organisation, so the quota and model gate checks apply as before. The cost goes on adding up, and `resumed` counts the times it was taken up. A run is taken up at most three times; a run sent to Langfuse (`trace`) is not taken up and reads as `interrupted`. What taking it up needs (the person's identity without name, the draft or version, the split and the cases) is kept in a `service-eval-resume` config entry under the tenant until the run ends.
- It runs up to four cases at a time and shares a limited number of case slots with the other test-set runs on its API instance, a fair share per organisation and per run ([development.md](../development.md), "Test-set runs side by side", has the settings). While it has no case in flight and waits for a slot, it carries `queuePlace` (1 is next in line). Before each case the run checks the organisation's monthly token quota; once it is used up, the run starts no new case, lets the ones in flight finish, and ends `failed` with the cases it finished.
- An eval capability run starts with `POST /tenants/{tenant}/eval-runs` (capability, test set, evaluators and provenance are required) and is listed by `GET /tenants/{tenant}/eval-runs`. Follow it with `GET /eval-tasks/{task}`; every instance answers the same status, read from the task and the stored run, except `waiting-for-scores`, which only the instance running the eval knows.
- An eval capability run names its evaluators: `contract` (answer pattern, an exact case's text, refusal and fields), `retrieval` (ranking metrics and grounded citations, below), `judge:criteria` and registered evaluator plug-ins. `judge:criteria` scores criteria cases on `expected.criteria`, or on the reference answer when a case has none. Its model is picked for the run's tenant, from another family than the models that wrote the answer (an embedder that only searched does not count) and than the models in `avoidAsJudge`; a portal test run's judge also avoids the service's own models. The run's provenance names it as `judge:criteria@<version>+<model>`, and labels and calibration are kept under `judge:criteria`. An exact case without its text scores 0, and a JSON part other than sources, retrieval and the guard's provenance counts as a structured answer, so an empty RAG answer is a refusal.
- `retrieval` scores two lists of hits with the same matching of a hit to an expected source: by chunk id when both have one; otherwise, or when the expected source names its position, by document (or its earlier id) and position. The hits the run's searches reported give `recall@1`, `recall@5`, `recall@10`, `recall@20`, `hit@5` (1 when any expected source is in the top 5), `mrr@10` (one over the rank of the first expected source in the top 10, else 0), `ndcg@10` (binary: each expected source counts once, at its first hit) and `document-recall@10` (the share of expected documents among the first ten distinct documents). Recall counts places in the list as before, so `recall@10` keeps its values; for `hit@5`, `mrr@10` and `ndcg@10` a hit seen earlier takes no new rank. In `rag-single-shot` and the step-flow `retrieve` block these hits come before the reranker; the agent loop reports them after it, and `read-document` after it in reading order. The sources the run returned, in their order, give `returned-recall@1`, `returned-recall@5`, `returned-recall@10`, `returned-hit@5`, `returned-mrr@10` and `returned-ndcg@10`, so in `rag-single-shot` a reranker's effect shows as the difference between the two. A case without expected sources is not scored on any of them, and the `returned-*` metrics are not scored for a run that returned no sources part. `citations-grounded` is the share of the answer's citations among the hits.
- `GET /eval-runs/compare?baseline={runId}&candidate={runId}&metric={metrics}` compares two completed runs of the same test set and version with a paired bootstrap. `metric` is one metric or a comma list, and the answer has `comparisons`, one per metric in the order asked (`metric`, `n`, `meanBaseline`, `meanCandidate`, `difference`, `ci`), with `allowedDifferent` and, when it applies, `staleJudges`. Runs that differ in commit, data, served models, judges or services answer 400, unless `allowDifferent` (a comma list of `data`, `services`, `servedModels`) names the difference: two services on two search engines are compared with `allowDifferent=services`, plus `servedModels` when the runs used different models. A commit or judges cannot be allowed to differ, and naming them or an unknown field answers 400. A metric no case scored in both runs fails the whole call with 400.
- A score has a `state`: `scored`, `not-applicable`, `pending`, `failed` or `missing`. A judge on `evaluator@2` may answer pending. The run then waits up to 5 minutes from its last case, `GET /eval-tasks/{task}` answers `waiting-for-scores` with how many scores are pending, and what has not arrived is `missing`. The run's `incomplete` names each judge with missing or failed scores, and a gate on a metric with any of them in its split fails.
- `GET /tenants/{tenant}/eval-runs/{runId}` finds both. `kind` tells them apart: `service` answers the run with its metrics, confidence intervals and case results, each answer read from its case's task, `kernel` answers the same body as `GET /eval-runs/{id}`. A test-set run judged by an older version of a platform judge than the current one, such as `judge:criteria`, names it in `staleJudges`, in `GET /tenants/{tenant}/services/{id}/eval-runs` and in the `service` answer here; `GET /eval-runs/compare` names it too. Capability runs from `GET /tenants/{tenant}/eval-runs` and `GET /eval-runs/{id}` have no `staleJudges`. Cost and tokens cover the answers and the judges, and show only with view-usage.
- `GET /tenants/{tenant}/services/{id}/eval-runs/compare?candidate={runId}&baseline={runId|published}` compares two test-set runs of the service case by case, for any member. Without `baseline`, or with `published`, the baseline is the newest completed run of the whole test set by the version the `prod` environment runs (no variant, no `split`, no `selected` cases), found by version or by the spec it tested, and a 404 when there is none. Both runs must be of the service in the path in the caller's tenant, else 404, and of the same test set, else 400 `urn:genai:problem:eval-runs-not-comparable`. Each case has its `input`, `type`, `split`, the verdict on each side (`pass`, `score`, the judge's `reason`) and a `change`: `better` or `worse` when the verdict flipped, `same` when it did not, `new` or `missing` when only the candidate or only the baseline has the case, and `pending` when the run without it is still running. A case outside the `split` or the `selected` cases of the run that lacks it is left out, not called new or missing. Cases come worse first, then better, new, missing, pending and same. `counts` covers every case; `change` filters the page, and `limit` (1 to 200, default 50) and `offset` page it, with `total` the cases that match. An invalid `change`, `limit` or `offset`, or no `candidate`, answers 400 `urn:genai:problem:eval-compare-invalid`. No answer text is read or shown, and no cost.
- No eval run endpoint shows a run's lease (`owner`, `heartbeatAt`, `released`), and `usage` shows only with view-usage, also in `GET /tenants/{tenant}/eval-runs` and `GET /eval-runs/{id}`. A failed run keeps the usage of the cases it got through. A run names the service it tested in `provenance.services`, not the draft capability made for it, so two runs of the same version can be compared.
- `GET /tenants/{tenant}/test-sets`, `GET /tenants/{tenant}/eval-runs` and `GET /tenants/{tenant}/feedback` answer `{ "data": [...] }`, like every other list.

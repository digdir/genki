# Services and definitions

Build, test and publish services. A service is a versioned definition; drafts, the playground and test runs let you change it safely before a new version is published. Also: skills, step-flow blocks, catalogue proposals from the builder assistant, layered settings and pins, export and import, shared services.

## Rights

- Reading needs membership in the tenant (any right).
- Saving drafts, publishing, test runs, settings, skills and import need `manage-services`. The playground also accepts `manage-datasets`.
- `POST /definitions` and `POST /definitions/validate` answer 403 `urn:genai:problem:tenant-not-registered` for an organisation Digdir has not registered, as the `/tenants/{tenant}` routes do. Publishing never registers an organisation.
- Only an operator changes who a service is shared with (`spec.availableTo`), through `PUT /operator/shared-services/{tenant}/{id}` or a publish in a support session. `POST /definitions` and `POST /tenants/{tenant}/import` answer 403 `urn:genai:problem:share-operator-only` when anyone else sends a value that differs from the published version, also when restoring an older version. Sending the published value unchanged is fine.
- A service with `spec.visibility: internal` is seen only by operators, the platform's own `workload` principals (such as the seed) and a test-runner key. Everyone else never finds it in a list, gets 404 on its paths, and may not publish, import, validate or draft one; publishing over its id answers 422 "already in use", and over one of its public names "already taken". Some routes answer an unknown id with an empty 200, so a 404 there tells an internal id apart. See [ADR 0004](../adr/0004-service-capability-and-version.md#internal-services).
- Another organisation reads, exports, copies and pins only the version of a shared skill that Digdir approved; any other version answers 404.
- An interface block is a `Block` definition ([ADR 0067](../adr/0067-interface-blocks-are-block-definitions.md)), validated with `POST /definitions/validate`, published with `POST /definitions` and read under `GET /tenants/{tenant}/definitions/blocks/{id}` and `.../versions/{version}`, with the same tenant and right checks as a service. `tier: built-in` and `tier: declarative` blocks are accepted; a declarative block's `spec.template` is checked against the element set, the field list, its own events, states, texts and props, and the limits, with 422 and a path such as `spec.template.root.children[1].text.bind`. Only an operator publishes a built-in block: anyone else gets 403 `urn:genai:problem:share-operator-only` with the path `spec.tier`, from validate, publish and import alike. genki's own built-in blocks are seeded in the platform tenant from `apps/api/config/local/blocks`, shared with everyone. A placed block in `spec.interface.layout` may pin one with `ref: "<organisation number>/<id>@<version>"`, beside its `block`: validate, publish and import refuse, with 422 and the path `spec.interface.layout.zones.<zone>[<i>].ref` (a draft's checks list it under `problems` with `ready: false`), a ref to a block that is not published, to another organisation's block or version that is not shared with everyone (as if it were not published), to a version that does not exist, a `block` other than the built-in block the ref draws (a declarative or code block stands as `block: ref`, and `ref` as a block needs a `ref`), a zone the edition does not allow, and a setting that is not a prop of the edition or not of its type. Once code blocks are accepted, only an operator shares a `tier: code` block with everyone: anyone else will get 403 `urn:genai:problem:share-operator-only` with the path `spec.sharing`. An import checks refs against what is already published, so a ref to a block in the same bundle is refused until that block is published in the target.
- `GET /tenants/{tenant}/blocks` lists the interface blocks the organisation may use: its own, genki's built-in ones and those other organisations shared with everyone, as `BlockSummary` rows (`origin` is `own`, `built-in` or `shared`; `usedBy` counts the organisation's own services that pin it). `?origin=` narrows it. `GET /tenants/{tenant}/blocks/{publisher}/{id}` gives one block with only the editions the organisation may use, one edition in full (`?version=`, the newest without it) and `usedIn`, where its services pin it in the draft, in test and in use. Who published an edition is named only to the organisation that published it. Both need membership, and another organisation's block that is not shared with everyone answers 404.
- `POST /tenants/{tenant}/blocks/preview` takes `{ definition, files?, states? }`, checks the block and returns `valid`, `errors`, `render` (what a host draws a declarative or code block from), `reads` and genki's made-up data for each state. It saves nothing, needs `manage-services`, and refuses a block whose `metadata.tenant` is another organisation with 403.
- `PUT /tenants/{tenant}/services/{id}/draft/blocks/{publisher}/{blockId}` with `{ version, zone?, settings? }` and a `change-reason` puts that edition in the service's draft, or moves a pin of the same block to it, starting the draft from the latest version when there is none, and refuses with 422 a service that has no layout yet. `DELETE` on the same path takes it out, and answers 404 when the block is not in the draft. Both need `manage-services`, return the draft with `checks`, and leave the version in use as it is until the draft is published.
- `GET /v1/models/{id}/interface` returns `blocks` beside the layout: the pinned edition of every `block: ref`, keyed by its ref, and nothing else of the publisher's blocks.
- A skill package may hold at most 1000 files and 20 MB of content, counted from the bytes actually unpacked; duplicate or overlapping entries are refused, and an import of an existing skill writes nothing.
- A high-risk service needs two different people to confirm its risk class (`POST .../risk-confirmations`) before it can be published. A confirmation the audit refuses answers problem+json with the task in `genai-task`.
- A skill whose requirements are not met answers `POST .../skills/{id}/publish` with `422` problem+json; `requirements` lists each requirement and whether it is met.
- Decisions on catalogue proposals (`POST /tenants/{tenant}/proposals/{pid}/approve`, `.../reject`, `.../send-for-approval`) and the operator's `POST /operator/proposals/{pid}/decision` and `.../status` read the reason from `change-reason` only; a `reason` in the body is ignored. Someone who cannot reach the tenant gets 404 from the proposal routes, before any right check.
- Changes need `change-reason` (at least 10 characters, a draft save too) and appear in `GET /tenants/{tenant}/audit`.

A playground run whose model or step fails answers `502` as `application/problem+json` with `type: urn:genai:problem:playground-unavailable`, `status: 502`, `setup`, `code` and, when the caller may see it, `detail` and `runId`. The streamed `failed` event carries the same problem.

A playground run on a published version that no longer fits the platform, for example one whose strategy version is gone, answers `422` with `type: urn:genai:problem:definition-outdated`, `setup`, `service`, `version`, `latestVersion` and the validation `errors`. The title names the first problem and points to the newest version, in bokmål or English.

## Playground changes on top of a service version

A playground setup with `service` runs that version's definition. `model`, `instructions` and `datasets` in the same setup change it for that run only; genki never writes the change to the service, a version or a draft. The changed definition is validated and checked against the building block policy like any other.

- `datasets` replaces the version's datasets. A dataset the version already has keeps its settings; any other must exist and be shared with the tenant, or the run answers `422` with the path `setup.datasets[i]`, the same answer for both cases. A setup without a service gets the same check.
- `instructions` replaces the one instructions field of the strategy the chosen variant runs: the variant's own strategy, or else `spec.strategy`, and the variant's `overrides.instructions` when it sets one. A strategy with several steps keeps its steps; agent-loop uses the replaced text wherever it uses its instructions. A strategy without one instructions field, such as step-flow, whose prompts live in the flow's steps, answers `422` with the path `setup.instructions` and a text in bokmål or English. `takesInstructions` on the version's `strategy` in `GET .../playground/options` tells beforehand.
- `skills`, `blocks` and `fields` are still ignored with a service.

## Typical sequence: change and publish a service

1. `GET /tenants/{tenant}/services`: the published services with status and channels. `GET /tenants/{tenant}/service-drafts`: the saved drafts, newest first, with `latestVersion: null` for a service never published (ADR 0051).
2. `GET /tenants/{tenant}/definitions/services/{id}`: the latest published version (`latest`) and every version (`versions`). For a new service, start from `GET /tenants/{tenant}/definitions/template`.
3. `PUT /tenants/{tenant}/services/{id}/draft` with `{ definition, files?, baseVersion, revision? }`. Send the `revision` you read; `409` means someone else saved in between. The draft answers `by`, who saved it last, and `byName`, their name or `null`. A test run of the saved draft (`POST .../eval-runs` with `version: draft` and no `definition`) records the revision as `draftRevision` on the run.
4. `POST /tenants/{tenant}/definitions/test-run` with `{ definition, files?, query }`: one run of the unpublished definition, nothing saved.
   `GET /tenants/{tenant}/services/{id}/draft/checks`: the checks a publish runs (schema, policies, risk confirmation, step flows, datasets and evaluation gates against recorded test runs) on the saved draft, without publishing it or calling a model; `ready` is `true` when publishing it now would pass, else `problems` lists why. on_publish hooks are not run here: when the organisation has enabled one, the answer has `hooksSkipped: true`, and the hook can still refuse the publish.
5. `POST /definitions` with `change-reason` and `{ definition, files, draftRevision }`: publishes the draft as the next version (`201`). `409 draft-outdated` means a newer version was published; call `POST .../draft/rebase` first. `422` lists what is invalid.
6. `GET /tenants/{tenant}/definitions/services/{id}/versions/{version}`: read one version.
7. `GET /tenants/{tenant}/audit`: the change log, with who published and why.

Pause or archive with `PUT /tenants/{tenant}/services/{id}/lifecycle`. Activating it again checks its latest version against the catalog, and answers `409` `urn:genai:problem:service-outdated` when something it names was deleted meanwhile; pause it, publish a fixed version, then activate it. `GET` on the same path gives the state with `reason`, `by`, `at` and, when genki knows it, the person's name as `byName`. Validate without saving with `POST /definitions/validate`.

Delete an archived service for good with `DELETE /tenants/{tenant}/services/{id}`. It needs manage-services and a `change-reason`, and is audited as `platform.service.delete`. The definition, every version, the draft, the environments and the organisation's step flows that nothing else still stored runs (no other service's version in any organisation, no other step flow, and never a recipe or a flow that has been shared) go at once, and the id can be used again. An active or paused service answers 409 `urn:genai:problem:service-not-archived`. A frontend, a live API key bound to the service, or another service that is not archived and names it (one of its public names, its capability id, or a URL path segment such as an A2A address) answers 409 `urn:genai:problem:service-in-use`, with each one in `errors` under `frontends`, `apiKeys` or `services`. Runs, conversations and stored documents are not deleted on the spot: they follow normal retention (ADR 0011). Runs of a deleted internal service stay hidden from everyone who does not see internal services.

## Recipes: step flows with plain settings

A recipe is a published `StepFlow` with `spec.recipe` (a title and a "pick this when" summary, in bokmål and English) and `spec.settings`, a JSON Schema for plain settings a variant fills in. Each setting needs `x-label` in both languages and may use `x-help`, `x-widget` (text, textarea, number, toggle, select, multiselect, list), `x-options`, `x-enumLabels`, `x-order` and `x-advanced` (ADR 0030). An `x-options` route may use `{tenant}`, `{dataset}`, `{datasetOwner}`, `{datasetKey}` (the service's first dataset) and the value of any other text setting, for example `/api/facets?tenant={datasetOwner}&dataset-config-key={datasetKey}&fields={documentField}` with `items: fields.0.options` for a dataset's real facet values.

1. `GET /tenants/{tenant}/step-flows/recipes`: the tenant's own recipes, then the recipes Digdir shares, with `ref`, `origin` (`own` or `shared`), `title`, `summary`, `purpose`, `settings` and `steps` (to draw the steps read-only). `GET .../step-flows/recipes/{id}/versions/{version}` returns the version a variant is pinned to.
2. A variant picks a recipe with `strategy: { id: step-flow, version: 1, config: { flow: <ref>, settings: { ... } } }`. The service itself can do the same.
3. Steps read a setting as `{{settings.<name>}}`. Missing settings take the schema's `default`.

Publishing checks both sides: a step flow is refused when a step reads a setting `spec.settings` does not declare, and a service is refused when a variant's settings are unknown, missing where required, or not allowed by the schema (`spec.variants[i].strategy.config.settings.<name>`).

**Fixed filters per variant.** A variant can pin a retrieval filter with `spec.variants[i].filters`, in the same shape a caller sends as `filters`: `{ fields: [{ field, type?, value-type?, selected-options }] }`. For example, a `notifications` variant of a documentation service searches only pages whose `product` is `product_notifications`, so a channel or frontend only has to choose the variant (`docs-assistant__notifications`). The filter applies to every search the variant makes, and the agent is told it is active. A caller's own filters are added to it. On the same field both apply, so a caller can narrow a fixed filter but not widen it. Publishing refuses a filter on a field that none of the service's datasets declares (`spec.variants[i].filters.fields[j].field`), or whose type the field cannot run (`contains` needs a text field; `multiselect` and `not-in-set` a multiselect one). Reading or listing a document by its id is not filtered. A filtered search, like any filtered search, goes only to the datasets that declare every filtered field.

The builder assistant (`POST .../services/{id}/assistant/turns`) proposes a new variant from a plain sentence as a level-1 change: a recipe with settings, or, when no recipe fits, a new step flow in `proposal.flows` that the portal publishes before it applies the change. `POST /tenants/{tenant}/step-flows/{id}/assistant/turns` proposes changes to a step flow draft.

When the assistant cannot answer, the turn has `status: unavailable` and a `reason`: `not_published` (the builder service is not published on the platform), `no_model` (no usable model with tool support; choose one under `assistant.model`), `model_failed` (the model run failed) or `empty_result` (the run finished without a result). For the last two, `turnId` is the task id, and the API logs `assistant unavailable` with `level: warn`, the reason, tenant, task and model, never the message or draft.

Sharing: an operator shares one of Digdir's recipes with every organisation with `PUT /operator/recipes/shares/{flow}` and stops with `DELETE` (both need `change-reason` and are audited); `GET /operator/recipes/shares` lists Digdir's recipes and whether each is shared. A service names an exact version (`flow@N`), so a newer version of a shared recipe changes nothing until the owner updates the variant. After unsharing, no new service can use the recipe, while services already published keep their pinned version.

## Build and edit a service from your own admin UI

The portal is one client of these routes; another admin UI, or one an LLM generates from `/openapi.json`, needs nothing else. Every text the routes return comes in bokmål and English.

1. `GET /tenants/{tenant}/definitions/template`: a valid starting Service definition with a model the tenant may use.
2. `GET /schemas` and `GET /schemas/Service@v1`: the definition as JSON Schema with labels, help, widgets and the right needed (`x-` keywords). `uses` links the schema for each strategy config, guardrail, input field, output and trigger.
3. `GET /tenants/{tenant}/definitions/strategies`: the ways of working a service can use. Each has `how` (`single`, `agent` or `flow`), `default` (the one to pick when the person only chooses the way of working), name, description, pipeline steps, `newConfig` (the starting `spec.strategy.config` when the service switches to it), `takes` (whether the config takes the service instructions and examples), `defaultInstructions` (for a strategy with built-in instructions: the readable `text` per answer language and a `note` on what the platform adds at run time, such as skills, filters or the date in `{date}`; instructions written in the service replace them, unless `layered` is true: then they are added after the built-in `sections`, each with an id, title, reason and text, which the service edits one by one in `spec.strategy.config.promptSections`, see [ADR 0068](../adr/0068-layered-agent-prompt.md); the sections listed are those of a service with datasets, and a service without datasets has only `role` and `reasoning`, with its own text) and `schema` (its config schema under `/schemas`).
4. `GET /tenants/{tenant}/step-flows/blocks`: the step blocks for a step flow, with names (`title`, `summary`) and labelled param schemas.
   `GET /tenants/{tenant}/step-flows/operations`: the operations a `call-operation@1` step may call here, for any member of the tenant. Each has `id` (the descriptor), `operation` (its kind), `summary`, `status`, `input` (the typed input as `{ name, type, required, values? }`, with `type` one of `text`, `number`, `boolean`, `choice`, `list`, `object`), `media` (the media types it makes) and `models` (the tenant's models that offer the kind, as `{ id, name, residency, processorRecord }`). Descriptors in review, `decide` and kinds not in production in this `environment` are left out, so the list holds only what publish can accept. Whether the service masks personal data and whether the model is the service's own are checked at publish.
5. Edit the definition in your form. `POST /tenants/{tenant}/definitions/complete` with `{ definition }` fills in what the platform derives and lists each change in `applied`: residency from the model, form field ids from labels, the strategy's starting config, human approval for high risk, no required sources for a fields output (validation refuses them), only the output parts that belong to the output kind, and a result field's description from its name when it has none. Nothing is saved.
6. `PUT /tenants/{tenant}/services/{id}/draft` with `{ definition, files?, baseVersion, revision? }` to save, as in the sequence above. Save a new service the same way when it is started, under an id of its own while the name can still change; it is listed by `GET /tenants/{tenant}/service-drafts` until it is published. Publish it under the id it keeps, then delete the draft (ADR 0051).
7. Open the draft again with `GET /tenants/{tenant}/services/{id}/draft?rebase=clean`. If a newer version was published since the draft started, the API rebases the draft on read when nobody changed the same path (`rebasedFrom` says from which version, and the rebase is audited). When both sides changed a path, the draft is returned unchanged with `behind: true` and `conflicts` (`path`, `published`, `draft`) for the person to choose; save the choice with `PUT .../draft`. A caller without `manage-services` gets `behind` and no rebase.
8. `POST /tenants/{tenant}/definitions/test-run` to try it (a test run completes the draft the same way first), then `POST /tenants/{tenant}/definitions/complete`, `POST /definitions/validate` and `POST /definitions` with `draftRevision` to publish the completed definition.

To use a model in a service, there is no route of its own: read the draft (`GET .../draft`, or start one from the published definition with `baseVersion`), set `spec.model.primary` to the model's id (from `GET /models` or `GET /tenants/{tenant}/building-blocks/model/{id}`), and save it with `PUT .../draft` and the `revision` you read. `GET .../draft/checks` then says whether a publish would accept it, for example when the model runs outside the service's `spec.model.residency`.

`GET /tenants/{tenant}/services/{id}/environment-history` lists the changes to a service's environments, newest first, for any member with `use-services`: each has `environment`, `action` (`added`, `removed`, `promoted`, `rolled-back` or `described`), `version` (what the environment runs after it, `null` while it follows every publish or once removed), `previousVersion`, `from` on a promotion, `at`, `by`, `byName` when genki knows the name, and `reason`. `environment` filters it and `limit` (1 to 200, default 50) pages it, with `total` the changes that match. Changes saved before the action was recorded are inferred from the versions: an environment that appears or goes is `added` or `removed`, and a version that changed is `changed`, since whether it was a promotion or a rollback is not known. Publishing is not in it: an environment that follows every publish moves without a change of its own. An environment can carry a `description` of who uses it, at most 200 characters: give it when you add the environment, or set or clear it with `PATCH .../environments/{environment}` and `{ description }`.

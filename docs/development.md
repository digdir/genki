# Development

You need [mise](https://mise.jdx.dev) (pins Node 24.21.0 in `mise.toml`) and Docker.

```sh
mise trust         # once per clone, or mise ignores mise.toml and runs whatever Node is on PATH
mise install       # Node 24.21.0
npm start          # setup, then API, portal, console and workspace; stop all with Ctrl-C
```

`npm start` is `npm run setup` followed by `npm run dev:all`; run them separately when you only need one.

`npm run setup` is safe to run again: it starts `docker compose up -d postgres knowledge` (pgvector on `127.0.0.1:55432`, and the knowledge server, `pgvector/pgvector:0.8.2-pg17`, on `127.0.0.1:55433`), waits until both answer, and creates `.env.local` from `.env.example` only when it does not exist. The new file gets the local `DATABASE_URL`, a generated `CONTENT_MASTER_KEY`, `DEV_API_KEY` and `DEV_SERVICE_API_KEY`, the local test model, and the knowledge settings below. In an existing `.env.local` setup only adds the knowledge settings that are absent (an empty one stays empty, which leaves the knowledge server out) and names the other settings it lacks. Then it runs `npm run knowledge:setup -- --local`; with `--skip-docker` it writes the settings but skips this, so run it yourself once the knowledge server answers.

**The knowledge server.** Knowledge data moves to a Postgres server of its own ([ADR 0042](adr/0042-the-knowledge-database.md)). It has three roles: `genai_knowledge_owner` (migrations and partition DDL), `genai_knowledge_writer` (data, no DDL) and `genai_knowledge_reader` (only the read functions). The worker logs in with its own login and switches to the writer or the owner; the API logs in with another and can only switch to the reader. A pgvector endpoint with `options: { connection: knowledge }` uses those pools and never the platform database. Each generation of such a dataset is its own partition, and the dataset's catalog entry names the active one (`generation`, such as `g-20261030-7f3c2a`, set when the dataset is first published there). Only the worker writes to it. The API reads it only through the read functions, as the reader, on a read pool that falls back to the primary. To try it locally, `npm run knowledge:seed` writes a small demo generation and prints the catalog entries to add to `apps/api/config/local/knowledge.yaml`. Without a knowledge server, such an endpoint is left out with a warning in dev mode; outside dev mode the API refuses to start, and saving one is refused.

**Native output.** A converter's native output is kept by file sha256, with no tenant (ADR 0042): `<sha256>/<converter>/<version>/<settings hash>.json.gz`, gzipped, with `<settings hash>.meta.json` beside it, where the settings hash is the sha256 of the settings as canonical JSON. The `NativeOutputStore` in `packages/port-blob/src/native-output.ts` builds those paths; uploads keep the tenant-keyed `BlobStore`. In Azure the store is the Blob container `conversions`, reached with the knowledge worker identity (`KNOWLEDGE_AZURE_CLIENT_ID`, required) and never an account key; the worker's convert jobs write a converter's native output there (`nativeOutputStoreFromEnv`), and since the text layer has none, nothing reaches it until Docling (issue 477), though the account key, which the file share mount needs, opens the container too (ADR 0042, Open); the container deletes an earlier version 30 days after that version was written, so an output older than that loses its earlier version at a later lifecycle run once it is replaced or deleted. Locally it is a folder under `DATA_DIR` (`apps/api/.data/conversions`). `scripts/upload-docling-export.ts` copies a Docling export (`<prefix>/<sha256>/docling.json` with `done.json`) into the container once, skipping outputs already there (issue 474); it signs with your az login, or with the account key (`--auth key`), which the worker's native output store never signs with. `npm run conversions:check` writes, reads back and deletes a probe conversion; on the worker in Azure, run `node scripts/conversions-check.ts` with `az containerapp exec`.

**Seeded conversions.** `npm run conversions:seed` sends one `knowledge.seed` job per two-character sha256 prefix (256), by default for the Docling export of KUDOS (`--converter docling --version 2.123.1 --settings <settings hash>`). The worker lists the native outputs under each prefix, skips files that already have that conversion, and stores the pages `docling-pages` makes, with the Blob path; a file it cannot read is logged as `a seed skipped a file` and left to the text layer. Running it again sends no job for a batch that still waits or runs, and a finished batch sent again only skips. On the worker in Azure, run `node scripts/conversions-seed.ts` with `az containerapp exec`.

**Binding.** The platform server makes a random id the first time its migrations run, and `npm run knowledge:setup` stores it on the knowledge server, so the two belong together. The worker compares them at start and every minute until they match (a check before every drop comes with the `knowledge.drop` handler, issue 139). While they differ it runs no knowledge job, logs `knowledge server bound to another platform server` and answers 503 on `/readyz`. A worker without a knowledge server is ready. Binding a knowledge server to another platform server, such as a copy of production's search data given to test, takes `npm run knowledge:setup -- --admin-user <name> --api-login <name> --worker-login <name> --rebind --reason "<why>"`, run as an admin of both servers. It is recorded in the audit log as `platform.knowledge.rebind`, with the old id, the new id and the reason. A restore needs no rebinding, since a restored server keeps its id.

**Other ports.** To run a second copy next to one that already runs, give it its own compose project, Postgres port, model port and app ports:

```sh
COMPOSE_PROJECT_NAME=genai-second GENAI_POSTGRES_PORT=8110 GENAI_KNOWLEDGE_PORT=8111 GENAI_MODEL_PORT=8104 npm run setup
GENAI_API_PORT=8100 GENAI_PORTAL_PORT=8101 GENAI_CONSOLE_PORT=8102 GENAI_WORKSPACE_PORT=8103 npm run dev:all
WORKER_HEALTH_PORT=8105 npm run dev -w apps/worker   # only if you run the worker too
```

Setup writes the ports into the new `.env.local`, and `dev:all` points the Vite proxies and the login issuer at the moved API. The mock login accepts registered `http` loopback redirects (`localhost`, `127.0.0.1` or `[::1]`) on any port, for login and logout; every other character must match the registered URI. The default clients in `apps/api/config/local/identity.yaml` therefore work on shifted ports without changes, and `dev:all` names missing callback registrations at start. Real Ansattporten still needs the callback registered for each app's port. Stop the copy's database with `COMPOSE_PROJECT_NAME=genai-second docker compose down -v`.

The apps talk to the live API through a Vite proxy on `/api`. To run one against in-browser mock data instead: `VITE_API=mock npm run dev -w apps/portal`. `npm run dev` starts only the API.

**Dev mode.** The API refuses to start without `DATABASE_URL`, without `ANSATTPORTEN_ISSUER` (or `MASKINPORTEN_ISSUER` plus `MASKINPORTEN_JWKS_URI`) and without `ALTINN_PDP_URL`, and names the missing settings, unless `GENAI_DEV_MODE=true`; the worker refuses to start without `DATABASE_URL` under the same rule. Dev mode allows in-memory storage, the mock Altinn rights and the mock login below, which can issue operator tokens, so it is for local development only; the API logs a warning at startup when it is on, and refuses it under `GENAI_ENV=production` or `NODE_ENV=production`. `npm run setup` writes `GENAI_DEV_MODE=true` into a new `.env.local`, and `npm run dev:all` sets it for the API unless you set it yourself. In dev mode `npm start` and `npm run dev:all` also set `GENAI_ENV=test` for the API, as genki-test runs, and `GENAI_MOCK_RIGHTS=true` when `ANSATTPORTEN_ISSUER` is empty, so the test persons get their rights from `identity.yaml` even when `.env.local` sets `ALTINN_PDP_URL` (the real PDP does not know them and gives them none). Set either yourself, such as `GENAI_MOCK_RIGHTS=false`, to keep your own value. Outside dev mode the API refuses to start with `GENAI_MOCK_RIGHTS=true`. An `.env.local` made before dev mode existed works with `npm start` and `npm run dev:all`; add `GENAI_DEV_MODE=true` to it to run the API alone with `npm run dev`.

**API keys for local clients.** In dev mode with the mock login active, `DEV_API_KEY` registers a general dev key, and `DEV_SERVICE_API_KEY` registers a key bound to one service: `DEV_SERVICE_API_KEY_SERVICE`, `kunnskapsassistenten` by default. Both keys are in `.env.local` after setup.

**Locked environment.** `GENAI_LOCKDOWN=true` turns on what genki-test runs with: only the keys above, registered from configuration at startup, may run anything that reaches a model or run ingestion (pipeline runs, connector syncs, engine switches, applying hypothetical questions). People, operators and keys made through the API get a 403 problem that says the environment is locked, and scheduled runs and worker triggers are skipped. People can only read and search; keys made through the API can still change configuration as far as their scopes allow. `LOCKDOWN_ENTRA_GROUPS` (Entra group object ids) and `LOCKDOWN_ENTRA_EMAIL_DOMAIN` let an Entra ID login through Ansattporten in one of those groups work with the whole platform, as operator with every right in the platform organisation; the mock login cannot issue such tokens. `LOCKDOWN_USER_GROUPS` gives members of other Entra groups the same rights in the platform organisation, without the operator role. API keys such a login creates may use models and run ingestion too, within their bindings and scopes; Maskinporten clients it creates may only call the services they are registered for. `/health` reports `lockdown`, and the portal, console and workspace show a banner. See [ADR 0033](adr/0033-locked-test-environment.md).

**Trying a new kind of model API.** `GENAI_ENV=test` (genki-test sets it; any other value or none counts as production) lets an operator try an operation descriptor in review: `POST /operator/operations/{descriptor}/try` with `{ "model", "input", "synthetic": true }` and a `change-reason`. The call runs as a kernel task of its own on a model from the catalogue, with every PII category masked, media input let through only because the data is synthetic and, in lockdown, only for an admitted Entra login; it is audited and metered like any other call. Bundled descriptors live in `packages/operations/descriptors`, their recorded fixtures in `packages/operations/fixtures`, and `operation@1` proves each one in `npm test` (ADR 0047). An operator can also upload one with its fixtures on a running genki, `PUT /operator/operation-descriptors/{id}` with `change-reason`: the same loader rules and `operation@1` run on the upload, it starts in review, and the API and the worker pick it up without a restart ([operations.md](api/operations.md)).

**A new kind of model API from a descriptor alone.** A descriptor file in `packages/operations/descriptors/<provider>/<api>@<version>.yaml` is an API of its kind in its `family`; a catalogue model binds it in `apis` (`{ classify: example/classify@1 }`), next to the built-in APIs, and no TypeScript changes. A model only serves the kinds it binds, and only through the API it binds. The loader refuses a descriptor whose `stream` is not `none` (streaming is #302), or whose input could choose the model: a model field in the wire request must be `$deployment` at the top, and the executor sets it to the catalogue deployment anyway. A descriptor may also be a list of steps with bound values, polling, `finally` steps, multipart, form, binary, text and ndjson bodies, open usage units, error mapping and answer checks, all as data (ADR 0049, [operations.md](api/operations.md)); `packages/operations/src/testdata` holds made-up examples of each, proved by `operation@1` in `npm test`.

**Provider objects, modules and live sessions (ADR 0049).** A descriptor with `resources` records what a call keeps at the provider in the `provider_objects` table (`packages/providers-postgres`), deletes it in `finally`, and the worker's nightly sweep (`packages/jobs/src/provider-object-sweep.ts`, leader lease `genai-worker-provider-objects`) deletes the rest and writes an incident to the audit log when it cannot; the connection's processor record must allow provider state. A module is hand-built WebAssembly in tests (`packages/operations/src/wasm.test-utils.ts`), run in a worker thread with limits (`packages/operations/src/module.ts`). A live session is `GET /v1/sessions`: `apps/api/src/session-upgrade.ts` sends the upgrade through the same app as every route, then hands the socket to the `live-session@1` way of working; tests use an in-process fake WebSocket provider (`packages/operations/src/session.test.ts`, `apps/api/src/live-session.test.ts`). Fixtures of session descriptors record `session` messages and `operation@1` replays them. No test calls a live provider.

**Letting a service use a new kind of model API.** A service step flow calls a reviewed descriptor with the block `call-operation@1` (`params: { descriptor: example/classify@1 }`, the descriptor's typed input as the step `input`). The step runs on `params.model`, else the service's model for the kind in `spec.model.operations` (for example `{ classify: lab/classifier }`, a model used only for that operation), else its main model. It publishes only when the descriptor is reviewed (`status: described` or `typed`), its kind is not `decide` (served only through `purpose-check`), the service has the `pii-before-model` guardrail, an operator has moved the kind to production in this environment (`POST /operator/operation-kinds/{kind}/maturity`), and the model's endpoint has a processor record (`PUT /operator/model-endpoints/{id}/processor-record`). The gate checks the maturity and the processor record again on every call, and refuses image, audio and file input unless the service's confirmed risk assessment records unmasked input of that media type with a reason (`spec.riskConfirmation.unmaskedInput`, #326); publishing checks the same. A caller's own file is such input too: audio and images sent to a service (`input_audio` or a base64 `image_url` part on `/v1/chat/completions`, a file on the portal Test page) reach a step flow as `{{input.files.0}}` with media type, size and SHA-256, and the service's `spec.input.accepts` must list the media type. A draft (builder, playground, skill test, assistant) cannot run such a step; publish the service first. The local setup with neither maturity nor a processor record refuses such a step; the raw tier above needs neither, since its data is synthetic (ADR 0047).

**The local test model.** With `LOCAL_MODEL_URL` set, `scripts/local-model.ts` serves `local/echo` and `local/replay`. To try any model API without a real model, point a descriptor or service at `local/replay` and put its fixture, or any response file, in a folder named by `LOCAL_MODEL_RESPONSES` (several separated by `:`); it then answers any input. A response file is JSON with `request` (`method`, `path` and an optional `body`) and `response` (`body`, optional `status` and `headers`); a leading `/v1` on either path is ignored. A file whose `body` the request contains answers first, the one with the most keys winning. Otherwise any file with the same method and path answers, preferring one whose `body.model` equals the request's model, then the most matching top-level keys, then file name order. Files are read on every request, so a new one works without a restart. A chat completion no file matches gets the echo; anything else answers `404`. Nothing leaves the machine and nothing costs money. Without `LOCAL_MODEL_URL` the local models are skipped.

**Frontend clients.** `apps/api/config/local/clients/kunnskapsassistenten.yaml` registers an example client: a separate frontend for Kunnskapsassistenten on `http://localhost:5177`, allowed to call the platform from the browser. Nothing in this repository runs on that port; it shows how a frontend of your own is registered.

**A local Langfuse.** Screens that read from an agency's Langfuse (judges, judge costs, labels, datasets) show something only with a Langfuse connection that has data in it. `npm run langfuse` starts Langfuse 4.72.0, the version production is moving to, from `compose.langfuse.yaml`, or reuses the one already running, and returns once `/api/public/health` answers. Every worktree shares that one instance (compose project `langfuse-genki`, about 2 GiB of memory): its web UI is on `http://localhost:34620`, where you log in as `genki@example.com` with the password `genki-local-only`. `npm run setup` and `npm start` leave it alone; stop it with `docker compose -p langfuse-genki stop`. It is for made-up data only, never CI or a deploy. Its start project has the keys `pk-lf-genki-test` / `sk-lf-genki-test`. A connection to it takes the address `http://127.0.0.1:34620`, not `localhost`: the API's fetch tries `::1` for `localhost`, where Langfuse does not listen, and fails with `ECONNREFUSED ::1:34620`; the web UI stays on `localhost`, where its login works. For a walk or a feature, make a project of your own:

```sh
npm run langfuse:seed -- issue-1 --judge relevans --llm-from .env.local
npm run langfuse:seed -- issue-1 --delete
```

The seed deletes a project of the same name first, with its LLM connections, makes it again with its keys and prints the host, keys and ids as JSON. `--judge <name>` (repeatable) adds an LLM-as-a-judge evaluator that scores whether the answer answers the question, and an enabled rule that judges each case of a test run once (filter `isExperimentItemRootSpan = true`). `--llm-from <env file>` gives the judges their model: an LLM connection to Foundry Claude with that file's last `FOUNDRY_CLAUDE_KEY` and `FOUNDRY_CLAUDE_BASE_URL` (`--model`, default `claude-sonnet-5`); without it the judges are paused. A connection to the project takes the printed host and keys, the way an agency connects its own (ADR 0040); when `LANGFUSE_BASE_URL` names another Langfuse, pick "Egen Langfuse" in the form first, and when it is this local one (`http://127.0.0.1:34620`), pick "Digdirs Langfuse". Langfuse without a licence makes no projects through its public API, so the seed logs in as the start user and calls the routes Langfuse's own UI calls; a Langfuse upgrade may rename them. Both files run when read from `origin/main` into another folder (`git show origin/main:compose.langfuse.yaml > …`, then `docker compose -p langfuse-genki -f … up -d --wait`), which is how a walk of an older commit uses them.

Only `.env.local` is loaded automatically. Secrets in config are referenced as `secret://env/<name>`, which reads the environment variable `<NAME>` (`foundry-openai-key` reads `FOUNDRY_OPENAI_KEY`). At startup the API publishes the flows and services in `apps/api/config/local` (definitions that already exist are skipped) and runs database migrations. Services in `apps/api/config/local/dev-services`, such as "Lokal testchat" on `local/echo`, are published only with `GENAI_DEV_MODE=true`, so the test and production environments never see them. A variant whose model is not configured is left out and logged, so the service still starts with its other variants. Test sets in `packages/eval/testsets` and `packages/jobs/examples/testsets` that belong to a local service (by `spec.service` or the service's `evaluation.testSets`) are created the same way when absent. The quality screens show scores only after a test run, so on a fresh clone they stay empty.

**Decisions.** A model in `apps/api/config/local/models.yaml` binds one API per kind it serves under `apis`, its connection's default chat API when left out on a connection with one family ([ADR 0047](adr/0047-one-governed-path-for-model-operations.md), ADR 0048). `foundry-openai/gpt-6-luna`, the `gpt-6-luna` deployment on genki-test-ai (DataZoneStandard, Sweden Central), is declared there on the `foundry` connection with `apis: { chat: openai/chat-completions@1, decide: openai/decide@1 }` and `residency: eu`, so it serves chat and the Azure OpenAI Decisions API (`/openai/v1/decisions`) through the kernel port `decision`. A discovered deployment gets `decide` from an operator: `PATCH /operator/models/{id}` with `{ "apis": { "chat": "openai/chat-completions@1", "decide": "openai/decide@1" } }`, kept across discovery like residency. A service uses it through the guardrail `purpose-check` with `model: foundry-openai/gpt-6-luna`; it needs the Foundry settings, and in genki-test a login that may use models. No test calls the Decisions API; the adapter is tested against the documented examples in `packages/providers-openai/src/fixtures/decisions`.

**Embedders, rerankers and prices.** The embedding models and the `colbert` reranker are models in `apps/api/config/local/models.yaml`, with `apis: { embed: openai/embeddings@1 }` or `apis: { rerank: colbert/rerank@1 }` and their settings under the kind; there is no `embeddings.yaml`, and `rerank.yaml` holds only rerankers on engines without an API. `apps/api/config/local/prices.yaml` gives each model a price per kind in kroner per unit, such as `chat: { input-token: 0.00003, output-token: 0.00012 }` ([Model providers](providers.md)). `GENAI_PROCESSOR_RECORDS=enforce` makes typed chat and decide calls refuse real data on a connection without a processor record; unset or any other value, they log a warning once per connection and go through.

**Test-set runs side by side.** A test-set run (and the model matrix and improvement proposals, which run test sets too) runs a few cases at a time in the API process. `EVAL_CASES_PER_RUN` (4 by default) is how many cases of one run are in flight at once, `EVAL_CASES_PER_TENANT` (4) how many of one organisation's runs together, and `EVAL_CASES_PER_INSTANCE` (8) how many on one API instance; an organisation or run never gets more than the instance allows, and a value that is not a positive whole number takes the default. The model matrix counts as the platform organisation, which it charges. A free slot goes to the waiting run that has had a slot least recently, so a run that has not started yet goes first and no run or organisation can take every slot. The limits hold per instance, not across replicas: with two API replicas up to twice `EVAL_CASES_PER_INSTANCE` cases run at once, and a run waits only for runs on its own instance. A run is `running` from the start; while it has no case in flight and waits for a slot, it carries `queuePlace` (1 is next in line). Live calls to a service never wait for these slots. Before each case the run checks the organisation's monthly token quota, and once it is used up the run starts no new case, lets the cases in flight finish and ends `failed`; it can pass the quota by at most what those cases use (up to `EVAL_CASES_PER_RUN` cases).

**Ingestion pipelines from configuration.** Each file in `apps/api/config/local/pipelines` names a platform dataset, a pipeline id and its spec. At startup the API creates a pipeline that is missing and updates one that only the seed has saved; a pipeline someone changed through the API, portal or console is left alone. Seeding only saves the pipeline. Running it is ingestion, which needs a person or key with the right, and which lockdown limits like any other run.

**Parquet sources.** `INGEST_WORKING_DIRECTORY` is where the API puts scratch files for Parquet downloads (the OS temp directory when unset), and `INGEST_PARQUET_MAX_BYTES` is the platform ceiling on disk bytes per Parquet file, which a pipeline's `maxBytes` cannot exceed (1 GiB when unset). See [ADR 0039](adr/0039-parquet-sources.md).

**The GenKI guide.** The service `genki-guide` (GenKI-guiden) answers questions about GenKI itself, with sources, from the dataset `digdir/genki-docs` on the `platform-pg` endpoint, embedded with `foundry/text-embedding-3-small`. Its pipeline `genki-docs` (`apps/api/config/local/pipelines/genki-docs.yaml`) is a folder source with this include list: `README.md`, `CONTRIBUTING.md`, `docs/**/*.md` (ADRs, this file, the frontend contract, the API docs), `packages/*/README.md`, `apps/*/README.md`, `examples/*/README.md` and the System Atlas module files `docs/architecture/modules/*.yaml` (without `order.yaml`). Folder sources read `.md`, `.txt`, `.html` and `.htm` by default; this pipeline sets `extensions: [.md, .yaml]` so the module files are read too. Every document is titled by its first heading (a YAML file by its top-level `name:`) and links to its file on GitHub (`https://github.com/digdir/genki/blob/main/<path>`). The images build the same list into `/app/genki-docs` (`scripts/docs-bundle.ts`), and the containers set `INGEST_FOLDER_ROOT` there, so the guide in an environment answers from the docs of the code it runs. The pipeline runs only when started, and documents change only when it runs again: after a change to the docs, deploy and run it once more.

- Locally: set `INGEST_FOLDER_ROOT` in `.env.local` to the absolute path of your clone, so the pipeline path `.` is the repository root (the worker needs it too once the dataset is on the knowledge database, since its runs list the folder), and have the Foundry settings (embeddings and the model the guide answers with). Start the API, log in to the console as Ola Drift, open Katalog, then Datasett, choose GenKI-dokumentasjon, and press Kjør on the pipeline. With an operator token: `POST /operator/datasets/digdir%2Fgenki-docs/pipelines/genki-docs/execute` with a `change-reason` header, then follow `GET .../executions`.
- In genki-test: deploy, then a person in one of `LOCKDOWN_ENTRA_GROUPS` logs in to the console with Entra ID and starts the pipeline the same way, or calls the same route with that login's token. Scheduled runs are skipped in lockdown, so nothing reindexes by itself.
- In the console, Systematlas (`#/atlas`) shows the System Atlas on the whole window, with a link back to the console in its topbar. The guide is the chat panel under the details panel. Each module offers prepared questions (explain it, how it connects, where it is in the code, how to change it), each connection and each traced request has its own ask, and an answer lists the atlas modules it mentions so you can jump to them. The atlas page only sends the question to the console; the console asks the guide through `POST /v1/chat/completions` (model `genki-guide__default`) with its login's token and sends the answer back, so the token never reaches the atlas page. The login needs the right to use services in the platform organisation, so in genki-test that is the Entra ID login. Opened on its own, the atlas shows the chat panel with a note and no input.

**Durable jobs.** Work that must outlive a process runs as jobs on pg-boss ([ADR 0041](adr/0041-durable-jobs-on-pg-boss.md)). The worker installs them: at startup, as the owner role, it creates and migrates schema `pgboss` on the platform database, creates every queue on its list `platformWork` (`apps/worker/src/platform-work.ts`), with the dead-letter queue `<queue>.dead` when the queue keeps dead letters, grants `genai_worker` what sending and working need, and then works each queue with the handler the list pairs it with, as `genai_worker`. A queue goes on that list with its handler (`queueWork(queue, handler)`). The knowledge queues are the exception: the worker installs them without working them until their handlers exist (below). The worker's store pool runs as `genai_worker`, a member of `genai_runtime` that also has DML on `pgboss`; `genai_runtime`, which the API uses, reads only a job's id and start time, never its data, and changes or deletes no job: it has `EXECUTE` on the two read functions the console uses and, to send the knowledge jobs (below), `INSERT` on the job tables and `SELECT` on their `id` and `start_after` columns. pg-boss keeps every queue in the same tables, so that grant would let the API send to any queue on the platform server. `npm run dev:all` does not start the worker, so run it beside the API with `npm run dev -w apps/worker` when you need jobs; in dev mode without a database (neither `DATABASE_URL` nor `PGHOST`) it keeps an in-memory queue of its own. A queue is defined with `defineQueue`: its policy, an expiry of at most 24 hours, a heartbeat of at least 10 seconds, retries, whether failed jobs become dead letters, and a payload schema. Payload values are keys, such as ids and organisation numbers; a value with whitespace or longer than 128 characters is refused. A job that serves an organisation names it under `tenant`, the only key dead letters can be filtered on. A finished job is deleted after 7 days, and one nobody takes, a dead letter included, after 14 days. There are no platform queues yet.

**Knowledge jobs.** The worker also installs the knowledge queues of [ADR 0042](adr/0042-the-knowledge-database.md) (`packages/jobs/src/knowledge-queues.ts`): `knowledge.ingest`, `.push`, `.activate` and `.drop` on the platform database, where `genai_runtime` may send jobs, reads only their ids and start times, and changes or deletes none, and, when a knowledge server is configured, `knowledge.convert`, `.index`, `.fill`, `.build`, `.check`, `.cleanup` and `.export` in schema `pgboss` on the knowledge database, installed by `genai_knowledge_owner` and worked by `genai_knowledge_writer`; `genai_knowledge_reader`, the API's role there, may only call the two read functions. The worker works `knowledge.index`, `knowledge.convert` (2 at once, with the text layer; Docling in it with issue 477) and `knowledge.check` at any hour, and `knowledge.build` and `knowledge.fill` only inside the night window. A run sends a convert job for each PDF or Word file with no stored conversion in `src_conversions`, and the record waits; the finished conversion sends its index job, and index jobs read the stored pages. Runs of datasets on `connection: knowledge` run as jobs. Every minute, one worker at a time reconciles knowledge runs (`apps/worker/src/reconciler.ts`): it sends back the dead letters the API was asked to send back, ends runs whose jobs have all ended, starts a queued run whose pipeline has no open run, and drops jobs of runs that are gone, finished or cancelled. Heavy knowledge work runs in the platform setting `knowledge.nightWindow`, written as `01:00-06:00` in Europe/Oslo time, or `always` to let it run at any hour (as to fill datasets before a go-live), and set only for the platform; work is heavy above `knowledge.heavyThreshold` chunks (100,000, platform only). The worker works `knowledge.build` and `knowledge.fill` only inside the window, re-reads both settings every 30 seconds, and moves waiting heavy jobs to the window's next start when the window changes (`apps/worker/src/heavy-work.ts`). A run's index jobs become `knowledge.fill` jobs once its report counts the threshold in `chunks`; a run ends on the generation it wrote (its own, such as an engine switch's, or else the dataset's active one): a generation its first ingest job prepared standalone is built and attached, and an attached one gets `VACUUM (ANALYZE)`, at once below the threshold (throttled outside the window) or as a `knowledge.build` job naming the run above it; and `knowledge.check`, at the window start, sends `VACUUM (FREEZE)` and `REINDEX` builds. Writers take the generation's advisory lock shared and give way to VACUUM, which takes it exclusively (pgvector 0.8.2). To try it locally, set `knowledge.heavyThreshold` low in the console's platform settings. An engine switch from another engine to a `connection: knowledge` endpoint fills its generation with runs like these, and the worker drops a generation the switch leaves with a `knowledge.drop` job (ADR 0025). `MARKER_TIMEOUT_MS` (6 hours by default) plus an hour is how long a `knowledge.convert` job may run, at most 24 hours. `KNOWLEDGE_INDEX_CONCURRENCY` (8 by default, 1 to 32) is how many `knowledge.index` and how many `knowledge.fill` jobs one worker works at once; documents embed side by side and write to their generation one at a time. A 429 from the embedding model makes the job wait as long as the provider asks and pauses the worker's other jobs on that model, for up to 20 minutes a try, so the deployment's quota sets the pace instead of failing documents (`packages/ingest/src/throttled-embedder.ts`).

**Tests.** `npm run check` runs prettier, eslint, the type check, dependency boundaries, the apps' size budgets and every test. `npm run size` builds the portal, console and workspace and fails when an app's first load, its entry and the chunks that entry imports up front, grows past its gzip budget in `scripts/size-budget.ts`. Docker must be running: the Postgres, pgvector and Typesense-writer suites start containers with Testcontainers. Run a part with `npx vitest run <paths>`. Tests never call real models; the live suites skip themselves unless their settings are set.

## Quality

```sh
npm run check   # prettier, eslint, typecheck, dependency boundaries, size budgets, all tests
```

Tests use Vitest; the Postgres, pgvector and Typesense-writer suites start containers with Testcontainers, so Docker must be running. CI (`.github/workflows/ci.yml`) runs the same steps as `npm run check`, with the tests split over four runners, plus a gitleaks scan and a Docker image build, without pushing.

Quality of answers is measured, not assumed: `packages/eval` runs test sets with judges and publishing gates, and `apps/parity` compares the platform with headless-rag on the same questions ([apps/parity/README.md](../apps/parity/README.md)). Components behind a port, such as a document converter, an embedding model or a search engine, are compared with a candidate in `benchmarks/`, against a reference and a margin set beforehand ([benchmarks/README.md](../benchmarks/README.md), ADR 0003).

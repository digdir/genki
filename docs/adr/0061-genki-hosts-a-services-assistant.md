# 0061 genki hosts a service's assistant

Status: proposed, 2026-11-19 (platform login for hosted Clients, 2026-11-19; the portal, workspace and console on the platform login, and back-channel logout, 2026-11-25)

Left: a logo and images other than the tab icon in a hosted assistant; a host's own `x-` blocks (ADR 0065) in the generic host, which draws only built-in and declarative blocks; and production Ansattporten, which #464 decides. Each needs its own change. genki-test switches to production Ansattporten with its own platform login client by one variable (`docs/runbook.md`, "Production Ansattporten").

## Context

A service's end users need an assistant on a web page. Today a service owner who wants one writes and runs a web app, as Kunnskapsassistenten does: a client and a BFF in one container in the owner's own Container Apps environment, one replica with tokens in process memory, a confidential Ansattporten client with its secret as a Container Apps secret, and a custom domain with a managed certificate bound by hand. Its backend already runs on genki as a service.

genki has the parts for a hosted assistant but no host. `@genai/ui-assembly` draws an assistant from a layout (ADR 0054), ADR 0065 proposes to store the layout in the service definition as `spec.interface` and leaves the read route, the theme, the menu and pages to later records, a Client registers a frontend and maps its Ansattporten client id to one service (`clientRegistry` in `apps/api/src/frontends.ts`), and ADR 0034 requires a BFF before real people log in. genki serves four fixed apps (`api`, `portal`, `workspace`, `console`) from one apps image (`docker/apps`, chosen by `APP`), on hostnames set in `infra/main.bicep`.

## Decision

### One generic host, and frontends that run elsewhere

- **genki runs one generic assistant host.** It is a fifth app in the apps image, `APP=assistant`, deployed as its own container app (`${baseName}-assistant`) in an environment of its own, with an identity of its own that has no right on genki's Key Vault or Postgres (ADR 0062). It serves every hosted hostname. For a request it looks the `Host` up, and draws the service that hostname belongs to, with the interface of the version the hostname's environment runs (ADR 0065, ADR 0064). An unknown hostname gets a plain 404 page and no login.
- **A hosted assistant is configuration, not code.** A service, a published `spec.interface`, a Client with `spec.hosted: true` and its hostnames, and DNS records. No build, no image and no Ansattporten client per service. A hostname is an entry in the environment's parameter file and a deploy for now, and a self-service claim later (ADR 0062).
- **The host draws built-in and declarative blocks in its own origin, and the service's theme, menu and pages.** It draws the layout through `@genai/ui-assembly`, a declarative block as data with its own Designsystemet components (ADR 0067), the theme from ADR 0063, and the menu and pages below. It runs no code from the service owner in its own origin: a code block runs only in a sandboxed frame from the block origin (ADR 0069).
- **A service that needs its own frontend code runs it itself.** It runs its own container in its own Azure (or anywhere), and registers it as a genki frontend: a Client of kind `browser` with bearer tokens, as today (ADR 0032), or `server` with a service key. genki runs no team's container in its own Container Apps environment.
- **No Front Door.** Custom hostnames bind to the host container app with free managed certificates (ADR 0062). Apex names use the environment's static IP.

### The host's configuration

- **A Client registration says it is hosted.** `spec.hosted: true` on a Client of kind `browser` makes it a hosted frontend: it is drawn on its hostnames, from the parameter file or claimed (ADR 0062), and logs in through genki's platform login unless it names its own Ansattporten client in `oidc` (below), and its `allowedOrigins` are its hostnames' origins, kept in step by the API. A Client has at most one service, as today, so a hostname draws exactly one service.
- **`GET /v1/hosts/{hostname}` is public.** It answers what the host needs before anyone logs in: the tenant, the service, the environment, the issuer and the OIDC client id to log in with (not the Client's registration id; the platform login client for a Client without `oidc`), the assistant's name, the icon for the browser tab (`null` when the service has none), the theme's stylesheet address and the menu and page titles. It answers no secret, no layout zones and no profile, and the same `404` (`urn:genai:problem:host-not-found`) for every hostname that is not active, so the answer does not tell why. The host may cache it for 60 seconds, so a removed or lapsed hostname may still draw its page for up to a minute; no session call succeeds in that minute, since the API checks the hostname on every session request.
- **The layout itself comes after login,** from `GET /v1/models/{id}/interface` with the person's session, so the layout keeps the access rules of the service. This record adds the route, which ADR 0065 leaves out: it answers the `spec.interface` of the version the caller's environment runs (ADR 0064), with the theme as its stylesheet address, to a caller that may invoke the service, and `404` to anyone else.

### The BFF

The BFF in ADR 0034 is built for the assistant host and, since 2026-11-25, for the portal, workspace and console (#41, "The platform apps" below).

- **The BFF is in the API, under the host's origin.** The host's nginx proxies `/auth/` to the API's `/bff/auth/` and `/api/` to the API, and `/theme/` to the public `GET /v1/themes/{hash}.css` (ADR 0063), as the other apps proxy `/api/` today (`docker/apps/default.conf.template`). It adds `X-Forwarded-Host` and `GenAI-Proxy-Key`, a secret the host reads from a Key Vault of its own (ADR 0062). The API compares the key in constant time and trusts `X-Forwarded-Host` only with a valid key.
- **The routes are those Kunnskapsassistenten uses,** so its registered redirect URIs keep working: `GET /auth/login`, `GET /auth/callback`, `GET /auth/org` to show the choice of organisation and `POST /auth/org` to make it, and `GET /auth/logout`. Choosing an organisation changes the session, so only the `POST` does it, with the exact `Origin` of the hostname. A return address after login or a change of organisation is a path on the same hostname, starting with a single `/`; anything else returns to `/`. The redirect URI is `https://{hostname}/auth/callback`, and the post-logout URI `https://{hostname}/`.
- **The BFF is a confidential client.** It runs the authorization code flow with PKCE, `state` and `nonce`, with genki's platform login client by default, or with a hosted Client's own client when the Client names one in `oidc`, with that Client's `oidc.audience` as `resource`. It asks for `authorization_details` of the platform's Altinn resource either way, unless rights come only from Entra groups: then it sends `acr_values=entraid` instead (ADR 0033). It authenticates with `client_secret_basic`, and `private_key_jwt` is added when an owner needs it.
- **A Client's own client secret is a tenant secret.** `spec.oidc.secret` on the Client names a tenant secret (ADR 0015), written through the write-only secrets API and bound to the issuer's token endpoint origin as its only allowed host. The owner rotates it: a new secret in Ansattporten's self-service, then `PUT` of the new value. genki never shows it.
- **Tokens stay on the server.** Sessions are rows in Postgres (`bff_sessions`): the session id hash, the hostname and client it was made for, the person's tokens sealed with the tenant's content key (as tenant secrets are), the chosen organisation, and the expiry, at most 8 hours. The BFF refreshes the access token with the refresh token a confidential client gets. Any API replica serves any session, so a restart or a new revision signs no one out.
- **Cookies are host-only.** `__Host-genki_session` is `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/`, and holds only the session id. The login's `state`, `nonce` and PKCE verifier sit in a sealed `__Host-genki_login` cookie for 10 minutes. The session id is new at every login.
- **A session works only on the hostname it was made for.** The API turns it into the same principal a bearer token from that client gives (confined to the client, ADR 0032), and refuses it when `X-Forwarded-Host` differs. On every request it reads the session and the hostname's state from Postgres with no cache, so a deleted session, a removed or lapsed hostname, or a Client no longer hosted stops the next call. A state-changing request through `/api/` needs the exact `Origin` of the hostname and a JSON body or a non-simple header.
- **Logout** deletes the session, revokes the refresh token and ends the Ansattporten session with `id_token_hint`.

### The platform login

A hosted Client without `oidc`, and the portal, workspace and console, log in through one Ansattporten client that genki owns, so a new service needs no client of its own in Samarbeidsportalen.

- **The client is platform configuration.** `PLATFORM_LOGIN_CLIENT_ID` and `PLATFORM_LOGIN_HOSTNAME` (`login.apps.<zone>`, `platformLoginClientId` and `platformLoginStage` in `infra/main.bicep`), with the issuer from `ANSATTPORTEN_ISSUER`. Its secret, `PLATFORM_LOGIN_CLIENT_SECRET`, is a secret in genki's Key Vault whose name the template parameter `platformLoginSecretName` gives (default `platform-login-client-secret`), not a tenant secret, and goes only to endpoints on the issuer's origin. Without the id and the hostname the platform login is off, and a hosted Client without `oidc` draws nothing (`404`). The client id is reserved: no Client may name it in `oidc`.
- **The login host is the assistant host on its own name.** `login.apps.<zone>` is a hostname of the assistant host with a stage of its own, as the host's own name has; its nginx sends `/auth/` to the BFF as on any hosted hostname. It is never opened to a tenant, so no Client can claim it. It has the client's one redirect URI, `https://login.apps.<zone>/auth/callback`, and post-logout URI, `https://login.apps.<zone>/auth/logged-out`.
- **The handoff.** `GET /auth/login` on the service's hostname sets a sealed `__Host-genki_handoff` cookie holding a random binding value and the return path, and sends the browser to `https://login.apps.<zone>/auth/login?host=<hostname>&binding=<sha256 of the value>`. The login host takes only a hostname that is active, opened to its tenant and drawn by a hosted Client on the platform login; anything else, a URL included, gets `404`, so it is no open redirect. It runs the code flow with the platform client, its own `__Host-genki_login` cookie holding the target hostname and, sealed for that hostname, `state`, `nonce` and the PKCE verifier, checks the ID token, and reads the organisations as the target Client (below). It then stores the person's tokens under a one-time code: 32 random bytes, kept only as a hash in `bff_sessions` with the target hostname and Client, sealed with the tenant's content key, and valid for 60 seconds. It redirects to `https://<hostname>/auth/handoff?code=...`. A login it refuses, cancelled at Ansattporten or older than ten minutes, goes back to `https://<hostname>/` with no code.
- **The code works once, on its hostname, in the browser that asked.** `GET /auth/handoff` reads the code's row and deletes it, and goes on only when its own delete removed it, so a second use finds nothing; it then refuses the code unless the row names this hostname and Client, has not expired, and its binding equals, in constant time, the hash of the value in this hostname's `__Host-genki_handoff` cookie. A code shown in another browser, or one an attacker got for their own login and slips into someone else's, finds no matching cookie. Only then does the BFF create the session, under the same rules as any other: a new session id, sealed tokens, at most 8 hours, bound to the hostname and Client. No code, token or secret is logged, and the host's nginx keeps no access log of `/auth/`, whose query strings carry codes.
- **Logout through the login host.** Logout on the hostname sends Ansattporten the `id_token_hint`, the platform client id, the post-logout URI on the login host and the hostname as `state`. `GET /auth/logged-out` returns the browser to `https://<hostname>/` only when `state` is a hostname the login host would sign in for, and otherwise shows a signed-out page in the person's language.
- **Back-channel logout.** Ansattporten posts a `logout_token` to `https://login.apps.<zone>/auth/backchannel-logout` (OpenID Connect Back-Channel Logout 1.0). The login host accepts it only as a form POST and only when the token is signed with a key from the issuer's JWKS, has the issuer as `iss` and the platform client id as `aud`, an `iat` at most five minutes old, the back-channel logout event in `events`, a `sid` or a `sub`, no `nonce`, and a `jti` it has not seen in the last ten minutes. It then deletes every session, in every tenant and on every hostname, made from that Ansattporten login: by `sid` when the token has one, else every session of that `sub`, matched by keys (a hash of issuer, client id and value) that each session row keeps in `bff_sessions.logout_keys`. A login still on its way to the app is ended too, since its handoff row keeps the same keys. It answers 200 with `Cache-Control: no-store`, 400 to a token it refuses, and 503 when it cannot reach the issuer or the database, so Ansattporten may retry. A replayed `jti` is caught by a row it claims in `bff_sessions` under `PLATFORM_TENANT`, and released again when the sessions could not be ended.
- **The client id alone grants nothing.** A token from the platform client counts only when the BFF presents it for a session's hostname: the BFF marks the API call, inside the process, with the session's tenant and Client (`apps/api/src/bff/acting.ts`), and the token verifier then confines the login to that Client exactly as a login through the Client's own client is confined (ADR 0032). The same token sent straight to the API is refused (`invalid_token`), unless the client is also in `EMPLOYEE_CLIENT_IDS`, where it gets what such a client gets and no Client. Being in `OPERATOR_CLIENT_IDS`, `EMPLOYEE_CLIENT_IDS` or `SERVICE_ENTRA_CLIENT_IDS` never widens a session made for a hostname.
- **A Client with its own `oidc` keeps its own login,** on its hostname's `/auth/callback`, unchanged. An audience lives in `oidc`, so a Client on the platform login has none: it takes the platform client's `resource`, the API audience, and the schema refuses `oidc` with an audience and no client id, saying so.

### The platform apps

The portal, workspace and console sign in through the platform login, each on its own hostname, as a hosted hostname does.

- **Their origins are platform configuration.** `PLATFORM_APP_ORIGINS` on the API is `portal=<origin>,workspace=<origin>,console=<origin>`, https origins, each app on a hostname of its own and never the login host's; the template fills it from `hostnames.portal`, `.workspace` and `.console` while the platform login is on. An app the setting leaves out cannot sign in. The apps' nginx sends `/auth/` to the BFF and adds `X-Forwarded-Host` and `GenAI-Proxy-Key` to `/api/` and `/auth/`, as the assistant host does, whenever `GENAI_PROXY_KEY` is set (`docker/apps/30-genki-config.sh`).
- **The same login and handoff.** `GET /auth/login` on an app's hostname sets the handoff cookie and goes to the login host, which signs in for the app's hostname as for a hosted one and hands the session back with a one-time code bound to the browser that asked. A code made for one app's hostname works on no other. Sessions are kept under `PLATFORM_TENANT`, bound to the app's hostname and to `platform-app:<app>`, at most 8 hours.
- **A session carries the person's own rights.** The BFF calls the API for an app's session inside the process as that app (`actAsPlatformApp` in `apps/api/src/bff/acting.ts`), and only there does the token verifier take the platform client as an employee client: the person acts per tenant with the organisations of their token, as with the former app clients, and is an operator when `OPERATOR_SUBJECTS` or a trusted Entra group says so. The same token sent straight to the API, or by a page as its own bearer, is still refused.
- **The console refuses a non-operator.** The login host asks, as the console, whether the login is an operator's, and for anyone else creates no handoff code: it returns the browser to `https://<console>/?signin=not-operator`, and the console shows that the person has no access. `GET /auth/me` on the console answers `operator`.
- **Logout** goes through the login host as for a hosted hostname, and returns to the app's own `/`.
- **Locally,** in dev mode only, an origin may be `http://<app>.localhost:<port>` and the login host plain `localhost` with `PLATFORM_LOGIN_ORIGIN`, so a TEST Ansattporten client can register `http://localhost:5173/auth/callback` (`docs/development.md`).

### In lockdown

ADR 0033 lets a service-group login through only a client listed in `SERVICE_ENTRA_CLIENT_IDS`, which takes a deploy to change.

- **A hosted Client passes lockdown by configuration.** In lockdown, a login through a Client with `spec.hosted: true`, through its own client or the platform login made for its hostname, is treated as a login through a listed service client: the Client must be registered in `PLATFORM_TENANT`, and the login is confined to it, gets only `use-services` and is read-only, as ADR 0033 sets out. The API reads the Client from the database at each login, so admitting or withdrawing one needs no deploy.
- **In lockdown only a platform operator sets or clears `spec.hosted`.** It is the admin action `platform.client.hosted`, with a reason, in the audit log (ADR 0010). A tenant's own change to the Client cannot set it there. Outside lockdown the owner sets it as part of the Client.
- **`SERVICE_ENTRA_CLIENT_IDS` stays** for service frontends that are not hosted, such as bearer-token frontends a team runs itself. A platform client (`OPERATOR_CLIENT_IDS`, `EMPLOYEE_CLIENT_IDS`) can never be hosted. Listing the platform login client there admits no hosted Client outside `PLATFORM_TENANT`.

### Menu and pages

- **`spec.interface` gains `icon`,** an optional base64 `data:` address of a PNG or SVG image, at most 24 KiB. The public host answer returns it, so the tab shows it before login; the assistant sets it as the favicon only for `data:image/` values.
- **`spec.interface` gains `menu` and `pages`,** beside `layout` (ADR 0065) and `theme` (ADR 0063), within ADR 0065's 256 KiB for the whole interface. `menu` is a list of at most 12 items, each a label and either `page: <id>` or an `https` link. `pages` is a list of at most 12 pages, each an id, a title and a body in Markdown.
- **Texts are in each of the service's languages,** one string or `{ nb, en }` as ADR 0065 has them for the profile, so the host follows the person's language.
- **Markdown is drawn without HTML.** Raw HTML is dropped, links are `https` or `mailto` only, and images and embeds are drawn as links. A page is at most 32 KiB and all pages 128 KiB.
- **The host draws no bar of its own.** Before login it shows the service's name in the corner, the sign-in in the middle of the window and the menu under it, in the browser's language. Once the person is signed in, the menu, «Innstillinger» when the layout has the settings block, and «Logg ut» are in the assistant's profile menu (in the classic look with a thread list and no menu, «Logg ut» stays under the thread list), and the language is chosen under «Innstillinger». When the assistant cannot load, the message offers «Logg ut» (amended 2026-11-25). A service with one language in `spec.languages` (the host answer's `languages`) is drawn in that language, with no language choice under «Innstillinger».

### Thread continuity when a frontend moves to the host

- **A thread's owner is the tenant and `issuer|sub`** (`userKey` in `packages/conversations/src/routes.ts`). Ansattporten's `sub` is pairwise per client, as in ID-porten, so the same person gets the same `sub` only from the same client id.
- **A frontend that moves to the host keeps its Ansattporten client id** when its threads must stay. Its Client registration becomes hosted, with the same `oidc.clientId`, and its people see their threads. A new client id, the platform login's included, gives everyone new owner keys.
- **A platform login has a subject per Client.** One client gives a person the same Ansattporten `sub` on every service and tenant, so the verifier never passes it on: a login confined through the platform client gets as `subject` the base64url HMAC-SHA256 of `tenant|client|sub`, the Client being the registration id, under `PLATFORM_LOGIN_SUBJECT_KEY`, or when that is unset a key derived with HKDF from `CONTENT_MASTER_KEY` ([ADR 0070](0070-versioned-content-master-keys.md)) (`platformLoginSubject` in `packages/identity/src/verify.ts`). The same person keeps it on the same Client across logins, and gets another on every other Client. Everything keyed by the subject is then kept per Client: threads, runs and their feedback and documents, and the identity a remote backend is sent (`send.identity: subject`), so two tenants' backends cannot join their data on a person. Without either, as in dev mode without Postgres, the key is random per process and subjects change on a restart; with a database set, the API refuses to start the platform login without one of them.

## Why

A generic host makes a standard assistant a matter of configuration: the next service needs no web app, no Azure resources and no deploy, and a fix to the host reaches every service at once. Keeping custom frontends outside genki's environment keeps genki's network, identities and secrets free of code it did not review, and keeps ADR 0028 (custom logic comes from outside).

The alternatives, with what we found:

- **Only frontends that teams run themselves.** It is today's model. Kunnskapsassistenten shows the cost: its own resource group, environment, registry grant, identity, DNS zone, managed certificate and manual deploys, one replica because tokens are in memory, and a BFF with its own login code that each new service would copy. The next service owner would do it all again.
- **Only the generic host.** It leaves no room for a service whose interface the catalogue cannot draw. Bearer-token frontends are already built and cost genki nothing to keep.
- **Teams' containers inside genki's environment.** One place to run everything, but team code would share genki's network, egress and managed identities, and genki would carry the review, patching and incidents of code it does not own.
- **One host deployment per service.** Isolation between services' pages, but a deploy and a container app per service, which is what a host should remove. The host draws data, not code, so one deployment is enough.
- **The BFF as its own service, or in the host's container.** A separate service is one more thing to deploy, secure and scale, and the host's nginx image runs no application code. In the API, the BFF uses the session store, content keys, tenant secrets and token verifier that are already there.
- **The client secret as a Key Vault secret per frontend.** The API's identity would need to write Key Vault secrets at run time. Tenant secrets are already sealed per tenant, write-only and bound to hosts.
- **Only a client per service.** Each service owner registers a client, its redirect URIs and its secret before anyone can log in, which is a manual step per service when the host is meant to be configuration. The option stays for a service that needs its own consent screen or Altinn resource.
- **One session cookie for a parent domain.** Hosted hostnames are on many domains, and a cookie for `apps.<zone>` would reach every service on it.
- **The session id or the tokens in the redirect.** A URL is kept in history, logs and `Referer`; the code is worth nothing after one use, a minute, or in another browser.
- **Moving thread owners to new keys at #464.** It would need a mapping from each old `issuer|sub` to the new one, which the pairwise `sub` does not give and genki would have to build from identity numbers it does not keep. The threads are test data, so they start fresh.
- **Menu links only, pages elsewhere.** Kunnskapsassistenten's onboarding, change log and about pages are its own Markdown today; without pages in genki a hosted service would need a second web site.

## Consequences

- KA becomes a service, an interface, a hosted Client with its current client id, a hostname per environment (ADR 0064) and DNS records. Its own app and the resources around it are retired once the swap is verified and the team agrees.
- A hosted frontend's people keep their threads only while it keeps its client id and issuer. A move to production Ansattporten (#464) changes both, so every person starts with no threads on every frontend. Nothing is in production yet and the threads are test data, so they are not moved. If real threads exist by then, a one-off migration script is prepared at #464: it records, for each login in a window before the switch, the old `issuer|sub` beside the keyed person id ADR 0060 derives from the identity number; at each person's first production login it finds the same person id and rewrites the owner of their threads, feedback and settings (`conversations.owner_hash` and the rows keyed the same way) from the old key to the new, per tenant, with an audit entry. Not built.
- ADR 0034 is built by this record for the assistant host and, since 2026-11-25 (#41), for the portal, workspace and console.
- ADR 0065's `spec.interface` gains `menu` and `pages`, and `GET /v1/models/{id}/interface` is built; its `Left:` drops them on acceptance. Its 256 KiB and texts per language already hold the pages.
- ADR 0033 gains the hosted Client as a second way past lockdown for service users. `SERVICE_ENTRA_CLIENT_IDS` stays for service frontends that are not hosted.
- The apps image's CSP stays `script-src 'self'`; a hosted page loads no script, style or font from another origin, and Markdown links open in a new tab with `rel="noopener noreferrer"`.
- New settings: `GENAI_PROXY_KEY`, in genki's Key Vault for the API and in the host's own Key Vault for the host. For the platform login, `PLATFORM_LOGIN_CLIENT_ID`, `PLATFORM_LOGIN_HOSTNAME` and the Key Vault secret `platformLoginSecretName` names (`platform-login-client-secret`, or `platform-login-client-secret-prod` for the production client); the client is registered once per environment in Samarbeidsportalen (`infra/README.md`, "Platform login").
- The portal's Client form still asks every browser Client for an Ansattporten client id, so a Client moves to the platform login, and is edited there, through the API (`infra/README.md`, "Platform login").
- The binding ties a code to the browser that started the login, not to who controls the hostname's DNS. Whoever controls a tenant's own domain can receive the codes sent to it, as they could receive an authorization code through a Client's own redirect URI; the session it gets stays confined to that tenant's Client.
- The platform login client is the portal's, workspace's and console's login as well (#41). What a session may do comes only from the hostname it was made for: a hosted hostname's Client, or a platform app's own rights inside that app's session, never from the client id.

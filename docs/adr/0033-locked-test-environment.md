# 0033 Locked test environment

Status: accepted, 2026-10-14 (built, 2026-10-14; ingestion locked, 2026-10-15; Entra logins, 2026-10-15; keys and clients from Entra logins, 2026-10-15; security review fixes, 2026-10-15; client allowlist, 2026-10-16; user groups proposed, 2026-11-02; admission on the run for knowledge jobs, 2026-11-02; user groups built, 2026-11-03; admission shown on keys, 2026-11-10; test-runner keys built, 2026-11-10; Maskinporten clients hold no right, ADR 0027, 2026-11-11; a knowledge run admitted again, and when its admission runs out shown, 2026-11-15; service groups, 2026-11-16; a replacement run admitted until its files are converted, 2026-11-17; one genki environment, 2026-11-19; a hosted Client admits service groups, ADR 0061, 2026-11-19; a service frontend's refusal in the service's words, 2026-11-19; test-runner keys by their own switch, issue #464, 2026-11-21; the platform login client counts as a platform client in a platform app session, 2026-11-25; rights from Entra groups without lockdown or Altinn, settings renamed from `LOCKDOWN_*`, 2026-11-25)

## Context

genki-test logs people in through Ansattporten TEST. With TestID anyone can log in as any synthetic test person, including the general manager of the organisation that plays Digdir (`PLATFORM_TENANT`). Login does not keep strangers out of test, and every model call costs money.

## Decision

`GENAI_LOCKDOWN=true` locks an environment. It is off by default, and `infra/env/test.bicepparam` turns it on for genki-test with the template parameter `lockdown`.

In lockdown, only a credential from configuration, a trusted Entra login (below) or a credential such a login created may reach a model provider. A credential from configuration is an API key whose secret the API was given at startup (today `DEV_API_KEY` and `DEV_SERVICE_API_KEY`). The API marks such a caller when it authenticates the request, by the digest of the key it presented, so a key made or rotated through the API carries the mark only as described under Keys and clients from Entra logins.

- People (Ansattporten), operators and every other caller get a 403 problem, `urn:genai:problem:locked-environment`, whose title says the environment is locked, on routes that run models: service calls (MCP, OpenAI, A2A, tool calls), playground and test runs, builder assistant turns, eval and batch runs, project runs, the quality matrix, enrichment proposals, diagnostics, direct dataset searches (which embed the query) and skill fixes.
- The same callers get the same problem, with a title that says ingestion is locked, on routes that fetch documents or write new embeddings: running a pipeline (tenant and operator), syncing a connector, starting, retrying or activating an engine switch, and applying hypothetical questions.
- The model port refuses the same callers, so a model call from a route not on that list, a background job or a trigger fails too.
- The worker reads the same setting. It binds no triggers, so a document that lands in a folder or a scheduled trigger starts nothing, and each sync logs that it is locked. Its model port uses the same rule, and the worker runs as a system user without the mark, so any model call it makes is refused.
- The ingestion service refuses to start a run that a credential from configuration did not start. Scheduled runs and the first sync of a new connector therefore do not run; a scheduled run is recorded as failed with the reason and logged.
- People other than a trusted Entra login (below) are read-only: every change, meaning every write that needs a change reason (ADR 0026), gets the same problem with a title saying changes need an Entra ID login. Their own preferences, conversations, feedback and checks that change nothing stay open. API keys keep the rights their scopes grant to change configuration; Maskinporten clients have none (ADR 0027). Startup seeding from YAML is unchanged.
- Checks that send a stored secret to an address the caller chooses (a building-block contract test, an operator knowledge endpoint test) are not reads: they get the same problem for people other than a trusted Entra login.
- For the same people, opening a draft with `rebase=clean` shows that it is behind instead of rebasing it, and a batch estimate skips the sample runs and assumes a range.
- One authenticator decides for the lockdown gate and the routes: the routes use the same caller as the gate (API keys excluded from the definition and platform routes, as before, except a test-runner key, below). When a locked route gets a credential that resolves to nobody, the gate answers 401 instead of passing the request on.
- `/health` reports `lockdown`, and `GET /me` reports `lockdownReadOnly: true` for a login that may only read. The portal, console and workspace then show a banner that tells such a login that changes, models and ingestion need an Entra ID login. Trusted Entra logins and members of `MEMBER_ENTRA_GROUPS` see no banner.

The embedding port is not locked, so search keeps embedding queries and reading existing data. Writing embeddings is locked where it starts instead: ingestion runs in the background under a system user, so the embedding port cannot tell who started it, but the start can. Saving a pipeline, including one with a schedule, is configuration and stays allowed.

## Rights from Entra groups

Decided 2026-11-25 for moving genki-test to production Ansattporten (issue #464), built 2026-11-25.

The group rules below are genki's production rule for who gets in, not a part of lockdown: they apply whenever a group setting is set, whatever `GENAI_LOCKDOWN` says. Lockdown keeps only its own gates on models, ingestion and changes. The settings are `OPERATOR_ENTRA_GROUPS`, `MEMBER_ENTRA_GROUPS`, `SERVICE_ENTRA_GROUPS`, `SERVICE_ENTRA_CLIENT_IDS` and `ENTRA_EMAIL_DOMAIN`. They were `LOCKDOWN_ENTRA_GROUPS`, `LOCKDOWN_USER_GROUPS`, `LOCKDOWN_SERVICE_GROUPS`, `LOCKDOWN_SERVICE_CLIENT_IDS` and `LOCKDOWN_ENTRA_EMAIL_DOMAIN`; the API refuses to start with an old name and says which new name it became. The parameter files read only the new names, with no fallback to the old ones, so an emptied variable takes the group away. They are set in each GitHub environment, so prod has no group until its own variables are set (infra/README.md).

- **Members.** An Entra login (`acr=entraid`) in `MEMBER_ENTRA_GROUPS` (genki-test-users, `789b5488-39ec-47b3-9217-840e5cd957fd`) gets every platform right in `PLATFORM_TENANT`, Digdir's organisation, as "User groups" says.
- **Operators.** An Entra login in `OPERATOR_ENTRA_GROUPS` (genki-test-operators, `76d10637-d517-413c-a10b-84675a3ed64b`) is a platform operator with every platform right in `PLATFORM_TENANT`. Acting there, in its own organisation, it keeps its rights, counts as an operator on every route (built-in blocks, operator-only settings, sharing) and is not asked for a content reason ([ADR 0072](0072-operators-own-the-platform.md)): `tenantAccess` gives an operator holding every platform right in an organisation its operator self as `actor`.
- **Service users.** `SERVICE_ENTRA_GROUPS` and `SERVICE_ENTRA_CLIENT_IDS` keep the narrow rule of "Service groups": an employee uses a service through its hosted Client or a listed registered client such as KA's backend, and nothing else.
- **Only the Entra login counts.** The verifier reads the `groups` claim only from a token with `acr=entraid`. Another login's `groups` claim is ignored.
- **Nowhere else.** A group gives rights only in `PLATFORM_TENANT`, never in another organisation.
- **Everyone else is refused.** A login in no group, with an email outside `ENTRA_EMAIL_DOMAIN` or through another client gets `urn:genai:problem:entra-not-trusted` from the API, and the BFF shows a page that says the person has no access (403) instead of an empty organisation.
- **Without Altinn.** With `OPERATOR_ENTRA_GROUPS` or `MEMBER_ENTRA_GROUPS` set and `ALTINN_PDP_URL` empty, the API starts without the Altinn PDP. Rights then come only from the groups: every person login that is not an Entra login in a group is refused with the same problem, the PDP answers nothing, the BFF sends no `authorization_details` and sends `acr_values=entraid`, so people go straight to Entra ID. With `ALTINN_PDP_URL` set, Altinn logins work as before beside the groups, for the day Altinn comes back. The service group alone does not let the API start without Altinn.

Production Ansattporten (`https://ansattporten.no`) gives what the rule needs, tried with genki's production client on 2026-11-25: `acr: entraid`, `amr: [entraid, entraid-mfa]`, the email and name, and a `groups` claim with all the person's Entra object ids (34 in the trial, no cap seen). It gives no `pid`, no Entra tenant id and no organisation for the person: `consumer` is the organisation that owns the client. Tests that state each rule are in `packages/identity/src/group-rights.test.ts`, `packages/composition/src/entra-groups.test.ts`, `apps/api/src/boot-guard.test.ts`, `apps/api/src/operator-access.test.ts` and `apps/api/src/bff/platform-login.test.ts`.

Removing a person from a group takes effect at their next access token, which production Ansattporten issued for 120 seconds in the login of 2026-11-25. API keys the person made live until someone revokes them.

## Entra logins

Ansattporten also offers login with Entra ID (`acr=entraid`). Without any group setting the API refuses such a login. With `OPERATOR_ENTRA_GROUPS` set (comma-separated Entra group object ids; the API refuses to start if one is not a GUID), the API accepts an Entra login whose `groups` claim holds at least one of them. When `ENTRA_EMAIL_DOMAIN` is set as well, the `email` claim must also end with `@` and that domain, without regard to case. genki-test sets both, the domain to `digdir.no`. The login must also come from one of the clients in `OPERATOR_CLIENT_IDS` (comma-separated Ansattporten client ids), checked against the token's `client_id`, and never through a client a tenant registered; the API refuses to start with `OPERATOR_ENTRA_GROUPS` or `MEMBER_ENTRA_GROUPS` set and `OPERATOR_CLIENT_IDS` empty, unless the platform apps sign in through the platform login. The portal, workspace and console sign in through the platform login client (ADR 0061), which counts as a client in `OPERATOR_CLIENT_IDS` only while the BFF presents a session made for one of the three apps' hostnames; then `OPERATOR_CLIENT_IDS` may be empty, and the API starts without it when `PLATFORM_APP_ORIGINS` is set. A token from that client sent straight to the API never counts. The API also reserves these client ids, so no tenant can register a client with one of them.

A trusted Entra login gets the whole platform, so the team can work in test:

- every platform right (ADR 0027) in the platform organisation (`PLATFORM_TENANT`) for the configured Altinn resource, set by the verifier, so the Altinn PDP lookup has nothing to fill in (the token carries no `pid` anyway);
- the operator role, so `/operator` routes and the console open;
- the internal scope `grant:trusted-entra-login`, which lets it use models, run ingestion and change configuration in lockdown, and invoke services in the platform organisation without asking the Altinn PDP. Only the verifier sets this scope: an Ansattporten token's own `scope` claim is never read into the principal, and Maskinporten scopes starting with `grant:` are dropped.

Work such a login starts keeps its admission. Batch, eval and project runs, test runs and resumed tasks run in the API under the person's own principal. The quality matrix, ingestion runs and the re-ingestion of an engine switch run under a system user; when the person who started them may use models, the API gives that system user the configured-credential mark, the same mark a configured key carries. The ingestion service sets it on a run it admitted, and an engine switch records it when it is started or retried. Nothing a caller sends can set it. Work that no person starts stays refused in lockdown, whoever configured it: worker triggers, scheduled ingestion and project subscriptions that run a service on new documents.

An Entra login outside the groups, with an email outside the domain, or from another client, gets a 403 problem `urn:genai:problem:entra-not-trusted` that says so, instead of an empty session. The token lists no organisations, so the portal and workspace ask `GET /me` for the organisations, names and rights of the login, and show the email when the token has no name.

Why groups and not the email alone: the token carries no Entra tenant id, and anyone can create an Entra tenant and give a user any email address, including one at `digdir.no`. A group object id is a GUID that only exists in the tenant that created it, so membership of a Digdir group is evidence of a Digdir account. The email domain is an extra guard, not the gate.

## User groups

Proposed 2026-11-02, built 2026-11-03.

`OPERATOR_ENTRA_GROUPS` makes every member an operator, and the operator role reaches every tenant. `MEMBER_ENTRA_GROUPS` (comma-separated Entra group object ids; the API refuses to start if one is not a GUID, and when it is set and neither `OPERATOR_CLIENT_IDS` nor the platform login is) admits more people to `PLATFORM_TENANT` without that role:

- An Entra login whose `groups` claim holds one of `MEMBER_ENTRA_GROUPS` passes the same checks as a trusted Entra login: a client in `OPERATOR_CLIENT_IDS` or the platform login in a portal, workspace or console session, never a client a tenant registered, and an email at `ENTRA_EMAIL_DOMAIN` when it is set.
- It becomes an employee of `PLATFORM_TENANT` with every platform right (ADR 0027), as a trusted Entra login does, and gets the internal scope `grant:entra-member`, set only by the verifier. It is not a trusted Entra login and never gets the operator role, so operator routes, content reasons and the console stay closed to it.
- In lockdown it is admitted like a trusted Entra login: it may use models and run ingestion, it is not read-only, and API keys and Maskinporten clients it creates or rotates are stored with `admittedInLockdown`. `isAdmittedEntraLogin` in `packages/composition/src/lockdown.ts` is the check at those points; the operator directory looks only at `grant:trusted-entra-login`.
- A login in both settings is a trusted Entra login and operator; `OPERATOR_ENTRA_GROUPS` wins.
- Users work in the portal and workspace. The console is for operators: a user who signs in to it is told that it is only for the operations team.
- Removing someone from a user group takes effect at their next token, as for the trusted groups.

Membership is controlled by the lab, which monitors it, so the rights are those of the Digdir organisation's own people rather than a reduced set. Two groups remain because of the operator role. Rejected: adding these people to `OPERATOR_ENTRA_GROUPS` (they would become operators in every tenant), a list of persons in configuration (a deploy per change), and opening TestID logins to models (anyone can log in with TestID).

## Service groups

Built 2026-11-16.

Every Digdir employee should be able to use a published service in test, such as Kunnskapsassistenten, without getting any right to build, change or publish. An email domain alone cannot say who that is, since the token carries no Entra tenant id (above); a group object id can. `SERVICE_ENTRA_GROUPS` (comma-separated Entra group object ids, meant for Digdir's all-employees group; the API refuses to start if one is not a GUID) admits them narrowly:

- Only through a client in `SERVICE_ENTRA_CLIENT_IDS` (comma-separated Ansattporten client ids) that a tenant has registered as a frontend of its service, or through a Client with `spec.hosted: true` (ADR 0061), which the API reads from the database at each login. The login is then confined to that client as any registered-client login is (ADR 0008): it reaches only the client's service and channels, such as service calls, its own conversations and feedback, and `GET /me`. The client must be registered in `PLATFORM_TENANT`; one registered elsewhere is refused. Through a platform client, an unlisted registered client that is not hosted, a hosted client outside `PLATFORM_TENANT` or no client, the login gets `urn:genai:problem:entra-not-trusted`. The API refuses to start with a platform client (`OPERATOR_CLIENT_IDS`, `EMPLOYEE_CLIENT_IDS`) in the list, since those can never be registered. The list may be empty when hosted Clients are the only way in.
- In lockdown only a platform operator, acting in the tenant (ADR 0072), sets or clears `spec.hosted`, through `PUT /tenants/{tenant}/clients/{id}/hosted` and the admin action `platform.client.hosted` with a reason in the audit log. A tenant's own save of the Client cannot change `spec.hosted`, nor the `oidc.clientId` of a hosted Client, since either would move the admission to another client. A Client marked hosted while lockdown was off keeps its admission when lockdown is turned on; only Clients in `PLATFORM_TENANT` are admitted, and only an operator can change `spec.hosted` once lockdown is on.
- The email must be at `ENTRA_EMAIL_DOMAIN` when it is set, as for the other groups.
- It becomes an employee of `PLATFORM_TENANT` with only `use-services` and the internal scope `grant:entra-service-user`, set only by the verifier. It is not admitted (`isAdmittedEntraLogin` is false): it is read-only, may not run ingestion, create keys or clients, and never becomes an operator.
- It may use models only to invoke the service: the model gate admits it when it is confined to a service (`mayInvokeServices`), and on the routes that run models the lockdown gate lets it through only on the service calls (`serviceCallRoutes`: MCP, OpenAI, A2A and tool calls, and stopping a `/v1` run it started). Playground, test, eval, batch and assistant runs stay refused.
- The two other groups win where they apply: an operator-group member is a trusted Entra login on any of these clients, and a user-group member is a user on the platform clients. A user-group member who is also in a service group and logs in through a service client is a service user there.

A person a service's frontend does not let in is told so in words for an end user, in their language, with the same problem types: a person confined to a registered client who may not invoke services gets `urn:genai:problem:locked-environment` titled «Denne assistenten er bare åpen for ansatte i Digdir» and told to log in with their Digdir account or ask the service's team; an Entra login refused through a client that is not a platform client (`OPERATOR_CLIENT_IDS`, `EMPLOYEE_CLIENT_IDS`) gets `urn:genai:problem:entra-not-trusted` with the same words. Platform logins keep the words above. Tests in `apps/api/src/lockdown.test.ts`.

Rejected: listing KA's client in `OPERATOR_CLIENT_IDS` (it would admit user-group logins unconfined there and reserve the id, so the client could no longer be registered and confined), and every registered client of the platform organisation without a list (a new frontend would open models to all employees without a deploy).

## Keys and clients from Entra logins

An API key created or rotated by a trusted Entra login, and a Maskinporten client registered by one, gets the same configured-credential mark when it authenticates in lockdown, so a team member can hand the KA test backend a key without a redeploy. The API stores `admittedInLockdown` with the key (column `admitted_in_lockdown` in `legacy_api_keys`) or with the client registration, and sets it from the principal that makes the change, never from the request body. `verifyApiKey` and the Maskinporten client admission turn it into the internal scope `grant:admitted-credential`, which the API turns into the configured-credential mark only in lockdown.

- The mark gives model use and ingestion and nothing else. The key keeps its own scopes and bindings: a key bound to a service reaches only that service, it is never an operator, and it gets no platform rights (a test-runner key, below, is the one exception).
- Rotating a key or saving a client again sets the mark anew from the principal doing it, so a rotation or save by anyone else drops it. Revoking works as before.
- Keys and clients made before this change, by an API key, or by anyone outside lockdown have no mark.
- In lockdown the key lists give each key `modelsInLockdown`, true when it has the mark or is a configured key, so the portal can say on the key whether it may use models. Outside lockdown the field is left out.

This is safe because in lockdown only a trusted Entra login can create a key or register a client at all: TestID logins are read-only, and the mark comes from the creating principal's internal scope, which only the verifier sets. An API key that creates keys passes no mark on.

## Test-runner keys

Built 2026-11-10.

A post-deploy smoke test must exercise genki-test fully: run services, use the playground, read timelines, validate definitions, create and delete throwaway definitions, and open every portal and console screen. An admitted key reaches only the service routes, a TestID login only reads, and an operator token with write rights must never sit in CI. A test-runner key fills the gap.

- **Who sets it.** `POST /tenants/{tenant}/api-keys` with `testRunner: true`, only when the API runs with `GENAI_TEST_RUNNER_KEYS=true` (the template parameter `testRunnerKeys`, on for genki-test), whatever the tier and lockdown, and only by an operator acting in the platform organisation (`mayGiveTestRunnerKeys`): a trusted Entra login (`isTrustedEntraLogin`), or a login the operator directory makes an operator (`OPERATOR_SUBJECTS` through `OPERATOR_CLIENT_IDS`) acting with its own rights in `PLATFORM_TENANT` (`platformOperator`). In lockdown that is in practice the first, since a login that is neither a trusted nor an admitted Entra login is read-only. A member of `MEMBER_ENTRA_GROUPS` is admitted but not an operator, so it may not, unless `OPERATOR_SUBJECTS` also lists it: the key's operator reads would give it more than it has itself. An operator acting as an operator in the tenant is refused, as for every key. Until 2026-11-21 the grant needed lockdown on the test tier; the switch lets the smoke test run once genki-test becomes production (issue #464). When ADR 0035 makes operators never tenant principals, this rule needs a new creator. Otherwise the API answers 403 `urn:genai:problem:test-runner-refused`. The handler of `platform.apikeys.create` stores the grant only under the same conditions, whatever the request carries. The request must also set `expiresInDays` (1 to 90) and `callsPerMinute`, or the API answers 400, so a leaked key has a bounded life and rate. The key stores `testRunner` (column `test_runner` in `legacy_api_keys`). Rotating it drops the grant. The `smoke-` prefix is reserved for smoke tests: a test-runner key may change any definition whose id starts with it, a service or a StepFlow. `GET /tenants/{tenant}/access` reports `testRunnerKeys`, and the portal shows the choice only then.
- **Defence in depth.** `verifyApiKey` turns the stored flag into the internal scope `grant:test-runner`. The API drops that scope from every caller unless `GENAI_TEST_RUNNER_KEYS=true`, and from every caller that is not an API key, so a stored grant does nothing where the switch is off.
- **Reads.** In its own tenant the key passes the tenant gate and the definition and platform routes, as a principal with every platform right (ADR 0027) in that tenant, so a timeline shows details and usage. `GET` is allowed under `/tenants/{own}`, `/me`, `/models`, `/definitions*`, `/settings*`, `/shared-services`, `/schemas*`, `/onboarding/*` and `/openapi.json`, the reads the portal screens need. Routes under `/tenants/{other}` answer 404.
- **Writes.** `apps/api/src/test-runner.ts` refuses every other write with 403 `urn:genai:problem:test-runner-scope` (`refuseOutsideTestRunnerScope`). It allows: the check routes (`reasonFreeWrites` of kind `check`) outside `/operator`, outside `secretSendingChecks` and except the batch estimate, which may run samples; feedback; `POST /definitions`, the service lifecycle and the service draft save and delete when the definition id starts with `smoke-`; and playground runs whose every setup is a published service the key's grants reach or a `smoke-` service whose inline draft, if any, also has a `smoke-` id. The service routes (`/v1`, `/api`, `/a2a`) behave as for any key.
- **One decision point for changes.** `refusedAction` in `apps/api/src/rights.ts`, which every admin action passes through, refuses a test-runner key every action except `platform.service.publish`, `platform.service.lifecycle`, `platform.service.draft.save` and `platform.service.draft.delete` on a target whose id starts with `smoke-`. So no second route can change anything else, even if the route gate let it through.
- **Operator reads.** Only on `GET` of an allowlist of routes that hold platform configuration or health, `/operator/tenants`, `/operator/operations`, `/operator/models`, `/operator/apis`, `/operator/plugins*`, `/operator/catalog*`, `/operator/tracing`, `/operator/quality` and `/operator/knowledge/engines`, the API presents the key as an operator without the admission mark, so it can read and, being a person kind without an Entra login, is read-only in lockdown. Paths match exactly (or below `/operator/plugins/` and `/operator/catalog/` with plain segments only); the query string does not count. Some of these list every tenant: this is the one place the key sees other tenants, and it is deliberate, so the smoke test can open the console's configuration screens. Every other `/operator` route, including audit, onboarding requests, content reasons, tenant definitions, running tasks and tasks, the label queue, usage, dataset and pipeline specs and secret names, answers 403 `urn:genai:problem:test-runner-scope`, as does every other method on `/operator`. On every other route the key is not an operator, so the operator's rights in every tenant never apply there.
- **Drafts.** The key opens a draft that is behind the published version the way a read-only login does: it is shown as behind and not rebased, since rebasing is not one of its actions.
- **Never.** Content reasons, secret values, key creation, rotation and revocation, Maskinporten client registration, tenant settings writes, ingestion and batch runs.

The smoke service is internal (`spec.visibility: internal`, [ADR 0004](0004-service-capability-and-version.md#internal-services)): only operators and a test-runner key see it, so the key lists, runs and publishes `smoke-` services marked internal while tenant members never see them.

The playground checks the key's service grants in the kernel's key grant policy as well, and that policy only passes a playground run for a key granted every service (`*`). A test-runner key that should use the playground is therefore created for all services. The tests in `apps/api/src/test-runner.test.ts` state each rule.

## Why

Test should stay open for the team to look at, and for configuration to be tried, without letting anyone with TestID spend model tokens. A pipeline run also crawls arbitrary websites from our network and spends embedding tokens without a ceiling, so it is locked the same way. A registered client such as the KA test backend is the only legitimate external user that needs models.

## Consequences

- genki-test has no credential from configuration, so models run there for trusted Entra logins and for the keys and clients they create, such as the KA test backend's key.
- An admitted key stays admitted until it is revoked or rotated by someone else. Removing a person from the Entra group does not revoke the keys they made; revoke them in the portal.
- TestID logins, including test persons who are general manager of `PLATFORM_TENANT` and operators listed in `OPERATOR_SUBJECTS` (`issuer|subject` pairs for Ansattporten logins), can only read in genki-test.
- Who may work in test is decided by Entra group membership in Digdir, not by the platform. Removing someone from the group takes effect at their next token.
- genki-test has two security groups in Digdir's Entra tenant, owned by the lab and created by Digdir IT on 2026-11-03: `genki-test-operators` (`76d10637-d517-413c-a10b-84675a3ed64b`) for `OPERATOR_ENTRA_GROUPS` and `genki-test-users` (`789b5488-39ec-47b3-9217-840e5cd957fd`) for `MEMBER_ENTRA_GROUPS`.
- A new service frontend open to every Digdir employee in test is registered in `PLATFORM_TENANT` and either marked hosted by an operator or, for a frontend genki does not host, its client id added to `SERVICE_ENTRA_CLIENT_IDS`.
- There is one genki environment and no separate production environment (decided 2026-11-11, issue #464). genki-test becomes production when issue #464 moves its logins to production Ansattporten, with rights from the Entra groups (above) until Altinn comes. The rules that need `GENAI_ENV=test` end then. Test-runner keys do not: they follow their own switch, so the smoke test keeps running after every deploy. The template sets the tier (`platformTier`, `GENAI_ENV`), lockdown and the traces environment from parameters, so the resource names stay `genai-test-*` while the tier becomes production (infra/README.md, "Production switches").
- A new check that sends a stored secret somewhere goes in `secretSendingChecks`.
- A new route that runs a model goes in `modelRunRoutes` in `apps/api/src/lockdown.ts`, and a new route that ingests or writes embeddings goes in `ingestionRoutes`, so it gets the clear problem and not a failed task.
- Knowledge jobs ([ADR 0042](0042-the-knowledge-database.md)) run ingestion in the worker (ADR 0041) and are admitted on the record that admitted them, not by a mark the job carries. When the API starts, sends back, admits again or (with issue 139) approves a run that runs as jobs, it sets the run's `admitted_at` after checking the caller and lockdown; a trigger refuses any change of it by `genai_worker`, and nothing in a job's data can admit it. Before a handler fetches, converts or calls a model, the worker reads the run through a definer function under platform access and refuses unless it is admitted and, in lockdown, admitted within 24 hours; only then does the handler get a system user with the configured-credential mark, so this is the one exception to the rule above that refuses every model call the worker makes. A run refused that way is failed with the reason and keeps what it wrote; a queued run whose admission ran out fails without starting. A scheduled run in lockdown sends no job and is recorded as failed, as before. A run that needs longer is admitted again while it is queued or running: `.../executions/{execution}/readmit`, or `.../engine-switches/{sid}/readmit` for all of a switch's open runs, audited as `platform.jobs.readmit` and `platform.engine-switch.readmit`. Its jobs stay as they are and its 24 hours start again. In lockdown, the API shows when the admission runs out (`admissionRunsOutAt`) on a queued or running run that is not being cancelled, in a pipeline's runs list, and on a switch with open runs (the earliest of them), and the console and the portal warn in its last 4 hours. A replacement run, which converts text-layer files again over weeks of nights (ADR 0042), carries the admission of the run that sent it, when that admission still held as the run ended, and stays admitted until its files are converted. Sending knowledge jobs back (`.../executions/{execution}/redrive`) and admitting runs again join `ingestionRoutes`. Generation builds, activation and rollback get the same check when they are built.

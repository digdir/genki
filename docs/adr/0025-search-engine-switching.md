# 0025 Search engine switching

Status: accepted, 2026-10-12 (built). Proposed 2026-10-07

## Decision

A tenant can move a dataset to another search engine without services noticing until the tenant decides.

- **The new engine is filled beside the old one.** The routers open a dataset at a given endpoint (`openAt`), so the switch writes to the target while services keep reading from the current endpoint.
- **Two methods.** _Copy_ reads the documents out of the current engine (`IndexWriter.read`, or a read-only export from Typesense) and writes them to the target. It needs the same embedding model on both sides. _Re-ingest_ runs the dataset's pipelines again into the target and works across embedding models, at a higher cost. The estimate shows both before anything starts.
- **Quality is compared before activation.** When the switch is filled, the dataset's test set runs against both engines: hits in the top five, mean rank and latency, with example questions. If the new engine is worse, activating needs a reason of at least 20 characters instead of 10.
- **Activating is a catalog change.** It publishes a new version of the dataset entry pointing at the new endpoint, with the person's reason, through the normal admin path. Every instance picks it up through the change feed.
- **Rollback.** The previous engine and its data are kept for `knowledge.switchRetentionDays` (14 by default). Within that time, rollback publishes the previous dataset version again; after it, the old generation is dropped and rollback is refused.
- **Typesense needs its own write key.** The shared Typesense cluster is search-only for this platform. Switching to Typesense is refused with "Krever egen skrivenøkkel" until a separate key and an explicit decision exist.

## Why

Search engines differ in cost, residency and what they support (0023), and a tenant should be able to choose without re-registering datasets or touching services. Comparing on the tenant's own test set turns the choice into a measurable one, and keeping the previous engine makes it reversible.

## Consequences

- A switch is an `engine-switch` config entry; its progress and decisions are versioned and audited like any other change.
- The copy or re-ingest job runs on the instance that started it, and is not resumed elsewhere. While it runs, it writes a heartbeat on the switch every 30 seconds. A switch whose heartbeat is older than two minutes (configurable) is marked as failed with "Overføringen stoppet. Start den på nytt.", and the tenant can try again.
- The writer port can drop a generation that is still active in its engine (`drop(dataset, generation, { force: true })`). Through the routers, a forced drop is refused for the generation the catalog serves, also from another endpoint of the same engine, since pgvector endpoints share tables per dataset id.
- One instance at a time cleans up old generations, under a lease in the config entries: the copies a cancel, rollback or retry left on the target, and the previous engine's data when the retention period is over. Data on engines the platform may not write to, such as the shared Typesense cluster, is never deleted. A drop that fails is recorded and not retried automatically.

## Independent pipeline runs (#107, 2026-10-23)

A normal run replaces its pipeline's documents and keeps documents belonging to the dataset's other enabled pipelines. After building fresh documents, it streams the previously active generation with `IndexWriter.read` and copies the siblings' documents, chunks and phrases into the new generation before promotion. Stored vectors are copied unchanged: siblings are neither fetched nor embedded again. The run's `stored` count still counts only fresh documents.

- **Attribution.** Ingestion sets the dedicated `IndexDocument.pipeline` attribute and records the embedding model in `IndexDocument.embeddingModel`, outside the user metadata in `fields`, even with source metadata turned off. pgvector persists them in the nullable `kn_docs.pipeline` and `kn_docs.embedding_model` columns; the migration leaves all existing rows unattributed and never backfills from user fields. The memory writer preserves both attributes directly. Writers declare whether their store/read round trip preserves pipeline and embedding model provenance with the optional `preservesPipeline` capability. Typesense declares false: it does not store pipeline provenance, and its reads and exports yield unattributed documents. It creates, writes, reads and drops no provenance collection, so there are no extra provenance HTTP writes or export credential requirements. A user column named `ingestion_pipeline`, `pipeline` or `embeddingModel` remains ordinary metadata on every engine. Provenance-capable writers preserve both dedicated attributes on copy/import and clear it on unattributed replacement. Source identifiers keep their existing meaning. Document and chunk ids stay unchanged; with compatible embedding models, if two pipelines produce the same document id, the fresh document wins and becomes owned by the current pipeline. Separate datasets are needed to retain distinct versions of the same identity.
- **Embedding changes.** Fresh embeddings record the configured model id outside source metadata, and the pgvector migration leaves old model provenance NULL. Independent multi-pipeline runs scan enabled siblings before preparing or embedding and refuse a different or unknown model when the dataset has a configured model. This preflight is conservative: every enabled sibling that could be copied must match, even if fresh document ids might later replace it. The actual copies are checked again before promotion. Unattributed documents and disabled siblings are excluded. A single pipeline can replace its old generation with a new model. Rebuild every pipeline after a model change: use a combined re-ingest switch where available, or pause schedules, leave one pipeline enabled and run it to replace the old generation, then re-enable and run each remaining pipeline before resuming schedules. Every source must be available. Copy switches preserve model provenance on compatible vectors; vectors with a different or unknown model are embedded again with the target model, even when their dimensions match. User metadata never supplies a model id.
- **Lifecycle.** The ingestion service snapshots the enabled, undeleted sibling ids in the same scope at run admission. Documents owned by disabled or deleted pipelines are not copied, so they disappear at the next successful sibling promotion. A pipeline configuration change during a run takes effect on a subsequent run. A single pipeline never streams old documents. Its existing empty-source and failure behavior is unchanged; a multi-pipeline run with an empty, successful source can promote just its siblings, removing its own vanished documents. An entirely failed source does not promote.
- **Old generations.** On a multi-pipeline dataset, the first promotion after upgrade drops the unattributed documents of every other source. Guessing ownership from user metadata would keep stale documents indefinitely, so neither `fields.ingestion_pipeline` nor any other user field supplies provenance. Every source must be available to rebuild; documents from an unavailable source cannot be restored. The maintenance sequence is to pause schedules while leaving the intended pipelines enabled, run each enabled pipeline once sequentially, and only then re-enable schedules. Unrerun legacy sources can be absent until that rebuild completes. This first promotion is not gated behind an explicit migration action; whether it should be is a rollout decision to make before deployment. Adding a one-time migration action needs a coordinated API, scheduler and persisted migration-state design and is left open rather than introducing an unreviewed bypass flag.
- **Capabilities and failures.** A multi-pipeline run requires both `read` and the optional atomic `promoteIfActive` operation. Missing capabilities refuse the run before preparing a generation or embedding documents; there is no destructive fallback. pgvector and the memory writer implement both. The current Typesense writer lacks conditional promotion and therefore cannot run independent sibling pipelines safely; single-pipeline ingestion and combined engine-switch rebuilds continue to work. A read or copy failure leaves the served generation intact.
- **Concurrency.** The run captures the active generation before writing, and pgvector compares that value while holding the same transaction lock as ordinary promotion. If another run or switch promotes first, the stale run fails with a request to rerun; it cannot overwrite the newer result. This also covers a previously empty dataset and single-pipeline runs on writers with conditional promotion. A retry rereads the latest generation and copies the winning siblings. There is no automatic retry or repeated embedding. Existing process-local dataset run locks still reject overlap within an instance; conditional promotion protects separate instances. This does not coordinate pipeline configuration or catalog/embedding changes with running jobs, nor does it change engine-switch activation semantics.
- **Engine switching.** Re-ingestion still builds every enabled pipeline into one shared generation. These jobs write attribution but omit sibling carry-forward, so they do not copy the old endpoint or copy a shared generation into itself. Copies between provenance-capable engines preserve attribution along with the existing fields. Typesense does not store provenance, so a copy switch from Typesense yields unattributed documents even when copying to pgvector. On a multi-pipeline dataset, pause schedules and follow that copy with the same maintenance rebuild described above before re-enabling schedules; alternatively choose a re-ingest switch to pgvector, which attributes every enabled pipeline in its shared generation.
- **Cost.** Each independent run scans the active generation for model compatibility before ingestion, scans it again for carry-forward, and writes the enabled siblings' documents and vectors again, in addition to its own fresh documents. Work and temporary storage are proportional to that combined generation; model cost remains proportional to fresh documents. Copying streams documents rather than buffering the whole dataset, with a set of fresh document ids to resolve collisions. Single-pipeline runs avoid the scan and copy; conditional writers add one cheap active-generation lookup. Failed unpromoted generations remain subject to the existing generation lifecycle; this change adds no garbage collector for ordinary ingestion.

# 0025 Search engine switching

Status: accepted, 2026-10-12 (built; in-place updates and generation recipes proposed in ADR 0042, 2026-10-27; switches into the knowledge database through ingestion runs, 2026-11-04; copy into the knowledge database, 2026-11-05). Proposed 2026-10-07

## Decision

A tenant can move a dataset to another search engine without services noticing until the tenant decides.

- **The new engine is filled beside the old one.** The routers open a dataset at a given endpoint (`openAt`), so the switch writes to the target while services keep reading from the current endpoint.
- **Two methods.** _Copy_ reads the documents out of the current engine (`IndexWriter.read`, or a read-only export from Typesense) and writes them to the target. It needs the same embedding model on both sides. _Re-ingest_ runs the dataset's pipelines again into the target and works across embedding models, at a higher cost. The estimate shows both before anything starts.
- **Quality is compared before activation.** When the switch is filled, the dataset's test set runs against both engines: hits in the top five, mean rank and latency, with example questions. If the new engine is worse, activating needs a reason of at least 20 characters instead of 10.
- **Activating is a catalog change.** It publishes a new version of the dataset entry pointing at the new endpoint, with the person's reason, through the normal admin path. Every instance picks it up through the change feed.
- **Rollback.** The previous engine and its data are kept for `knowledge.switchRetentionDays` (14 by default). Within that time, rollback publishes the previous dataset version again; after it, the old generation is dropped and rollback is refused.
- **Typesense needs its own write key.** The shared Typesense cluster is search-only for this platform. Switching to Typesense is refused with "Krever egen skrivenøkkel" until a separate key and an explicit decision exist.

## Why

Search engines differ in cost, residency and what they support (0023), and a tenant should be able to choose without re-registering datasets or touching services. Comparing on the tenant's own test set turns the choice into a measurable one, and keeping the previous engine makes it reversible.

## Consequences

- A switch is an `engine-switch` config entry; its progress and decisions are versioned and audited like any other change.
- The copy or re-ingest job of a switch into any other engine runs on the instance that started it, and is not resumed elsewhere. While it runs, it writes a heartbeat on the switch every 30 seconds. A switch whose heartbeat is older than two minutes (configurable) is marked as failed with "Overføringen stoppet. Start den på nytt.", and the tenant can try again.
- The writer port can drop a generation that is still active in its engine (`drop(dataset, generation, { force: true })`). Through the routers, a forced drop is refused for the generation the catalog serves, also from another endpoint of the same engine, since pgvector endpoints share tables per dataset id.
- The comparison runs two endpoints against each other (`openAt`). Two generations on the same engine cannot be compared, because a pgvector search always reads the active generation.
- [ADR 0042](0042-the-knowledge-database.md), proposed, changes how pgvector datasets get new generations: in-place updates for normal runs, and generations, activation and rollback within one engine for a changed recipe. Activation names the generation in the catalog, and a named candidate can be searched and compared with the active generation on the same engine, which the previous point rules out today. For datasets in the knowledge database, documents owned by their pipelines replace copying the other pipelines' documents into each new generation (issue 107), and a disabled pipeline keeps its documents. A switch into the knowledge database fills its generation with ingestion runs that run as jobs (ADR 0041) and follows their run records instead of a heartbeat in the API, and an evaluation run that names the generation it fills is to check it through a service's full retrieval path before it is activated (issue 143, not built). Otherwise engine switches stay as described here, and a switch counts as an open run of every pipeline of its dataset.
- A switch into the knowledge database (ADR 0042) re-ingests through ingestion runs on the durable job queue (ADR 0041) into a generation that is not active, named as the catalog names one (`g-<yyyymmdd>-<6 hex>`). It follows their run records in the API's minute timer instead of a heartbeat, survives restarts and deploys, and waits for the night window when the fill is heavy. A run ends only once the worker has built and attached the generation, and the comparison reads it by name. Re-ingest is refused for a dataset with a second pipeline, search phrases or a source kind the knowledge database does not take yet.
- A copy into the knowledge database is one run of the switch's own, with no pipeline, which the worker runs as jobs like a re-ingest. It reads the dataset from its current engine, when that engine hands documents over one by one (the Typesense export: a listing of the documents collection, then one document with its chunks per index job), and writes a record per document, owned by `_copy` (ADR 0042), with the chunks as the engine holds them: the same text and order, new chunk ids from the document id, a page from Marker's page breaks when the text has them, and vectors from the switch's embedding model, which a copy into the knowledge database needs. A dataset that a Kudos pipeline fills, even one turned off, is named as that pipeline names it (`kudos:<uuid>`, the old number kept as an earlier id); a document with no UUID is skipped as `no_uuid`, and of two numbers with one UUID the higher is copied and the other skipped as `same_uuid`. Any other dataset keeps its ids. The switch shows its documents copied, skipped by reason and failed. Its refresh before activation is a copy again. The start may name up to 1,000 source ids: such a copy deletes nothing, compares, and is refused at activation. Its estimate scales the chunks and characters of the first 100 documents to the dataset, priced for the chosen model. Tests: "a switch into the knowledge database can copy a dataset, with a record per document", "activating a copy switch copies again before it publishes", "a copy of named documents compares but cannot be activated".
- A copied chunk keeps its document and position but not its old chunk id, so an expected source in a test set, written with the old engine's chunk id, matches a hit with another chunk id by its document (or earlier id) and position, never by the document alone. The switch's hit@5 comparison and the retrieval judges use the same rule (`sameSource`).
- While its runs are open, in `running` and `activating`, the switch holds every other run of its dataset: a start is refused with the switch's id, and a schedule firing is recorded as failed. Its own runs are never held.
- A retry after a failed fill writes on into the same generation; a retry after a failed comparison compares again. A fill whose documents partly failed goes on to the comparison and shows how many.
- Activating a switch into the knowledge database runs each pipeline once more into its generation, so what changed in the source since the fill is applied, and the switch is `activating` meanwhile. Once those runs have succeeded, the platform publishes the catalog version that names the knowledge endpoint and the generation, with the reason of the person who activated it (`platform.engine-switch.activate`, audited). Only that publish may move a dataset onto the knowledge database. A refresh run that fails puts the switch back to `ready` with its error.
- Left-over generations on the knowledge database are dropped by `knowledge.drop` jobs that the sweep sends; the worker refuses to drop a generation the catalog names as active. Rollback republishes the previous catalog version at once, and the knowledge database's records stay. Such a switch needs the API and the worker of the release that built it: an older API fails it for a missing heartbeat, and an older worker fails its runs, since the dataset names no generation on the knowledge database yet, so start one only once both run it.
- One instance at a time cleans up old generations, under a lease in the config entries: the copies a cancel, rollback or retry left on the target, and the previous engine's data when the retention period is over. Data on engines the platform may not write to, such as the shared Typesense cluster, is never deleted. A drop that fails is recorded and not retried automatically, except a `knowledge.drop` job, which the job queue retries and then keeps as a dead letter.

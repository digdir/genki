# 0041 Durable jobs on pg-boss

Status: proposed, 2026-10-29

## Context

The platform has no durable job queue. `@genai/jobs` defines a `MessageQueue` port (`send`, `subscribe`) with only an in-memory implementation (`packages/jobs/src/queue.ts`), so a message is lost on restart and its consumer runs in the same process. Long work runs inside one process, guarded by locks and heartbeats:

- an ingestion run holds a writer lock per dataset and collection (`writerLockKeys`) in a map in the API process (`apps/api/src/ingestion.ts`), so the lock does not hold across API replicas;
- an ingestion run still `running` more than 6 hours after it started is marked failed when an API instance starts, unless that instance is running it (`failStaleRuns` in `apps/api/src/ingestion.ts`), so an instance that starts beside another fails a long run the other is still working on (issue 176);
- pipeline schedules (`none`, `daily`, `weekly` at 03:00) fire from the API every minute and are safe across replicas because a firing writes a versioned config entry;
- an engine switch runs on the instance that started it and fails when its 30-second heartbeat stops (ADR 0025);
- batch, eval, project and quality-matrix runs keep an owner and a heartbeat in the API (`apps/api/src/background-lease.ts`), and a run whose instance stops is marked failed, or interrupted for an eval run, once its heartbeat is two minutes old;
- the worker fires trigger schedules from one instance at a time through a leader lease (`packages/providers-postgres/src/leader-lease.ts`).

The knowledge database proposal ([PR 125](https://github.com/digdir/genki/pull/125)) needs work that outlives a process: ingestion runs that last several nights, conversions that take hours on a GPU host outside Azure, and index builds that wait for a night window. A deploy must not lose any of it, and two replicas must not do the same work twice. This record sets the queue that work runs on; the knowledge database's own queues belong to its record.

## Decision

- **pg-boss is the platform's durable job queue.** A new `JobQueue` port in `@genai/jobs` sends a job with a priority, a key, a start time and an optional transaction, and runs handlers with heartbeats. Its implementation lives in `packages/providers-pgboss`, since vendor libraries stay in `packages/providers-*`. pg-boss 12 needs Node 22.12 or later (the platform runs Node 24) and PostgreSQL 13 or later. The `MessageQueue` used by `queue-message` triggers (ADR 0007) stays in memory until a trigger needs durability.
- **A job lives on the server that holds the state it follows from,** in pg-boss's own schema `pgboss` on that server, and is sent in the same transaction as the change it follows from, through pg-boss's `db` option, so the change and the job commit or roll back together. Each server that has jobs gets its own `pgboss` schema.
- **The worker runs jobs; the API only sends them.** `apps/worker` takes jobs with pg-boss `work()`, which sends heartbeats while a handler runs. The API's background work (ingestion runs, engine switches, batch, eval, project and quality-matrix runs) stays as it is until a record moves it into jobs.
- **Only the worker's role can read or change the job tables.** Of the roles the apps run queries as, only the worker's has DML on a server's `pgboss` tables. On the platform server that is `genai_worker`: a member of `genai_runtime` (ADR 0022) that also has DML on `pgboss`, with no login, not a superuser and without `BYPASSRLS`, and the migration refuses to run if it is either. `genai_runtime`, which the API uses, has `USAGE` on the schema and `EXECUTE` on the console's read functions, and no right on the tables. A record that introduces a queue the API sends to grants `genai_runtime` only what sending needs, and adds a test that sends to it as `genai_runtime`; pg-boss 12.38.0 reads `pgboss.version` and `pgboss.queue`, calls `pgboss.job_now()`, inserts into the job table and returns the job's `id`. The API cannot read, change or delete a job except through the read functions. It calls them through a `JobReads` port that does not start pg-boss, since starting pg-boss reads `pgboss.version`.
- **Every queue states its contract in code,** in one place per queue: its server, policy and key, expiry and heartbeat, retries and backoff, and dead-letter queue. The record that introduces a queue lists it. This record introduces none.
- **A job that calls a service outside the platform makes one attempt and waits for it.** The client sets its own header and body timeouts from that service's timeout, because Node's `fetch` gives up on a response without headers after 300 seconds by default ([undici `headersTimeout`](https://github.com/nodejs/undici/blob/main/docs/docs/api/Client.md)). The queue's retries replace a client's own retry ladder.
- **Jobs run at least once, so handlers are idempotent.** A handler writes its result under a key that a second run writes again, so running it twice leaves the same result.
- **Job data carries keys, never content.** A job names what it follows from by its own key, such as a run's id or a record's number. It never carries a title, a file path or any other value taken from a source or a user, since such a value can name a person. Payloads and stored errors hold no content. A handler that acts for an organisation takes the organisation from the record it loads, never from the job's data, so a job that names another organisation cannot act for it.
- **Jobs are deleted on a schedule.** A job is deleted 7 days after it ended, and a job nobody takes, a dead letter included, 14 days after it could first start (`deleteAfterSeconds` and `retentionSeconds`, pg-boss 12's defaults, set in code for every queue so an upgrade cannot change them). Job data holds only keys, so erasure under ADR 0011 never has to reach into the job tables.
- **A queue that fetches, converts or calls a model states how its jobs are admitted.** In lockdown (ADR 0033) the worker's model calls are refused, so such a queue says what admits a job before it starts and how long that admission lasts.
- **Failures are visible and can be sent back.** A job that fails after its retries moves to its queue's dead-letter queue and is reported to operators. A new console screen shows queue counts and dead letters to operators. Sending dead letters back (`platform.jobs.redrive`) is an operator action with a reason, audited (ADR 0010); a record that introduces a queue may let others send its jobs back. The API records the request and the worker sends the jobs back, since the API's role cannot change a job.
- **Recurring jobs use pg-boss `schedule()`** with `tz: 'Europe/Oslo'`, which sends one job per occurrence however many instances run.

## What the spike showed

A throwaway `pgvector/pgvector:0.8.2-pg17` container with pg-boss 12.38.0, a worker process per queue and a fake HTTP service that answers after a set time ([`benchmarks/knowledge-spikes/pgboss/`](https://github.com/digdir/genki/tree/evidence/knowledge-spikes/benchmarks/knowledge-spikes/pgboss) at tag `evidence/knowledge-spikes`):

| Check                                                          | Result                                                                            |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Install with a role that only has `CREATE` on the database     | Pass. Schema version 46 created in 120 ms                                         |
| A job sent inside a transaction that rolls back                | Pass. The job does not exist; the same send in a committed transaction does       |
| One queued job per `singletonKey` (policy `short`)             | Pass. The second send returns `null`; one queued job per key                      |
| Priority                                                       | Pass. Taken one at a time, jobs with priority 1, 10 and 5 come out as 10, 5, 1    |
| A job that always fails, `retryLimit` 2, dead-letter queue set | Pass. Three attempts, then the dead-letter queue, after 57 s                      |
| Worker killed (`SIGKILL`) mid-job, heartbeat 30 s              | Pass. Another worker took the job 30 s after the kill, and it completed           |
| A 10-minute job with a 30 s heartbeat                          | Pass. Handed out once, completed after 10 minutes                                 |
| A 6-minute response through Node's default `fetch`             | Fails after 302 s with `UND_ERR_HEADERS_TIMEOUT`; with both timeouts off it waits |

The spike tested only the `short` policy, which allows one queued job per key but any number of active ones. `exclusive`, `stately` and `singleton` are untested.

## Why

- **A library over our own module.** Claiming with `SKIP LOCKED`, leases, heartbeats, retries with backoff, dead letters, priorities and one job per key are each small, but the edge cases (a lease that lapses during a long call, a worker that only looked dead, a poison job) are where a home-made queue fails. pg-boss covers them, keeps everything in Postgres and passes the checks above.
- **Postgres over Azure Service Bus.** With Service Bus, "this file needs converting" and "a job is queued" live in two systems and can drift apart. In Postgres they commit together.
- **A queue on the server whose state it follows, not one central queue.** A job commits with its change only when both are on the same server. A central queue on another server would cross databases on every job whose state lives elsewhere.
- **The foundation first, without a queue of its own.** Evaluating with Langfuse ([ADR 0040](0040-evaluating-with-langfuse.md)) needs no queue while its judges are advisory: the wait for a judge's scores stays inside its eval run's lease, and trace deletes are pending rows the nightly purge works through. A judge that blocks needs that wait as a job, which ADR 0040 leaves to a decision of its own. The knowledge database's queues depend on its records, run states and admission rules, which are still under review. Settling the queue, its port and its rules first lets that review be about the knowledge database alone. On its own, this record changes no behaviour.
- **Grants, not a convention, keep the API out of the job tables.** The worker reads every organisation's jobs to run them; the API only sends. With DML for `genai_runtime`, one query in the API could read, change or delete every organisation's jobs, and only review would catch it. With grants, that query fails with `permission denied` in the first test that runs it, which is how ADR 0022 has the database enforce isolation where the application could get it wrong. A role, not a login: both apps already log in as the app identity and switch role per connection (`infra/README.md`), so the worker switches to `genai_worker` and needs no new identity. The cost is that a pg-boss upgrade that changes what sending touches needs `genai_runtime`'s grants changed.

## Consequences

- pg-boss creates and migrates its schema on start, which needs `CREATE` on the database. The owner role installs and migrates it, with `migrate` and `createSchema` off for the apps, and grants the roles above. A pg-boss upgrade that changes what sending touches fails the tests that send as `genai_runtime` until its grants are changed.
- On the platform server, the worker's pool runs as `genai_worker` instead of `genai_runtime` for everything it does, since it sends jobs in the same transaction as its changes. Its row-level security is the same as `genai_runtime`'s.
- On the platform server, the `pgboss` tables have no row-level security, like the kernel's tables (ADR 0022). The API reads job state only through `SECURITY DEFINER` functions that refuse to run without `withPlatformAccess`, and its role has no other way to read it, so ADR 0022's rule that a table the API reads directly gets a tenant column and a policy does not apply. ADR 0022 points here.
- pg-boss uses each process's pool for its server through its `db` adapter, so it gets the same Entra ID token as the rest of the platform; each pool's size and each server's `max_connections` include pg-boss's polling.
- pg-boss's documentation does not mention Azure Database for PostgreSQL. It was checked only in a container; the first deploy to test checks install, migrations and deletion before anything depends on it.
- An expiry cannot exceed 24 hours (`expireInSeconds` at most 86400). Work that lasts longer, such as an ingestion run over several nights, is split into jobs that each fit under that limit and keeps its progress in its record, so the next job goes on where the last one stopped. A single job that needs longer is out of contract.
- The 6-hour startup check for ingestion runs is unchanged here (issue 176). A record that moves runs into jobs must keep the check away from them.
- Not built (issue 155). Tests to add with the build, each named for its rule, on a test queue: a job sent in a rolled-back transaction does not exist; a killed worker's job is retried after its heartbeat; a job that keeps failing ends in the dead-letter queue and is reported; job payloads hold no content; an ended job is deleted after 7 days; a nightly schedule sends one job per occurrence with two instances; the console reads jobs only with platform access; `genai_runtime` cannot read, change or delete a job; the worker sends and works jobs as `genai_worker`; the migration refuses a `genai_worker` that is a superuser or bypasses row-level security. With the first queue that has a real handler and record (issue 135): a handler run twice leaves the same result; a client of an outside service makes one request per attempt and waits longer than 300 seconds when its service's timeout says so; a handler acts for the organisation of the record it loads when the job's data names another. With the console screen (issue 181): sending back is audited and only operators can do it.

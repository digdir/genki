# 0051 A new service is a draft on the server

Status: proposed, 2026-11-03 (built, 2026-11-11: drafts saved from the first change, `GET /tenants/{tenant}/service-drafts`, deleting the draft of a service never published; amended 2026-11-20: an empty draft is saved when Ny tjeneste opens; amended 2026-11-24: every publish goes through the publish page; amended 2026-11-26: every service gets the new Oppsett; amended 2026-11-27: a new service is refused an id another service has)

## Context

The builder saved the draft of a published service on the server (`PUT /tenants/{tenant}/services/{id}/draft`), but a service that had never been published lived only in the builder's memory. A reload, a closed tab or another browser lost it, and it never showed under Tjenester.

## Decision

- **A new service is saved as a service draft as soon as Ny tjeneste opens,** the same entry a published service's draft uses: config entry kind `service-draft`, scoped to the tenant, with `baseVersion: 0`. The portal saves the platform template under a new id and opens that draft, so a new service has the same Oppsett, draft checks and address as any other draft from the start. Every service, published or not, gets the same Oppsett: one form with the builder assistant beside it, and an Avansert tab with how it works, tools, variants, limits, API keys and channels, JSON and YAML. Utforming offers Maler and Designelementer; the words a layout already holds stay in it and in Avansert → JSON. The YAML under Avansert writes to the draft only text the schema check (`POST /definitions/validate`) accepts. The old addresses of a published service lead to their new places (`/channels/{frontend}` to the same client under Avansert, `/settings` to Avansert → Grenser, `/definition` to Avansert → YAML, `/setup/risk` and `/setup/guards` to the publish page). Until 2026-11-20 the first change saved it, and the builder showed a separate form before that.
- **Every publish goes through the publish page, for every service.** Publiser opens `#/services/{id}/setup/publish`. A service never published gets a first publish page (what is left, Utgave 1, risk and safety rules) and then opens as the published service; a published one keeps the page that compares the draft with the edition in use, where its risk level and safety rules are set too, and returns to Oppsett after the publish. The publish dialog is gone.
- **The draft has an id of its own until it is published.** The client picks it; the portal uses `utkast-` and eight hex digits. The name, and the id the service is published under, can change until the first publish. The portal publishes under the first free id from the name (`name`, `name-2` and so on, archived services counting as taken), then deletes the draft, and opens the published service. It picks the free id itself and does not warn before publish that the name's id is taken: a second «Kopi av Svar» is published as `kopi-av-svar-2`. A public name the portal made from the name follows that id (`kopi-av-svar-2__default`), since the platform refuses a public name another service has; a public name the person typed stays. It sends `newService: true` with that `POST /definitions`: the API then publishes only a version 1, and answers `409` `urn:genai:problem:service-id-taken` with the `id` when another service, archived ones too, already has the id, so a new service can never become the next version of another. The store checks it in the transaction that writes the version, so two new services publishing under the same id at once cannot both get it. A publish without `newService` stays the next version of the id, as from a published service's draft or straight from YAML. The admin MCP's `publish_definition` sends `newService: true` only when it is given `newService: true`, as for a service from `new_service_template`. Only when the list of services cannot be read does the portal publish under the id from the name, and then the `409` says the id is taken on the first publish page.
- **`GET /tenants/{tenant}/service-drafts` lists the tenant's drafts,** newest first: `id`, `name` (null until the draft is named), `purpose`, `outputKind`, `latestVersion` (null for a service never published), `revision`, `at`, and who saved it last (`by`, `byName`). Any member of the tenant reads it, as with one draft; saving and discarding need `manage-services`.
- **The draft belongs to the tenant,** as the service will. Every save records who made it, and the audit log has each one. The browser holds no copy a person could lose: the playground's remembered setups in `localStorage` keep no definition. Web pages, own documents and the wished result, which the draft cannot hold yet, are kept only in the page's memory per tenant and service, never sent to the API, and forgotten on logout.
- **A draft of a service never published can be deleted from its page.** «Slett utkastet» asks for confirmation on the page, then calls `DELETE /tenants/{tenant}/services/{id}/draft` with the revision it last saw and returns to the list. It is offered only to someone with `manage-services`, and only once the draft is saved. The draft of a published service is not deleted this way.
- **`GET /tenants/{tenant}/services` stays the list of published services.** Key bindings, the code examples and the admin MCP read it as services that can be called.

## Why

People expect work in progress to be kept where they work, from any browser, as the draft of a published service already is. The alternatives were turned down:

- Browser storage keeps the work in one browser and loses it with cleared site data.
- Unpublished services in `GET .../services` would show up as callable services to every reader of that list.
- An id fixed from the name at the start would either keep a name typed later out of the id, or leave the draft behind when the service is renamed.
- A draft only its creator can see would be a new access rule; the draft of a published service is shared in the tenant.

## Consequences

- A draft that is never published stays in the list until someone deletes it. Since Ny tjeneste saves on opening, that includes drafts nobody changed; removing untouched drafts is not built.
- The id rule's tests are `apps/api/src/service-id-taken.test.ts`, against the in-memory store and Postgres, and the builder's in `apps/portal/src/screens/services/live-builder.test.tsx`.
- The tests are `apps/api/src/service-drafts.test.ts` ("the list of service drafts") and `apps/portal/src/screens/services/live-builder.test.tsx` ("a new service saved as a draft on the server").

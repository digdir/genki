# 0030 Frontends from schemas

Status: accepted, 2026-10-12 (a: partly built; b: built, proven by two contract-only builds)

Not built yet (a): portal screens for settings, guardrails, service input fields, tool-connection registration, datasets, triggers and the catalogues still use handwritten forms. Built: the server, the shared renderer, the console schema browser, portal step-flow block params and portal service strategy settings.

The decision has two parts that can succeed or fail separately: (a) schemas and the shared renderer for the platform's own screens, and (b) schemas and the published contract for external and LLM-generated frontends.

## Decision

### (a) Schemas and a shared renderer for the platform's own screens

Every configurable thing on the platform is described by a published, versioned schema with UI metadata, so a frontend for end users, service owners or Digdir operators can be generated from it. Handwritten screens are allowed where the design asks for more, but they read the same schemas, and nothing configurable exists only in a handwritten screen.

- **What is described.** Every definition kind (Service, StepFlow, Skill), every strategy config, step block params, guardrails, the settings registry, catalogue entries (models, datasets, rerankers, embeddings, prices), building blocks and plug-in manifests, tool connections, triggers, and each service's input fields and output.
- **Format.** JSON Schema 2020-12 generated from the zod schemas that validate the config, so the schema a frontend sees is the one the API enforces. UI metadata sits on each property as `x-` keywords:
  - `x-label`, `x-help`: `{nb, en}` texts, resolved to one language when the request says `Accept-Language`;
  - `x-group`, `x-order`: sections and order;
  - `x-widget`: a hint from a fixed list (text, textarea, prompt, number, toggle, select, multiselect, model, dataset, tool, secret, cron, code, list, map);
  - `x-options`: where choices come from (an enum, or an API route such as the model catalogue or a dataset facet);
  - `x-right`: the platform right needed to change it (ADR 0027), and `x-operator` for operator-only;
  - `x-settableAt`: for settings, the layers that may set it (ADR 0006);
  - `x-readOnly`, `x-advanced`, `x-showIf`: published-and-locked fields, fields hidden by default, and conditions on other fields;
  - `x-sensitive`: never echoed back (secrets, keys).
- **Where it is served.** `GET /schemas` lists kinds and versions; `GET /schemas/{kind}@{version}` returns one schema, with `ETag`. Strategy, block and plug-in schemas are listed under the kind that uses them, so a service editor can fetch the config schema for the strategy a service picks. Tenant-specific choices (`x-options` routes) are resolved by the frontend with the person's own token.
- **One renderer.** A shared React package renders a schema with Designsystemet: fields, groups, validation messages from the API's problems, rights (disabled with the reason), and read-only views. The portal and console use it for every config screen; the workspace keeps rendering services from their input fields and output.
- **Proven by tests.** A test fails when a property has no `x-label` in both languages, when a widget hint is unknown, when a route is missing from `/openapi.json`, or when a config screen sets a value its schema does not describe.

### (b) Schemas and a contract for external and LLM-generated frontends

A frontend that is not the portal, written by an agency or generated by an LLM, must be buildable from what the platform publishes, without reading the repository. Three sources, read in this order, are enough:

- `docs/frontend-contract.md`: auth, the `/v1` extensions (including the per-service `input_fields`, `_chat`, `_batch`, `_documents` and `status` on `GET /v1/models`), conversations, citations, streaming and errors. `docs/build-a-frontend.md` gives the shortest call sequence.
- `/openapi.json`: every route with its request and response shapes.
- `GET /schemas` for what can be configured, and `GET /v1/models/{id}/schema` for one service: its concrete input form and its output shape as JSON Schema 2020-12 with the same `x-` metadata and `Accept-Language` resolution as (a), so `@genai/schema-forms` or any JSON Schema form library can draw it. It uses the credential a frontend already has for `/v1/models`, answers only for services that credential may see (`404` otherwise), and its `input` accepts and rejects the same values as the API's input validation.

**Proof.** Twice, an LLM agent with only these documents and a running API (fake model, no access to the repository) built a working, generic frontend, checked in a headless browser. The first build covered the service list, forms drawn from the schema, streaming, both languages, conversations and feedback. The second added a dataset: sources and `[N]` citations, filters, table output, attached documents and a service key acting for an end user. Each gap the builders found was fixed in the API or the contract, with a test. Not proven yet: streaming edge cases with a real model (`retract`, `no_answer`), version pinning and batch runs, and a third build against the fixed contract.

## Why

The platform's promise is configuration and API first (ADR 0023): a new service, model or building block should not need frontend work, and agencies may build their own frontends. Schemas the API already enforces are the right foundation, but without published schemas and UI metadata every screen had to be written by hand, and the labels lived in frontend code where other frontends could not reach them.

## Consequences

- Labels and help texts for configuration move from the portal and console catalogues to the schema metadata, in one catalogue per package next to the schemas. The apps keep catalogues only for their own chrome.
- A new strategy, block or plug-in kind shows up in the portal and console when its schema has metadata, without a UI change.
- Schema versions follow the definition versions (`genai/v1`). A breaking change to a schema is a new version, and both are served while clients move.

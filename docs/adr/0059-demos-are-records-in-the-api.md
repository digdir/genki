# 0059 Demos are records in the API

Status: proposed, 2026-11-17 (records, seeding, library routes, recorder upload routes and the console library built; recordings queued and cancelled from the console, demo settings, progress by step screenshots and the workflow uploading to the library built 2026-11-18; the scheduled demo-recorder workflow and its queued list built 2026-11-25; `workspace` no longer an app, 2026-11-26)

Left: the recorder job in its own container, share links and a public player, the demo assistant, publishing and archiving, an Entra group for viewers who are not operators, and speech through the governed path.

## Context

Narrated demos of genki are recorded by `scripts/demo.ts` from `demos/*.yaml`, by hand or in the hand-run `demos` workflow, and land as workflow artifacts that only people with GitHub access can find. People who present genki need a library they can play and download from, and the recording should later move into the platform.

## Decision

- **A demo is a versioned configuration entry** of kind `demo` in the platform scope, with the shape of `demos/*.yaml`: `title`, `description`, `audience` (`municipality`, `state-agency`, `internal`), `language`, `voice`, `viewport`, `app` (`portal`, `console`) and `path`, `signedIn`, `ready` and `steps`. `app` plus `path` replaces the absolute `start` URL, so a demo is not tied to one host; a file with `start` is read as the app named by the host's first label and the rest of the URL as the path. Each step's `do` commands must start with one of the recorder's browser commands, the same allowlist as `parseDemo`, and take no flag but `--name`, `--exact`, `--text`, `--timeout`, `--load` and `--url`; the recorder checks both again before it runs a stored step.
- **A recording is a configuration entry** of kind `demo-recording`, a new version at each change: `demo`, `demoVersion`, `genkiVersion`, `status` (`running`, `recorded`, `failed`), `steps`, `narrated`, `voice`, timestamps, `seconds`, `files` and `failure` (`step`, `command`, `message`). Its files are blobs under `demos/recordings/{id}/` in the platform tenant: `demo.mp4`, `demo.srt`, `poster.jpg` and `failed-step-{n}.png`, each with its own size limit.
- **Seeding.** At start the API reads `demos/*.yaml` (shipped in the image through `docker/runtime-assets`) and saves each as a demo by `platform:seed`, a new version only when the file changed. A demo last saved by someone else is kept.
- **Viewer and editor.** `GET /operator/demos`, `GET /operator/demos/{id}`, `GET /operator/recordings/{id}` and its files need the demo viewer role; `PUT /operator/demos/{id}` (JSON or the YAML of a file, a change reason, optional `if-match`) needs the demo editor role and is audited as `platform.demo.save`. Today an operator holds both roles and nobody else does; the check lives in `mayViewDemos` and `mayEditDemos` in `apps/api/src/demos.ts`.
- **The recorder.** `GET /recorder/recordings?status=queued` (only `id` and `demo` of each queued recording, oldest first), `GET /recorder/recordings/{id}`, `POST /recorder/demos/{id}/recordings`, `PUT /recorder/recordings/{id}/files/{name}` and `POST /recorder/recordings/{id}/finish` take only the key whose SHA-256 hex digest is set in `DEMO_RECORDER_KEY_SHA256`, sent in `x-recorder-key` and compared in constant time. Without the setting every recorder call is refused. The recorder acts as the platform principal `recorder`; starting and finishing a recording are audited as `platform.demo.recording.start` and `platform.demo.recording.finish`. A recording takes files only while it runs, and finishes as recorded only with its video.
- **Recording from the console.** `POST /operator/demos/{id}/recordings` (demo editor, change reason) queues a recording of the stored demo, audited as `platform.demo.recording.start`; `upTo` makes a silent trial of the first steps, kept out of the library's `latest` and `recorded`. A demo has at most one queued or running recording: both this route and the recorder's start answer 409 `recording-open` otherwise, and the recorder never takes up a queued recording it did not name. The library, detail and settings say which recorder takes queued recordings: `job` when a recorder job is wired into the demos module, `scheduled` when the API has `GENAI_DEMO_RECORDER=scheduled` and a valid `DEMO_RECORDER_KEY_SHA256`, so the `demo-recorder` workflow picks them up, and otherwise `workflow`, where the route answers 503 `recorder-not-set-up`. `POST /operator/recordings/{id}/cancel` (demo editor, change reason) ends a queued or running recording as `cancelled`, audited as `platform.demo.recording.finish`; the recorder's next upload then gets 409 and it stops. The recorder takes up a queued recording by naming it in `POST /recorder/demos/{id}/recordings`, and reads the demo version and settings it records with `GET /recorder/recordings/{id}`.
- **Statuses and files.** A recording is `queued`, `running`, `recorded`, `failed` or `cancelled`, with `requestedBy`, `upTo` and `cancelledBy` when they apply. Besides the files above it takes `step-{n}.png` after each step, which is its progress, and `sample.mp3`, a sample of its voice. A failure's `command` is the command as a JSON list.
- **Settings.** `GET` and `PUT /operator/demo-settings` (demo editor, change reason, `if-match`, audited as `platform.demo.save` with target `demo-settings`) hold the default voice, viewport, test organisation, a label for the recording login, the retention in days and the demo writer's daily tokens, as one config entry of kind `demo-settings`; version 0 means the defaults. The settings point at the newest recording with a `sample.mp3` in the default voice. Retention is not enforced until the recorder job runs.
- **Out of date** is a recording made on another genki version than the API runs (`APP_VERSION`); the library returns that version so the console can show it.

## Why

Configuration entries are versioned, audited by `by` and `reason`, stored in Postgres without a migration, and already hold other platform records, such as the state register (ADR 0058). The recorder key is the smallest identity that lets the hand-run workflow fill the library before the recorder container exists, and it reaches only the three recorder routes: it is not an API key, carries no tenant rights and cannot read the library. A separate header keeps it out of the bearer-token path and the lockdown rules for people and API keys.

Rejected: Entra app roles `GenAI.DemoViewer` and `GenAI.DemoEditor` on the console client, because operator login goes through Ansattporten groups (ADR 0035) and no Entra app roles reach the API today; a new table, since the records are few and versioned; and a share link now, which needs its own expiry, revocation and public route.

## Consequences

- The `demos` workflow uploads its results when `DEMO_RECORDER_KEY` and `SMOKE_API_URL` are set in `genki-test`: it starts a recording with the key, uploads a screenshot after each step, `demo.mp4`, `demo.srt`, `poster.jpg`, `sample.mp3` and any `failed-step-{n}.png`, and finishes it.
- Sellers and presenters who are not operators cannot open the library yet. Giving them the viewer role needs a mark from an Entra group in the verifier, as ADR 0035 does for operators.
- The console fetches a whole video into the browser before it plays; range requests and short-lived links come with the public player.
- The `demo-recorder` workflow runs every five minutes on main. Its first step asks `GET /recorder/recordings?status=queued` with the key and ends when the list is empty; otherwise it writes the lines to voice to a one-day artifact, voices them in a job with the review identity and no key, and records each queued recording in turn with `node scripts/demo.ts recording --queued` in `genki-test`. It runs one at a time in its own concurrency group, so a tick never cancels a hand-run `demos` run waiting for its turn. A queued demo that needs a sign-in without `SMOKE_API_KEY` is finished as failed, and a recording the API cannot read is left for the next run. The queue artifact holds the narration of the queued demos and, like the voice clips and videos of the `demos` workflow, can be downloaded by anyone signed in to GitHub for a day, since the repository is public. genki-test sets `GENAI_DEMO_RECORDER=scheduled` and takes `DEMO_RECORDER_KEY_SHA256` from the variable of that name in the `test` environment; prod sets neither. Neither that variable nor the `DEMO_RECORDER_KEY` secret is set yet, so until they are, genki-test answers 503 and the workflow ends at its first step.
- When the recorder runs in its own container, it keeps these routes and moves from the key to a workload identity.

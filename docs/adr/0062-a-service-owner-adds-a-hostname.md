# 0062 A service owner adds a hostname

Status: proposed, 2026-11-19 (partly built, 2026-11-19: hostnames from the parameter file; self-service claims and an assigned address at publish, issue #999, 2026-11-25: API, storage, DNS check, portal, and the binder job with its Azure fence)

Left: wildcard hostnames; hostnames on the API, portal, workspace and console, which stay in `hostnames` in `infra/main.bicep`; certificates the owner brings; and Front Door. Each needs its own change.

## Update, 2026-11-19

A maintainer adds a hostname now, through the environment's parameter file and a pull request (`hostedHostnames`, below). A name in genki's own zone, `<subdomain>.apps.<zone>`, is the default: genki assigns it and writes its DNS records, and no owner claims a name in genki's zone. A custom domain the service owns is the option. Kunnskapsassistenten first gets `kunnskap.apps.genki-test.digdir.cloud`, then moves `qa.kunnskap.digdir.cloud` this way. The self-service flow this record first proposed (a claims API, a DNS challenge token, a binder job, a custom role and an Azure Policy fence) is built since 2026-11-25 under "Self-service claims" below. The host's own environment and identity hold for both.

## Update, 2026-11-25

Issue #999: a service made in the portal gets an address its users can open, with no pull request and no deploy. This builds "Self-service claims" below, with two adjustments.

- **genki assigns a name in its own zone at the first publish.** When a service whose production version has an assistant interface (`spec.interface.layout`) is published and has never had an assigned name, the platform creates a hosted Client for it if it has none (`<service>-host`, `spec.hosted: true`, no `oidc`, so it logs in through the platform login, ADR 0061) and claims `<label>.apps.<zone>` for it, where `<label>` is the service id as one DNS label. A label in `defaultReservedLabels` (`login`, `assistant`, `kunnskap`, `api`, `portal`, `console`, `workspace`, `www`, `auth`, `bff`, `admin`, `apps`, `status`, `docs`, `mail`) or the label of an `apps.` name in `GENAI_HOSTED_HOSTNAMES` is never taken; a name another claim holds gives `<label>-2` and so on. The portal asks for the same with `POST /tenants/{tenant}/services/{service}/address` for a service published before, or after its owner removed the first one. This name needs no DNS proof, since genki owns the zone: the claim starts in `binding`, and the binder writes its CNAME and `asuid` TXT records in the zone `apps.<zone>` (`zone` and `recordName` in the binder's work). There is still no wildcard: each name has its own managed certificate. Owners still cannot claim a name under genki's zones or under `GENAI_DNS_ZONE`; only the platform assigns one. `GENAI_DNS_ZONE` names the zone; without it nothing is assigned.
- **In lockdown, a new hosted Client needs an operator** (ADR 0033): the automatic address creates one only when an operator publishes, and the portal's request from anyone else is refused. A platform operator holding every right in the platform's own organisation counts as an operator there, here as on every route (ADR 0072). A service that already has a hosted Client gets its name either way.

`hostedHostnames` keeps working as it is: its names reach the API as `GENAI_HOSTED_HOSTNAMES`, are opened to their organisation, are never claimable, and their `apps.` labels are never assigned. A name is opened either by the parameter file or by an `active` claim; the parameter file wins where both exist. Claims supersede the parameter file: once Kunnskapsassistenten's names are claims, their entries go, and `hostedHostnames` with them.

## Context

genki's custom domains are four fixed hostnames, one per app, in the `hostnames` parameter of `infra/main.bicep`, bound in three stages by `customDomainsStage` (`none`, `hostnames`, `certificates`) in `infra/modules/containerapps.bicep`. Adding one means a pull request to a param file and an infrastructure deploy by a maintainer. A hosted assistant (ADR 0061) needs a hostname per service and environment, chosen by the service owner, on a domain the owner controls.

Azure Container Apps binds a custom domain to an app in `properties.configuration.ingress.customDomains` and issues a free managed certificate (`Microsoft.App/managedEnvironments/managedCertificates`) once DNS points at the app: a CNAME to the app's FQDN and a TXT record `asuid.<host>` with the app's `customDomainVerificationId` for a subdomain, an A record to the environment's static IP for an apex name. Changing ingress is an application-scope change and makes no new revision. The verification id is the same for every hostname on the app, so it proves that DNS points at genki, not which tenant asked.

Azure has no action for binding a domain alone. Binding needs `Microsoft.App/containerApps/write`, which also changes the app's image, environment variables, secrets and identities, and managed certificates are written with `Microsoft.App/managedEnvironments/managedCertificates/write` on the whole environment. Azure Policy can deny a write by the values it sets, through aliases, but cannot compare a new value with the old one.

genki's apps share one identity today. The web apps carry it (`infra/modules/containerapps.bicep:471-474`), it reads every secret in Key Vault (`infra/main.bicep:239`, Key Vault Secrets User in `infra/modules/keyvault.bicep:25-33`), it is the Postgres login (`containerapps.bicep:157`), the worker carries it (`containerapps.bicep:264-266`), and the managed certificates live in the same environment as the API (`containerapps.bicep:114`). Any identity that can write a container app holding that identity can reach all of it.

## Decision

### The host stands apart

- **The assistant host runs in its own Container Apps environment,** `${baseName}-hosted-env`, with its own managed certificates. genki's API, worker and apps, and their certificates, stay in the existing environment.
- **The host has its own identity,** `${baseName}-assistant-id`. It may pull images from genki's registry and read one secret, `GENAI_PROXY_KEY`, from a Key Vault of its own, `${baseName}-hostkv`, which holds nothing else. It has no role on genki's Key Vault, no Postgres login and no other Azure role. The host reaches the API over HTTPS on the API's public hostname.

### Now: a maintainer adds a hostname through the parameter file

- **One entry adds a hostname end to end.** `hostedHostnames` in `infra/env/<env>.bicepparam` takes `{ subdomain or hostname, tenant, stage, apex? }`, added by pull request and reviewed by a maintainer. The review is where it is checked that the organisation asking owns the service and, for a custom domain, controls the domain.
- **A subdomain is the default.** `subdomain` is one lowercase DNS label and becomes `<subdomain>.apps.<dnsZoneName>` (`genki-test.digdir.cloud` in test, `genki.digdir.cloud` in prod). The template writes its CNAME to the host app's FQDN and its `asuid` TXT record in genki's own Azure DNS zone, as it does for the four app hostnames, or in the delegated zone `apps.<zone>` while the binder is on. Each name has its own managed certificate; there is no wildcard. The `apps.` level holds these names alone: no app hostname and no custom domain may be put there, and the API accepts exactly one label under `apps.` in genki's zones and nothing else in them.
- **The API opens the hostname to that organisation.** Every entry reaches the API as `GENAI_HOSTED_HOSTNAMES` (`host=tenant,host=tenant`). Only a hosted Client of that tenant may name it in `spec.hostnames`, with the environment it draws (ADR 0064), and `GET /v1/hosts/{hostname}` answers only for a hostname that is both opened and named; every other hostname gets the same `404` (`urn:genai:problem:host-not-found`). Any other name under genki's own zones (`genki-test.digdir.cloud`, `genki.digdir.cloud`, `azurecontainerapps.io` and every zone in `GENAI_RESERVED_DOMAINS`) is never opened (`isAssignedName` in `apps/api/src/hosts.ts`).
- **The assistant host binds it in stages,** per hostname, as `CUSTOM_DOMAINS_STAGE` does for the four app hostnames, since Azure issues a managed certificate only for a hostname already on the app: `none` opens it in the API only, `hostnames` adds it to `${baseName}-assistant` with binding `Disabled`, and `certificates` creates a managed certificate in `${baseName}-hosted-env` and binds it `SniEnabled`. Each step is a pull request and a deploy. Nothing binds while `assistantHostEnabled` is off.
- **For a custom domain, the owner creates the DNS records,** in their own zone: a CNAME from the hostname to the host app's FQDN and `TXT asuid.<hostname>` with the host environment's verification id. The deploy's output `assistantHost.dnsRecords` lists them per hostname. genki writes no record in the owner's zone.
- **An apex name works without a CNAME.** With `apex: true` the record is an A record to the static IP of the host's environment (not genki's existing one), and the certificate is validated over HTTP, which Container Apps documents for apex domains.
- **Removing** the entry unbinds the hostname and closes it in the API at the next deploy; its certificate is deleted by hand. While the domains are passed through (`keepBoundDomains`, on with the binder), a removed entry stays bound until it is removed by hand (`docs/runbook.md`, "Hostname binder"); setting its stage to `none` still unbinds it. **Rolling back** a moved domain is pointing its record back where it was and removing the entry.
- **No identity writes Azure at run time.** Only the deploy binds hostnames, as it binds the rest of the template. The exception is the binder, while `hostnameBinderEnabled` is on (test), which writes the host app, its certificates and the `apps.` zone.
- A test holds every entry in both parameter files to the API's rules: a subdomain that is one valid label or a lowercase hostname outside genki's zones, a nine-digit organisation number, a known stage and no name twice, and keeps the four app hostnames off `apps.` (`scripts/hosted-hostnames-infra.test.ts`). Moving a team's existing domain is in `docs/runbook.md`.

### Self-service claims

Built in the API, the database, the worker and the portal (issue #999), and the binder job with its identity, role, policies and alerts (behind `hostnameBinderEnabled`, on in test). It replaces the parameter file for hosted hostnames: each entry becomes a claim, and `hostedHostnames` is removed once none is left.

#### Claiming a hostname

- **A hostname belongs to a hosted Client.** `POST /tenants/{tenant}/clients/{client}/hostnames` with `{ hostname, environment, reason }` claims one for a hosted Client (ADR 0061). It needs `manage-services` and goes through the admin action `platform.client.hostnames.add` (ADR 0010). The reason comes in `change-reason` or the body. A claimed hostname is not written into the Client's `spec.hostnames`, which keeps only names from the parameter file: the claim itself opens the name while it is `active`, and the API admits a signed-in page from `https://<hostname>` to that Client's channels for as long (`claimedOrigin` in `apps/api/src/composition.ts`). A hosted Client may so have no hostname of its own. Taking hosting off a Client, or removing it, removes its claims.
- **Some names can never be claimed.** A name under genki's own zones (`genki-test.digdir.cloud`, `genki.digdir.cloud` and every zone in `GENAI_RESERVED_DOMAINS`), under `azurecontainerapps.io`, a name in `GENAI_HOSTED_HOSTNAMES`, an IP address, a wildcard, and a name longer than 253 characters are refused with `400 hostname_not_allowed` (`claimRefusal` in `apps/api/src/hostname-claims.ts`).
- **A hostname may redirect.** A claim with `{ hostname, redirectTo, reason }` names another hostname of the same Client instead of an environment. Once both are `active`, `GET /v1/hosts/{hostname}` answers `{ hostname, redirectTo }`, and the host sends the browser on to the same path on `redirectTo` with `location.replace`; it starts no login there and registers no redirect URI for it. A `308` from the host's web server would need it to ask the API for every request, and is left.
- **The owner proves control of the domain with a token only they get.** A claim answers a random token and three records to create: `_genki-challenge.<hostname>` TXT with the token, `asuid.<hostname>` TXT with the host app's verification id, and a CNAME from the hostname to the host app's FQDN (an A record to the static IP for an apex name). The token is per claim, so knowing genki's verification id is not enough.
- **An apex name works without a CNAME.** DNS allows no CNAME at a zone apex, so for a name such as `kunnskap.digdir.cloud` the records are an A record to the static IP of the host's environment, `asuid` and `_genki-challenge` TXT records at the apex itself, and the managed certificate uses HTTP validation, which Container Apps documents for apex domains. The static IP is the host environment's, not genki's existing one, and the portal shows it with the records.
- **The first verified claim owns the hostname.** Claims in `pending-dns` do not block each other: several tenants may claim the same name, and the answer is the same whether or not someone else has. A unique index on the hostname (stored lowercased) covers exactly the states `binding`, `active` and `removing`, so the first claim whose challenge verifies takes it. Every other claim on that name ends `failed` with `not_verified`, the same result as records that never appear, so the claim itself does not say who holds a name; the name's public host answer still names the service it draws. A later claim can take over only once the holder is `lapsed` or removed.

#### Binding it

- **DNS is checked by genki, Azure is written by a job of its own.** The worker checks the three records through a resolver that asks the authoritative name servers, and moves a verified claim to `binding`. It has no Azure right.
- **The binder is a Container Apps Job,** `${baseName}-hostname-binder`, in the host's environment, with one identity, `${baseName}-binder-id`, and nothing else attached. It runs every minute, one replica per run (parallelism 1). A run stops taking new work after 45 seconds, every request to Azure or the API times out after 15, and Azure stops the run after 55, so runs do not overlap in practice; nothing in Azure forbids two at once, and one that loses a write to another tries it again the next minute. It asks the API for the claims in `binding` and `removing` (`GET /internal/hostnames/work`, Entra token for the binder's identity, refused for any other principal), applies them, and reports each result (`POST /internal/hostnames/{id}/result`). It holds no database login, no Key Vault right and no genki secret. It runs `scripts/hostname-binder.ts` in the worker image, so it adds no image to the pipeline, and calls Azure Resource Manager and the managed identity endpoint over plain REST.
- **The contract.** `GET /internal/hostnames/work` answers `{ items: [{ id, hostname, apex, action: 'bind' | 'remove', step: 'add' | 'certificate' | 'enable' | 'unbind' | 'done', zone?, recordName? }] }`; `zone` and `recordName` come only for a name genki assigns, `<label>.apps.<zone>`. `POST /internal/hostnames/{id}/result` takes `{ step, ok, message?, certificateId? }`. A result for another step than the claim's is `409 step_mismatch`. The binder reports a step once it is done or has failed, and nothing while it waits (a certificate being issued, the host app busy with another change), so the API sees no result for a run that only waited.
- **The binder's token.** It asks the managed identity endpoint for a token for the audience in its `HOSTNAME_BINDER_AUDIENCE`, `api://<client id>` of an Entra app registration made for the API, since the API has no Entra audience of its own (`API_AUDIENCE` is Ansattporten's). The API accepts it (`apps/api/src/binder-token.ts`) only RS256, signed by a key of the Entra tenant `GENAI_HOSTNAME_BINDER_TENANT_ID`, with that tenant's v1 or v2 issuer, audience `GENAI_HOSTNAME_BINDER_AUDIENCE`, as an application token (no `scp`), and with `oid` equal to `GENAI_HOSTNAME_BINDER_PRINCIPAL_ID`, compared in constant time; every other caller, and every call while these are unset, gets the same `404`. The template sets the three on the API while the binder is on (the principal from the binder's identity, the audience from `hostnameBinderAudience`, the tenant from the deployment's), with `GENAI_DNS_ZONE`, the zone under whose `apps.` the API assigns names, and leaves them empty otherwise. It also gives the API and the worker the host app's FQDN, the host environment's verification id and static IP (`GENAI_ASSISTANT_HOST_FQDN`, `GENAI_ASSISTANT_HOST_VERIFICATION_ID`, `GENAI_ASSISTANT_HOST_STATIC_IP`), and the API `GENAI_HOSTNAME_LIMIT` when `hostnameLimit` is set. The job is deployed only once `hostnameBinderAudience` is set.
- **What the binder tells the API.** A failed step reports the binder's own refusal, or only Azure's status and error code (`Azure answered 409 Conflict`); the resource path and Azure's full message stay in the job's log, so a tenant who sees the claim's message learns nothing of genki's subscription.
- **The binder's role has only the actions binding needs,** a custom role `genki hostname binder (<baseName>)`, assignable only in the environment's resource group: `Microsoft.App/containerApps/read`, `Microsoft.App/containerApps/write`, `Microsoft.App/containerApps/listCustomHostNameAnalysis/action`, `Microsoft.App/managedEnvironments/read`, `Microsoft.App/managedEnvironments/join/action`, `Microsoft.App/managedEnvironments/managedCertificates/read`, `Microsoft.App/managedEnvironments/managedCertificates/write`, `Microsoft.App/managedEnvironments/managedCertificates/delete`, `Microsoft.ManagedIdentity/userAssignedIdentities/assign/action`, `Microsoft.Network/dnsZones/CNAME/read`, `Microsoft.Network/dnsZones/CNAME/write`, `Microsoft.Network/dnsZones/CNAME/delete`, `Microsoft.Network/dnsZones/TXT/read`, `Microsoft.Network/dnsZones/TXT/write` and `Microsoft.Network/dnsZones/TXT/delete`. The binder does not call `listCustomHostNameAnalysis` yet; it stays from the first list as read-only analysis. It is assigned on four resources only: the host app, the host's environment, the host's identity (Azure checks `assign/action` on every identity a written app carries, even one it already has) and the zone `apps.<zone>`. Besides it the binder has AcrPull on genki's registry, to pull the worker image. Nothing in genki's own environment, Key Vault or Postgres.
- **Names genki assigns live in a zone of their own.** While the binder is on, `<label>.apps.<zone>` and its `asuid` record are in the zone `apps.<zone>`, delegated from genki's zone with an NS record, and the template writes the names it binds there too. Azure cannot scope a role to record sets that do not exist yet, so the zone is the narrowest scope that lets the binder write new names, and it keeps the binder away from `api`, `portal` and the other records in genki's zone.
- **Azure Policy fences the rest of the write.** A custom policy with effect `Deny` (`policyEffect`, `Audit` to try it first), assigned on the resource group and matching the host app by name, refuses any write that sets: an image outside genki's registry and the `genai-apps` repository, or not pinned by digest; a container other than the one `assistant`, a command or arguments; an environment variable other than `APP` (only `assistant`), `API_UPSTREAM` and `ANSATTPORTEN_ISSUER` (only the values the host app had when an owner last applied `infra/hostname-binder-access.bicep`, so a deploy that changes either needs the re-apply step in `docs/runbook.md`, "Hostname binder") and `GENAI_PROXY_KEY` (only from the secret `genai-proxy-key`); a secret other than `genai-proxy-key` from `${baseName}-hostkv` through the host's identity; a secret reference on any variable but `GENAI_PROXY_KEY`; a registry or registry identity other than genki's and the host's; a system-assigned identity; Dapr; `allowInsecure`; internal ingress or a target port other than 8080; or any init container, volume, volume mount, service bind or scale rule. Azure Policy has no alias for the keys of `userAssignedIdentities`; another identity is kept off by RBAC instead, since attaching one takes `assign/action` on it. A second policy on the `apps.` zone refuses a CNAME that does not point at the host app, a name of more than one label, a TXT record that is not `asuid.*` or holds anything but the host's verification id, and any other record type than the zone's own NS and SOA. The deploy writes within the same fences.
- **Two Activity Log alerts** go to the maintainers' action group: every write the binder's identity makes in the resource group, mailed only where `alertMailMaxSeverity` is 2 or more (not in test), and every write Azure Policy refuses there. An Activity Log alert cannot match "not by the deploy identity" or "more than `customDomains`", so the first rule is every binder write instead, and the second catches a write that crossed a fence. With the policies in `Audit`, nothing is refused and the second stays silent.
- **Each step is idempotent.** The binder adds the hostname with binding `Disabled`, creates a managed certificate with CNAME validation (HTTP for an apex name), and switches the binding to `SniEnabled`. It reads the app's `customDomains` and writes them back with a JSON Merge Patch that carries nothing else, so a deploy that lands between its read and its write keeps its image and settings; one run at a time. A step that finds its work done reports it done again without a write; for a name genki assigns it reads the two records first and writes them only when they differ. A certificate that ends `Failed` is deleted, so the next run asks again. Azure's 429 and 5xx answers are retried within a run, and a failed step is tried again the next minute; the API handles a failure that lasts 48 hours as below. For a name genki assigns, each bind step first writes its CNAME to the host app and its `asuid` TXT record with the host environment's verification id; the binder takes the zone from its own setting and refuses an item whose `zone` differs, whose `recordName` is not one label under `apps.` or does not match the hostname, or whose hostname is one the template binds. `add` leads to `certificate`, `certificate` to `enable`, and `enable` to `active`; `unbind` ends a removal as `removed`. A binding the binder reports failing for 48 hours from the claim entering `binding` ends `failed` with `bind_failed: <step>`; when it got past `add`, it is first unbound, through `removing`, so a name is never left bound with no claim. The binder's `message` keeps the status and code of Azure's answer for operators; the tenant's view leaves it out. A removal keeps the name held and is retried until the unbind succeeds, so a name is never free while it is still bound. Removing a `lapsed` claim unbinds it too, unless another claim holds the name by then. The internal routes skip the lockdown gate and the change-reason rule, since they check the binder's token themselves; any other caller, signed in or not, gets `404`. A claim the binder never reports on stays in `binding`.
- **States:** `pending-dns`, `binding`, `active`, `failed`, `lapsed`, `removing`. `GET /tenants/{tenant}/clients/{client}/hostnames` shows the tenant's own claims with their records and when they were last checked. The portal shows the same, with the records to copy.
- **Only `active` hostnames are served.** `GET /v1/hosts/{hostname}` answers 404 for every other state, so the host draws nothing and starts no login on a hostname that is not verified.
- **The database is the truth, Azure follows.** On each run the binder also compares the app's `customDomains` with the `active` and `binding` hostnames, adds what is missing and removes what no claim holds, and reports each change. Not built: the work list names only claims with a step left, so the binder cannot tell a domain no claim holds from one the template binds. It needs the API to list the hostnames held as well.
- **The infrastructure deploy keeps them.** The host's module reads the app's current `customDomains` through an `existing` reference and passes them through, so a deploy does not drop them before the binder runs again. A name in `hostedHostnames` is the template's, at every stage; a name removed from `hostedHostnames` while the binder is on stays bound until it is removed by hand (`docs/runbook.md`, "Hostname binder"). A domain the binder adds between a deploy's read and its write is dropped by that deploy, and comes back at the binder's next step for it; an `active` name dropped that way waits for the comparison above. The other way round, a deploy that reads the app before the binder unbinds a name and writes after it binds the name again, with a certificate the binder has deleted by then; the claim is gone, so nothing unbinds it, and it is removed by hand (`docs/runbook.md`, "Removing a hostname"). The binder writes nothing while the host app is still provisioning, but a deploy that writes the host app while the binder's change is provisioning can fail on Azure's conflict, and is safe to run again. The pass-through follows `keepBoundDomains`, which follows `hostnameBinderEnabled` unless set: turning the binder off with it unbinds every name the binder bound at the next deploy, so it stays `true` until those names are gone. It reads the host app, so a new environment's first deploy runs with the binder off.

#### Keeping it, and taking it away

- **genki checks each active hostname once a day.** The worker checks `pending-dns` claims every 5 minutes and active ones once a day, through `authoritativeDns` in `apps/worker/src/hostname-dns.ts`, which finds the zone's name servers and asks them directly. When `_genki-challenge` or the record the claim asked for (the CNAME, or the A record for an apex name) has been gone for 7 days in a row, the hostname is `lapsed`: it is no longer served, and the audit log and the portal say so. After 30 days lapsed it goes to `removing` and the binder unbinds it, or straight to `removed` when another claim holds the name by then. This keeps a hostname whose domain has changed hands from drawing a service. A name genki assigned is never checked.
- **Removing** (`DELETE .../hostnames/{hostname}` with a reason, action `platform.client.hostnames.remove`) stops sessions on it at once, since the API reads the hostname's state for every session request (ADR 0061); the binder then unbinds it and deletes its certificate. Removing the Client, taking hosting off it, or removing the service environment a claim draws removes those hostnames. A service whose platform-made Client is still there cannot be deleted; the refusal names that Client by id.
- **Rolling back** is removing the hostname in genki and pointing the CNAME back where it was. genki has no other state for it.
- **Every step is in the audit log:** the claim and removal (`platform.client.hostnames.add`, `.remove`) and the assigned address (`platform.service.address`) as admin actions; each change of the binder's step or state (`platform.client.hostnames.bind`, actor `platform:hostname-binder`); and verification, expiry, lapse and removal by the worker (`platform.client.hostnames.verify`, `.expire`, `.lapse`, `.remove`, actor `platform:hostname-dns`). A retry that changes nothing is not logged again; the claim keeps the last records seen (`check`).

#### Limits

- At most 4 hostnames per Client, 20 per tenant and 200 for the host app, and at most 5 claims per tenant waiting for DNS (`400 hostname_limit`). The platform limit is under `GENAI_HOSTNAME_LIMIT` and is lowered if Azure's own limit turns out lower.
- A claim not verified in 7 days expires.
- Managed certificates are free. The host is one container app and one environment whatever the number of hostnames.

#### What a stolen binder can do

If the binder's identity is taken, the attacker can, within the policy: bind or unbind hostnames on the host app, create or delete certificates in the host's environment, and roll the host to another genki image by digest. That can take hosted assistants offline, or serve them on a hostname the attacker controls, where the BFF still refuses a session on a hostname that is not `active` for its Client.

In `apps.<zone>` it can create or delete names, but each must point at the host app and carry the host's verification id, so a stolen binder can take a genki-assigned name offline, including `login.apps`, or point a new one at the host, which the API answers 404 for until a claim is `active`. It cannot point a name at a server of its own.

It cannot: run code of its own on the host, read genki's Key Vault, reach Postgres, change the API, worker, portal, workspace or console, touch their certificates, or write any record in genki's zone outside `apps.`. The one secret within reach is `GENAI_PROXY_KEY`, and only by mounting it into a genki image, which does not print it. Rotating the proxy key and the binder's identity is the response, and the alert says when. Within the fences it can also change what they leave open: the host's probes, its replicas and resources, its ingress transport, IP restrictions and CORS, which can take the host offline or raise its cost but reach no secret. A name it bound survives every deploy, since the deploy passes the host's domains through, so the response also removes those names by hand. The fences rest on Azure Policy evaluating these writes: until an owner assigns the policies, or while they are in `Audit`, the binder's role alone lets it change anything on the host app, run code there as the host's identity and read `GENAI_PROXY_KEY`, and in `apps.` point a name anywhere.

## Why

A maintainer's pull request is enough while a handful of services have hostnames, and it gives what self-service would lose:

- **Review by a person before a name goes live.** The reviewer checks that the asker controls the domain.
- **One source of truth for Azure state.** The host app's domains are in the template, so a deploy never drops them (while the binder is off).
- **No write right to Azure at run time.** No identity outside the deploy can change the host app (while the binder is off).

It costs a pull request and up to three deploys per hostname, and a maintainer's time. Self-service later gives a service owner a hostname in minutes without asking a maintainer and with no deploy, with the checks kept as rules the API enforces and as the audit log. Because Azure has no narrower right than writing the whole app, its boundary is drawn around the app: its own environment, its own identity with almost nothing, and a policy on what any write may set. Its reserved list, first-verified rule and DNS proof cover the abuse we know of: claiming genki's own names, another tenant's names, or a name the claimant does not control.

Rejected:

- **The binder's identity on the worker or the API.** Those carry the shared identity with all of Key Vault and Postgres, so a flaw in either would hand over both the data and the host.
- **The host in genki's own environment, with the shared identity.** A write to it could attach the shared identity or a Key Vault reference and read every platform secret, and certificate rights there would cover the API's.
- **A custom role with a binding action only.** Azure has none: the compute permissions list no action for custom domains apart from `listCustomHostNameAnalysis`.
- **The API calls Azure in the request.** Certificate issuance takes minutes and fails often while DNS propagates; the request would time out and a retry would race with itself.
- **`asuid` alone as proof.** The verification id is the app's, not the claim's, so any tenant could point its claim at a name someone else has pointed at genki.
- **Uniqueness from the first claim.** It would let any tenant block a name it does not control, and its 409 would tell it who holds which names.
- **Front Door.** It removes the Bicep pass-through and per-app limits, but costs a base fee per profile and every request, and ADR 0061 decided against it for now. It stays the way out if hostnames outgrow one app.

## Consequences

- Kunnskapsassistenten's `qa.kunnskap.digdir.cloud` is added through the parameter file. The DNS zone stays where it is until the old resource group is retired. Later hostnames per environment, `test.kunnskap.digdir.cloud` for `test` and the apex `kunnskap.digdir.cloud` for `prod` with `qa` redirecting to it (ADR 0064), are entries of the same kind; the redirect needs the self-service flow or a host rule of its own.

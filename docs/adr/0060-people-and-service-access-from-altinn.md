# 0060 People and service access from Altinn

Status: proposed, 2026-11-18 (built against the local fakes; not yet run against Altinn tt02 or production)

## Context

ADR 0027 gets a person's own rights from the Altinn PDP at login. The portal's Tilgang page also needs the other side: who in the organisation holds which of the five rights, and a way to let only some of them use a given service. Altinn holds the rights; genki must not become a second place where they are granted.

## Decision

- **Who has which right comes from Altinn access management.** `httpAltinnPeople` in `packages/identity/src/altinn-people.ts` reads the organisation's party from `GET /accessmanagement/api/v1/enduser/authorizedparties`, lists the persons it has given access to with `GET .../enduser/connections?party={org}&from={org}`, and asks `GET .../enduser/connections/resources/rights` for each person's direct and indirect rights on the platform resource. The actions map to the five rights as in ADR 0027. People with none of the five are left out.
- **The API reads as the organisation's system user.** The token is a Maskinporten grant with `authorization_details` of type `urn:altinn:systemuser` for the organisation (`0192:{orgno}`), exchanged for an Altinn token. Each organisation must create a system user for genki and give it access management rights in Altinn. Settings: `ALTINN_PEOPLE_URL`, `ACCESS_PERSON_KEY_SECRET`, `ALTINN_PEOPLE_MASKINPORTEN_CLIENT_ID` and `ALTINN_PEOPLE_MASKINPORTEN_KEY` (fall back to the PDP client), `ALTINN_PEOPLE_MASKINPORTEN_SCOPE` (default `altinn:accessmanagement/enduser:connections:toothers.read`), plus `ALTINN_SUBSCRIPTION_KEY` and `MASKINPORTEN_ISSUER`. Without `ALTINN_PEOPLE_URL`, dev mode reads the local test data through `peopleFromTestData`, and any other mode answers 503 `altinn_not_configured`. The API refuses to start when `ALTINN_PEOPLE_URL` is set and a setting is missing, or the URL is not HTTPS.
- **A person is a keyed hash, never a national identity number.** `personKeys(ACCESS_PERSON_KEY_SECRET)` turns the identity number into a 22-character HMAC-SHA256 id. The identity number stays inside the identity package; the portal, the stores and the audit log see only the id and the name.
- **The list is kept two minutes per organisation, and the last good list is served when Altinn fails**, marked `stale` with the time it was read. With no earlier list the API answers 503 `altinn_unavailable`. Reads are not audited and not logged.
- **Per-service access is a genki limit on top of Altinn.** `PUT /tenants/{tenant}/access/services/{service}` with `mode: selected` and person ids limits a service to those people; `mode: all` removes the limit. It needs Administrere tjenester and a change reason, goes through the admin action `platform.service.access`, and is stored as config entries of kind `service-access` per tenant and service, so the audit log holds who changed it, when and why. One person decides; there is no second approval. Only people in the organisation's current list, or already on the limit, can be chosen; a stale list counts for 24 hours. The audit entry's before and after hold person ids, not names.
- **The limit applies to people only.** `serviceAccessPolicy` in `packages/identity/src/service-access.ts` wraps the invoke decision: an employee principal invoking a limited service of its own tenant must have a person id on the list, resolved through the remembered identity number. API keys, Maskinporten clients and operators pass to the inner policy unchanged. A service with no limit is never affected, whatever state Altinn is in. On a limited service, a login with no known person, or a list that cannot be read, is refused. A chosen person still needs Bruke tjenester from Altinn. An Entra login has no identity number, so it cannot use a limited service. A shared service is limited only for people of the tenant that owns it, not for other organisations' people. A draft run of a stored service, such as the playground or an eval, is limited like the service unless the person holds Administrere tjenester.

## Why

Reading rights from Altinn keeps one source of truth and lets the organisation's access manager keep using Altinn. The system user path is what Altinn offers vendors for reading an organisation's connections; reading with the signed-in person's own token would need new Altinn scopes in the login and an access manager to be the one looking. A keyed hash lets the policy match a login to a list entry without storing or showing identity numbers. Limiting services inside genki rather than as Altinn rights per service avoids one Altinn resource per service.

## Consequences

- New: `GET /tenants/{tenant}/access/people`, `GET /tenants/{tenant}/access/services` and `PUT /tenants/{tenant}/access/services/{service}`, in `apps/api/src/access-people.ts`, with tests in `apps/api/src/access-people.test.ts`, `packages/identity/src/altinn-people.test.ts` and `packages/identity/src/service-access.test.ts`.
- `createMockAltinnAccessManagement` serves the three Altinn reads from the local test data, and the HTTP client is tested against it.
- `apps/api/src/main.ts` mounts the module and wraps the invoke policy with `serviceAccessPolicy`. Without `ALTINN_PEOPLE_URL` outside dev mode the people list answers `altinn_not_configured`, and the invoke check still applies to limited services.
- To confirm with the Altinn team before this is accepted: that the end-user connections API accepts a system user token for these reads, the exact scope, and which access package the system user needs.
- A limit controls who can use the service, not who can read or copy its setup. Any member can read a service's definition, and a member who can open the playground (Administrere tjenester or Administrere datasett) can run a copy under another id, which the limit does not cover. This is accepted; the Tilgang page says so where a limit is chosen.
- Changing `ACCESS_PERSON_KEY_SECRET` makes every stored limit point at unknown ids; rotating it needs a migration of the `service-access` entries.

# 0072 Operators own the platform

Status: proposed, 2026-11-25 (built). Supersedes the support sessions of ADR 0010, ADR 0027 and ADR 0035.

Left: the operator routes under `/operator/*` that span tenants keep their current rules; this record does not reclassify them (see Consequences).

## Context

ADR 0010 let an operator act in an organisation only inside a support session with a reason and a time limit, and ADR 0006 put the limits Digdir sets behind such a session. In practice operators are the platform's owners (ADR 0035): they set quotas, models, flags and settings for every organisation, and a session per change added ceremony without protecting anything that needed it. What needs protecting is the organisation's content, because it can hold personal data.

## Decision

- **Operators change configuration directly.** An operator acts in any organisation on the tenant routes (`/tenants/{tenant}/...`) with every platform right and no session. This covers configuration, metadata and limits: the `operatorOnly` settings (`usage.monthlyTokens`, `usage.tenantCallsPerMinute`, `assistant.dailyTokens`, `batch.approvalLimitNok`) and budgets, allowed models, feature flags, settings, keys' metadata, service definitions and hostname claims. `tenantAccess` in `apps/api/src/access.ts` makes the operator `{ ...operator, tenant, actor: operator }`.
- **Every operator change has a reason and shows in the organisation's log.** Every write needs the `change-reason` header (`requireChangeReason`, unchanged). The audit entry names the operator as actor with the organisation as `onBehalfOf`, and the organisation's own audit (`GET /tenants/{tenant}/audit`) shows it. A quota request's decision does not change the quota; the operator sets `usage.monthlyTokens` separately, with a change reason.
- **Content needs a reason once a day.** A route in `contentRoutes` (`apps/api/src/content-reason.ts`) answers an operator `403` `urn:genai:problem:content-reason-required`, with the organisation in `tenant`, until the operator gives a reason with `POST /operator/tenants/{tenant}/content-reason` and `{ "reason": "..." }` (at least 10 characters). The reason holds for that operator and that organisation until the Europe/Oslo day ends, then the API asks again. Giving it is the audited admin action `platform.content.reason`. There is no start, end, time limit beyond the day, or banner.
- **Every content read is audited with the day's reason.** The middleware `requireContentReason` appends `platform.content.read` to the organisation's audit for each content request, with the operator as actor, the reason, and the route pattern (`content:<METHOD> <route>`) as target. The portal's log shows it as «Digdir så innhold» with the reason.
- **An operator is never one of the organisation's people.** The operator stays kind `operator`, without `authorizedFor` for the organisation, so Altinn rights stay the organisation's. People, keys and clients of the organisation keep exactly their rights (ADR 0027), and only operators set the `operatorOnly` limits (ADR 0006). An operator whose login carries Altinn rights for an organisation, which in lockdown includes every right in `PLATFORM_TENANT` (ADR 0033), acts there as an employee with those rights and needs no content reason, as before.
- **Support sessions are removed.** `POST /support-sessions`, `GET /operator/support-sessions` and `POST /operator/support-sessions/{id}/end|extend`, the `support-session` header and the actions `platform.support.open|end|extend` are gone. The table `support_sessions` now holds the daily content reasons (one row per reason, `expires_at` at the end of the Oslo day), with the same row-level security and change feed.

## Why

Operators already decide models, prices, quotas and the catalogue for everyone; a session to change one organisation's quota protected nothing and made routine work slow. Personal data is what the law and the organisations care about, so the extra step sits there. A daily reason per organisation keeps the trail (who looked, why, at what) without a session to open, extend and forget to end. A list of content routes with a test that forces every new route into one of two lists keeps the gate from silently missing a route.

Rejected: keeping sessions only for content (the time limit and the banner add ceremony, not protection, once every read is audited with a reason); a reason per request (it would be typed as noise); a second person approving content access (ADR-level controls stay proportionate: one person and an audit trail).

## Consequences

- To check with Digdir's personvernombud before production: that a reason once per operator, organisation and day, with every read audited and shown in the organisation's log, is enough for reading content that can hold personal data.
- New tenant routes must be added to `contentRoutes` or to the metadata list in `apps/api/src/content-reason.test.ts`. A skill's definition holds its test cases, so `definitions/skills/{id}` and its versions, on the tenant routes and on `/operator/tenants/{tenant}/definitions`, are content (`skillDefinitionRoutes`); other kinds stay metadata. `GET /tenants/{tenant}/export` is content. Routes outside `/tenants/{tenant}` that reach one organisation's content call `contentGate`, as `POST /testcase-candidates/{id}/review` does. The `/v1`, MCP and A2A adapters get the kernel through `contentGatedKernel`, which answers an operator's read, events, cancel, resume or annotation of another organisation's run as not found until the day's reason is given, and records the read; an operator's own runs and the platform's own readers are not gated. `/eval-runs/{id}`, `/eval-runs/compare` and `/eval-tasks/{task}` no longer take an operator into a tenant at all.
- The console asks for the reason in a dialog when a content request answers `content-reason-required`, gives it, and repeats the request. Its organisation screen keeps the path `#/support-access` and changes settings and keys directly. A redesign of these screens is left for the console overhaul.
- Tests: `apps/api/src/operator-access.test.ts` ("refuses an operator a skill's definition and the organisation's export until a reason is given, and shows other definitions directly", "lets an operator raise an organisation's monthly tokens without a support session, with a change reason", "shows an operator's change in the organisation's own log", "refuses an operator's content read until a reason is given for that organisation today", "keeps the content reason for the rest of the Oslo day and asks again the next day", "never gives an operator a tenant's own rights outside lockdown") and `apps/api/src/content-reason.test.ts`.
- `/operator/quality/label-queue` leaves out a judge's reason, which can quote an answer, for each organisation the operator has not given today's reason for, and records a read for those it shows. `/operator/quality/sink-labels` is metadata: connection ids, label verdicts, counts and labeller ids, no run text. `/operator/tasks` and `/operator/running-tasks` list ids, status and times, and stay metadata.
- Still to do:
  - Prune the content-reason cache. `support_sessions` keeps every reason and every old support session, and each content request reads all of them; expired rows should be skipped or removed.
  - Refuse only once across instances. A reason given on one API instance reaches the others on the next reload, so the console's one retry can land on an instance that refuses again.
  - Parity gives its reason once per process, so a run that crosses midnight in Oslo is refused after midnight.
- Old audit entries `platform.support.*` stay in the log and keep their labels.

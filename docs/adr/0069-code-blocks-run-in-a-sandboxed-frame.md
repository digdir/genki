# 0069 Code blocks run in a sandboxed frame from a block origin

Status: proposed, 2026-11-21 (built: the block origin, the frame and its CSP, the bridge, the bundle by sha256, and the review before a code block is shared with everyone; not deployed, since no environment has a block origin yet)

Left: a registrable domain for the block origin in Azure, on a site of its own (not under `digdir.cloud`, which genki's zones share), its DNS and route to the API container, and `GENAI_BLOCK_ORIGIN` and the apps' `frame-src` in the Bicep parameters; until then genki-test refuses code blocks. The host's `set-filter` and `open-page` handlers, which the bridge checks and passes on but the hosted assistant does not yet carry out. Unlisting a block shared with everyone (ADR 0067). Each needs its own change.

## Context

ADR 0067 reserved a `code` tier for interface blocks: a built bundle an organisation writes, drawn in a hosted assistant (ADR 0061) beside genki's own blocks. The bundle is code genki did not write, running next to a person's session, answers, sources and threads. ADR 0061 promised the host runs no code from the service owner in its own origin. The host page's CSP is `script-src 'self'`, so a `srcdoc` frame, which inherits it, could run the bundle only by weakening the host.

## Decision

### The block origin

- **A code block runs only in a frame from the block origin**, `GENAI_BLOCK_ORIGIN`, on a site of its own (never under the service or API domains, nor under `digdir.cloud`, the registrable domain genki's zones share). The API process serves it on a second listener, `GENAI_BLOCK_PORT`, as a separate Hono app (`apps/api/src/block-frames.ts`) with none of the API's routes, no auth and no cookies. It answers only `GET` and `HEAD`, only when the `Host` header is the block origin's host, strips any `set-cookie` and never reads a cookie. Locally `npm start` sets `http://localhost:8090`; anywhere else it must be `https`, and never under genki's reserved domains, their parent `digdir.cloud` or a hosted service hostname (`blockOriginFrom` in `apps/api/src/block-origin.ts`, which refuses to start otherwise).
- **Code blocks are off without it.** While `GENAI_BLOCK_ORIGIN` is unset, validate, publish, preview and import refuse `tier: code` at `spec.tier`, and the interface carries no frame address, so a ref block draws the placeholder.
- **Three routes.** `/frame/{publisher}/{id}/{version}/{sha256}` is a fixed page that loads the runtime and the bundle; `/bundle/{publisher}/{id}/{version}/{sha256}.js` is the bundle; `/runtime/{hash}.js` is the bridge runtime genki wrote, at an address holding the first 16 hex digits of its sha256. A frame or bundle answers `404` unless that edition exists, is code, its `code.sha256` equals the address and the stored bundle still hashes to it.

### The frame

- **The host frames a block with `sandbox="allow-scripts"` and nothing else**, `referrerpolicy="no-referrer"` and `allow=""`, so it runs in an opaque origin: no `allow-same-origin`, `allow-top-navigation`, `allow-popups`, `allow-forms` or `allow-modals`.
- **The frame page's CSP** is `default-src 'none'; script-src <runtime> <bundle>; style-src 'unsafe-inline'; img-src data:; font-src 'none'; connect-src 'none'; webrtc 'block'; media-src 'none'; object-src 'none'; frame-src 'none'; worker-src 'none'; manifest-src 'none'; form-action 'none'; base-uri 'none'; frame-ancestors <hosts>; sandbox allow-scripts`, with `nosniff`, `no-referrer`, `Cross-Origin-Resource-Policy: cross-origin` and every powerful feature off in `Permissions-Policy`. `connect-src 'none'` stops `fetch`, XHR, WebSocket and `sendBeacon`; `img-src data:` stops pixel beacons; `webrtc 'block'` is set for browsers that support it, but Chromium ignores it as an unrecognised directive, so it does not stop WebRTC there (see Consequences).
- **`frame-ancestors`** are the hosted service hostnames (`GENAI_HOSTED_HOSTNAMES`), genki's assistant hostname, `https://*.apps.<zone>` for the zone of the assistant hostname (both zones when none is set), the `https` origins in `GENAI_BLOCK_FRAME_ANCESTORS` (the portal) and, in dev mode only, `http://localhost:*` and `http://127.0.0.1:*`. They are read from the settings at start, so an agency's own Client hostname needs `GENAI_BLOCK_FRAME_ANCESTORS` or `GENAI_HOSTED_HOSTNAMES`.
- **The apps' own CSP** keeps `script-src 'self'` and `connect-src` as they were; `frame-src` adds the block origin when `GENAI_BLOCK_ORIGIN` is an `https` origin (`docker/apps/30-genki-config.sh`).
- **Caching.** The bundle and the runtime are immutable for a year, since their address holds their hash. The frame page is revalidated (`no-cache`), since its `frame-ancestors` follow the settings.

### The bundle

- **An edition carries `block/bundle.js`** and optionally `block/source/<path>` for the reviewer, in the definition's existing files; nothing else under `block/`. The bundle is at most 256 KiB of UTF-8 with no NUL, `code.bytes` must equal its size, and `code.sha256` its hash. Sources are at most 20 files and 512 KiB in all. `code.reads` is at most 32 paths from the field list.
- **The hash is checked in the API.** `@genai/definitions` stays browser-safe and has no crypto: `checkBlockFiles` checks paths and sizes, and `checkCodeEdition` takes the block origin and the hash, which `codeBlockProblems` in `apps/api/src/block-bundles.ts` computes with `node:crypto`. It runs in `admin.check` (validate and preview), the import check, the admin's publish and every publish through the composed store, so the same rule holds on every path.
- **Request bodies.** `POST /definitions`, `POST /definitions/validate` and `POST /tenants/{tenant}/blocks/preview` take at most 4 MiB and answer `413` above it. Import keeps its own limits.
- **No code runs on genki's servers.** The API stores and serves a bundle as bytes.

### The bridge

- **One private channel per frame.** The runtime is the frame's first script. Before the bundle runs it makes a `MessageChannel` and posts `{ genki: 1, type: "ready" }` to its parent with one port. The host (`packages/ui-assembly/src/bridge.ts`, `code-block.tsx`) takes that port only from a message whose `event.source` is the frame's own window and whose `event.origin` is `"null"`, the opaque origin of the sandbox, and only once per frame. After that every message in both directions goes over the port, and the host listens to nothing else from the frame. A page the frame navigates to is a new document without the port, so it gets nothing from the host. This does not stop the bundle from leaking what it already holds (see Consequences). The parent that receives the port is one `frame-ancestors` allows.
- **Messages are JSON objects `{ genki: 1, type, ... }`** (`@genai/contracts/block-bridge`). Host to frame: `render`, with the state, locale, colour scheme, a fixed list of Designsystemet tokens whose values match `^[#(),.%\sa-zA-Z0-9-]{1,64}$`, the settings, the texts in the locale and the data. Frame to host: `resize` (0 to 2,000 pixels), and `event` with `ask`, `open-document`, `set-filter`, `open-page` or `notify`, each with a closed payload.
- **The host** parses a message to its exact shape first and then sizes what it parsed against 8 KiB; it takes 20 events and 20 resizes a second, an event only when the block declares it, and `ask` and `notify` at most once a second each. It posts `render` on the port, holding only `code.reads` (`pickReads`), cut to 64 KiB, at most every 100 ms while the data changes. No `ready` within 5 seconds of the frame loading draws «Designelementet svarer ikke»; a second `load` (the frame navigated to a page that loaded) closes the port, removes the frame and draws «Designelementet ble stoppet». A navigation that never loads, such as one answered with `204 No Content`, fires no `load`, so this catches only navigations that commit. A new frame address starts a new frame. A block from another organisation gets a caption with the publisher's name.
- **Events.** `ask` only fills the composer; the person sends. `open-document` is carried out only for a source index in the data the block was given. `notify` goes to a polite live region. `set-filter` and `open-page` are checked and passed to the host's handlers; the hosted assistant does not carry them out yet.
- **The runtime** (`apps/api/src/block-frame-runtime.ts`) takes a `render` only on its port, of the right shape, and sends events on it only after the first render. It exposes `genki.onRender` (a renderer added later gets the latest render), `genki.emit` and `genki.resize`.

### Sharing a code block with everyone

- **A tenant shares a code edition with its own organisation.** Asking for `everyone` on validate, publish or import is `403` `urn:genai:problem:share-operator-only` at `spec.sharing` (ADR 0067).
- **A share request goes to an operator.** `POST /tenants/{tenant}/blocks/{id}/share-requests` (`manage-services`, the change-reason is the request's reason) asks for the newest edition of the organisation's own block; `422` unless it is the newest, code and not already shared with everyone, `409` while another request on the block is pending. It is stored on the config entry store (kind `block-share-request`, scope the tenant, id the block) and `GET` on the same path lists the organisation's own requests, with who decided them; another organisation gets `404`.
- **One operator decides.** `GET /operator/block-share-requests` and `/{rid}` show the request with what the edition reads, its events and size, and its bundle and sources as text. The bundle is what is approved: the sources are an aid for the reviewer and nothing ties them to the bundle, and the screen says so. `POST .../{rid}/approve` publishes the next edition as a copy of the one reviewed with `sharing: everyone`, as the operator, so the edition read is the edition shared; `POST .../{rid}/decline` leaves the block as it was. Approval answers `409` `urn:genai:problem:block-share-stale` once a newer edition is saved, also one saved while the approval runs: its publish passes the reviewed version as the expected latest to the definition store, which checks it in the same transaction that allocates the next version, so it never rolls the block back. The share routes' problems are `urn:genai:problem:block-share-operator-only`, `-pending`, `-not-pending`, `-stale` and `-studio-off`; a definition body over 4 MiB is `urn:genai:problem:definition-too-large`. Each needs an operator (`403` for anyone else) and a change-reason (`400` without one). Requests and decisions on one API process are taken one at a time, so two approvals publish one edition. The console's «Designelementer til gjennomgang» is the screen for it.
- **Every edition shared with everyone gets its own review.** A later edition is saved for the organisation and needs a new request.
- **Audit.** Requests, approvals and declines are admin actions (`platform.block-share.request`, `.approve`, `.decline`) in the organisation's audit log, targeting `block:<orgnr>/<id>@<version>`, with the operator as the actor, as for other operator actions in an organisation. The approved edition names the operator as its publisher. One operator and the audit log, no second person (proportionate controls).
- **The block detail** (`GET /tenants/{tenant}/blocks/{publisher}/{id}`) carries `review`, the newest request on the organisation's own block.

### Behind the blockStudio flag

- **Code blocks are off until `blockStudio` is on (ADR 0071).** It is self-service: a person can turn it on to build and try code blocks, and a tenant admin for the whole organisation.
- **For the caller.** While it is off for the caller, validate, preview, import and publish refuse `tier: code` at `spec.tier`; the block list and detail leave out code editions and `review`; pinning a code edition answers `404`; and every share-request route, the operator's too, answers `404` like an unknown route (`requireFlag`).
- **For the organisation.** A service draws a code block only while the flag is on for the service's organisation, by the tenant's choice or `GENAI_FLAGS`, not one person's, so the interface carries no frame address otherwise. An operator approves a share request only while the flag is on for the block's whole organisation (`409` otherwise).
- **The block origin is not behind the flag.** It serves an edition to anyone who has its address, as before; only the gated routes hand addresses out.
- **The console's «Designelementer til gjennomgang»** is in the menu and at its address only while the flag is on for the operator.

## Why

A separate origin with an opaque sandbox is what browsers offer for running code one does not trust next to a session: it gets no cookies, storage or DOM of the host, and the CSP takes away the network. Serving it from the API process on its own listener needs no new service, and keeping it a separate app with none of the API's routes means no API route can be reached on the block origin. Addressing the bundle by its hash means the address the reviewer approved can never serve other code.

Turned down:

- **`srcdoc` or a `blob:` frame.** It inherits the host's CSP, so the bundle runs only if the host allows inline or blob scripts for everyone.
- **Running bundles in the host's origin behind a review.** Review reduces risk but does not contain it, and blocks shared only within an organisation are not reviewed.
- **A shadow DOM or a JavaScript sandbox in the host.** Same-origin code can reach the host's session.
- **Reviewing only when what a block reads widens.** Every edition shared with everyone is reviewed; it is simpler and a swapped bundle cannot ride on an earlier approval.

## Consequences

- **Residual risks, said plainly.**
  - **A code block can send everything it is given to anyone, continuously.** The bundle can set `location.href` to a URL of its own with the data in it, as often as it likes. When that URL answers `204 No Content` the browser keeps the document, fires no `load` and the host never notices; a test sent a dozen such requests in four seconds, each carrying the person's question. No CSP directive or sandbox flag stops a frame navigating itself. Removing the frame on its second load only catches navigations that commit. So the controls are what the block is given and who looked at it: `code.reads` limits the data to the fields it declares, and an operator reads the bundle and its `reads` before any other organisation runs it. A code block shared only within its organisation is not reviewed, so `code.reads` is its only control: it can send the person's question and what else it reads to wherever its own organisation wants. Organisations need to know this before they pin one.
  - **WebRTC.** `connect-src` does not govern WebRTC, and Chromium ignores `webrtc 'block'`, so a block can reach a STUN or TURN host over UDP with what it was given; a test saw STUN packets leave the frame. The same controls apply.
  - Inside its box a block can draw anything, including a fake form, but can submit it only by navigating, as above.
  - Frame and bundle addresses are capabilities: anyone who has one can read that bundle, also of an edition shared only within its organisation, so a bundle must hold no secrets.
  - A frame's address and its `frame-ancestors` list the hosted hostnames, which are public names anyway. `*.apps.<zone>` in `frame-ancestors` also matches deeper names than genki assigns.
  - Requests and decisions are taken one at a time within one API process; two API processes could each take one on the same block at the same moment.
  - A busy loop can slow the tab where the browser shares a process with the frame.
- To switch the tier off, unset `GENAI_BLOCK_ORIGIN`: validate refuses code, and pinned code blocks draw the placeholder. Turning `blockStudio` off for an organisation does the same for its services, and for everyone in it who has not turned it on for themselves.
- An export holds an edition shared with everyone as it is, so importing it as the tenant is refused at `spec.sharing` until an operator imports it or the tenant sets `sharing: organisation`.

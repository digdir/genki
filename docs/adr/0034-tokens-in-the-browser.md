# 0034 Tokens in the browser

Status: proposed, 2026-10-16 (the BFF in the API, for the assistant host first, ADR 0061; built for the assistant host, 2026-11-19, and the host signs in through it wherever it serves the BFF; without it, the host keeps its token in `sessionStorage` on the same conditions; the portal, workspace and console sign in through the BFF with the platform login and hold no token, 2026-11-25)

## Context

Until 2026-11-25 the portal, workspace and console logged in with Ansattporten in the browser, with the authorisation code flow and PKCE as public clients, and kept the session in `sessionStorage`. All three kept the access token, the refresh token when Ansattporten issues one, and the ID token. Before the access token expired they renewed it with the refresh token, or without one by a `prompt=none` authorisation in a hidden frame of their own origin, unless the issuer's metadata leaves `none` out of `prompt_values_supported`. All three asked for the same API audience, so a token from any of them carried the person's full rights in all of them. Anything that runs script in an app's origin can read the token and send it anywhere: the CSP limits which script runs, not where that script sends data.

A backend-for-frontend (BFF) keeps the tokens on a server and gives the browser only an HTTP-only session cookie, as Kunnskapsassistenten does (its ADR 0011).

## Decision

- **The portal, workspace and console hold no token.** Each signs in through the BFF on its own hostname with genki's platform login client (ADR 0061, "The platform apps"), keeps only the `__Host-genki_session` cookie, and calls the API through its own `/api/` with that cookie and `GenAI-CSRF`. Their own Ansattporten clients and the settings `PORTAL_CLIENT_ID`, `WORKSPACE_CLIENT_ID`, `CONSOLE_CLIENT_ID` and `CONSOLE_TOKEN_ENDPOINT` are gone.
- **A page that still logs in in the browser,** the assistant host where it serves no BFF, keeps its token in `sessionStorage` on these conditions, which hold today and must keep holding:
  - The apps' CSP allows scripts from their own origin only, with no inline script and no `eval` (`docker/apps/headers.conf`), and every page except the System Atlas refuses to be framed. Only the app's own origin may frame it, and `frame-src` allows only the app's origin and the login issuer.
  - The apps load no third-party script; the one third-party stylesheet is pinned with SRI. React escapes what it renders, and every link built from service or user data is limited to http(s).
  - No API route reachable through the apps' `/api/` proxy returns caller-controlled content as script or HTML, since `script-src 'self'` includes that proxy.
  - The System Atlas is a same-origin frame of the console that can read the console's session. It counts as console code, and every `innerHTML` in it takes only escaped or console-rendered HTML.
- **The token that matters in test is a trusted Entra login, not TestID.** A stolen TestID token is worth no more than a fresh TestID login. A trusted Entra login (ADR 0033) has every platform right and can create API keys and clients that keep model access after the token expires and after the person leaves the Entra group. The risk this decision accepts is an XSS against a team member.
- **The BFF does the code exchange as a confidential client,** keeps the tokens server-side, and gives each app origin its own HTTP-only, `Secure`, `SameSite=Lax` cookie with the `__Host-` prefix. The apps call the API through their own origin with that cookie, and the API turns the session into the same principal as a bearer token, accepted only from the app origin it was created for. External frontends keep using bearer tokens (ADR 0032). Where no session cookie is sent, a platform app's hostname passes a caller’s own bearer token through unchanged and outside any app session, so a smoke test's key works through the app origin; a session cookie always wins and the page's bearer is dropped.
- **The BFF is built in the API** (ADR 0061), for the assistant host and the platform apps.
- **A token kept in the browser is kept in `sessionStorage` only,** never in `localStorage` or IndexedDB. `sessionStorage` is per tab, but survives a reload, a duplicated tab and a restored session.

## Why

A BFF removes the token from the browser, so an XSS bug can act as the person only while the page is open, not take the token away. That matters in production, where the tokens act for real organisations. In test the data is synthetic, and the people whose tokens are worth stealing are a small team. Kunnskapsassistenten already built a BFF, so the pattern and its pitfalls are known: tokens live in the replica that signed the person in, so it needs sticky sessions or a shared session store.

Rejected: tokens in `localStorage` (survives the tab, readable by any script in the origin), and a BFF for the portal, workspace and console in test now (cost without matching benefit while the data is synthetic). A BFF as its own service or in each app's container: ADR 0061 puts it in the API, which already has the session store, content keys and token verifier.

## Consequences

- Closes the token criterion in #41: no platform app holds a token.
- The BFF needs a session store shared by API replicas, so restarts do not sign everyone out. It rotates the session id at login, binds `state`, `nonce` and the PKCE verifier to a pre-login cookie, and at logout destroys the session, revokes the refresh token and ends the Ansattporten session.
- With cookies, every state-changing request through `/api/` checks the exact `Origin` and requires a JSON body or a non-simple header, since sibling subdomains are same-site.
- Refresh tokens go to confidential clients only (Digdir's token endpoint documentation), so the BFF refreshes the access token server-side; with rotation (one use per refresh token) each refresh stores the new one under the session's lease. The browser-side `prompt=none` renewal in a hidden frame is gone with the browser login.
- Logout deletes the session, revokes the refresh token and ends the Ansattporten session; Ansattporten's back-channel logout ends the sessions of that login (ADR 0061). Unsaved input kept across re-login is stored per tab, not per person, and is cleared on a deliberate logout.
- The ID token is used only for the display name, for logout and for the keys a back-channel logout finds the session by. It grants nothing and the API never accepts it. The BFF checks its `nonce`.
- A new script source, inline script or third-party library in the apps lets an XSS bug act as the person while the page is open; review the CSP when adding one.
- Built 2026-11-19: the assistant host (`apps/assistant`, ADR 0061) logs in in the browser on the same conditions, as a public client of the service's hosted Client, and keeps only the access token and ID token in `sessionStorage`, with no refresh and no silent renewal: when the token expires, the person logs in again. It checks `state`, `nonce` and the issuer the metadata names, returns only to a path on its own hostname, and is served with the same CSP, with the issuer's origin in `connect-src`. All of it is in `apps/assistant/src/login.ts`, which the host uses only where it serves no BFF. Tests: `apps/assistant/src/app.test.tsx` and `apps/assistant/src/login.test.ts`.
- The BFF is built for the assistant host as ADR 0061 describes it, in `apps/api/src/bff`, with sessions in `bff_sessions`. It runs in front of the API and only for a request with a valid `GenAI-Proxy-Key`: it swaps the session for the access token as a bearer token, so the API checks the same principal, issuer and `sub` as for a browser token, and drops the cookie, the proxy key and any credential or `genai-acting-for` the page sent. Tests: `apps/api/src/bff/bff.test.ts` and `bff-postgres.test.ts`.
- Decided here where ADR 0061 is silent: `GET /auth/me` answers the name and organisations, never a token. The non-simple header for a state-changing call without a JSON body is `GenAI-CSRF`. `GET /auth/logout` is refused unless `Sec-Fetch-Dest` is `document` and `Sec-Fetch-Site` is same-origin or none, when the browser sends them, so an image in an answer cannot log anyone out. The login cookie is sealed with the tenant's content key. A refused refresh deletes the session and answers 401; an issuer that does not answer gives 503 and keeps it.
- The assistant host signs in through the BFF wherever the host serves it: it asks `GET /auth/me`, and a JSON answer means the BFF is there. It then sends the person to `/auth/login?next=<path>`, calls genki through `/api/` with the session cookie and `GenAI-CSRF`, opens a cited document's site path through the same proxy, and logs out with `/auth/logout`, which ends the Ansattporten session with `id_token_hint`. The page holds no token. Where `/auth/me` answers the host's page instead, as without the proxy key, it keeps the browser login above. Tests: "calls genki through the BFF with its CSRF header and no token once the host has signed the person in" in `apps/assistant/src/app.test.tsx`, and `apps/assistant/src/bff.test.ts`.
- The proxy key is set in `infra/env/test.bicepparam` (`assistantBffEnabled`), with the same `genai-proxy-key` in genki's and the host's Key Vault; `infra/README.md`, "Turning on the assistant host", has the order. Prod has it off.
- Built 2026-11-25: the portal, workspace and console sign in through the BFF with the platform login on their own hostnames (ADR 0061, "The platform apps"); their pages ask `GET /auth/me`, send the person to `/auth/login?next=<page>`, call `/api/` with the session cookie and `GenAI-CSRF`, and log out with `/auth/logout`. Their SPA login code, silent renewal and client ids are removed. Tests: `apps/api/src/bff/platform-apps.test.ts` ("passes a JSON POST or one with the CSRF header from the app’s own origin", "refuses a form-encoded POST from the app’s own origin without the CSRF header", "passes a caller's own bearer token through the portal only without a session, and outside the app session"), `apps/portal/src/bff-login.test.ts`, `apps/workspace/src/bff-login.test.tsx` and `apps/console/src/bff-login.test.tsx`.

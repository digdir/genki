# 0067 Interface blocks are Block definitions

Status: proposed, 2026-11-20 (partly built: the kind and its publish, 2026-11-20; `ref` in the layout and its check, genki's blocks seeded, and the host's block registry, 2026-11-21; the block list across publishers, preview, pinning in a draft, `block: ref`, the zone and settings checks on a ref, the interface's `blocks`, and the operator-only rule for sharing a code block with everyone, 2026-11-21; the declarative tier: its template language, linear check and renderer in the assistant host, 2026-11-21; the code tier with its block origin, bridge and review before sharing with everyone, ADR 0069, 2026-11-21)

Left: the named host channels for code blocks (`set-filter`, `open-page`), Block Studio's screens, the builder editing a layout with `ref`, the genki-admin tools for blocks, importing a design, and unlisting. Each needs its own change; this record fixes the contract they build on.

## Context

A hosted assistant (ADR 0061) draws a service's layout (ADR 0065) from a fixed catalogue of blocks that genki builds as React components in `@genai/ui-blocks` and wires by hand in `packages/ui-assembly/src/Assistant.tsx`. The block ids live twice, in `builder/catalogue.ts` and in `catalogueBlockIds` in `@genai/definitions`, and a new block, a new variant or a changed text is a pull request into genki. ADR 0053 made blocks "data in, events out" and ADR 0054 made the layout data, but a block itself has no record of its own: no owner, no version, no sharing and no way to be published without a developer.

The adopted direction: one publish path for everyone, designers included. A designer or owner saves a block on test, tries it in the real app and promotes it with a reason and an audit entry. genki's own blocks travel the same path. Only the host and core (frame, chat shell, block registry, renderer, sandbox, bridge, named channels and the field list) are code changes by developers.

## Decision

### A kind of its own

- **An interface block is a definition of kind `Block`** beside `Service`, `StepFlow` and `Skill` (`blockDefinition` in `packages/definitions/src/schema.ts`). It has the same `apiVersion`, `metadata` (`tenant`, `id`, `name`, `version`) and store as the other kinds (ADR 0005), so it gets versions, validation, a change reason and the audit log without a new store, table or right.
- **It goes through the definition API.** `POST /definitions/validate` checks it, `POST /definitions` publishes it with `change-reason`, and `GET /tenants/{tenant}/definitions/blocks/{id}` and `.../versions/{version}` read it. The operator's `/operator/tenants/{tenant}/definitions/blocks/...` reads it too. Tenancy and rights are the existing ones: a member of the tenant reads, `manage-services` validates and publishes, and another tenant gets `404` on the reads and `403` on validate and publish. An export of a tenant carries its blocks, before its services.
- **A published version never changes.** A new look is a new version.

### The manifest

`spec` is closed and framework-free: JSON a host reads, never code genki runs.

- `tier`: `built-in`, `declarative` or `code`.
  - `built-in`: drawn by a component the host already has. `builtIn` names it, one of `builtInBlockIds` in `@genai/contracts`, and only this tier has `builtIn`. genki's catalogue blocks are the built-in tier.
  - `declarative`: `template`, a template of data from a fixed element set the host draws (below).
  - `code`: a built bundle drawn in a sandboxed frame from a separate registrable domain, with no token and a narrow message bridge (ADR 0069). `code` holds its `sha256`, `bytes`, `reads` and an optional `height`; the bundle is the file `block/bundle.js`.
- `title`, and optionally `summary`: a text per language, as a map keyed by `nb`, `nn` and `en`; `nb` is required. Nynorsk is one more key, not a new shape.
- `zones`: the zones it may stand in, `primary`, `main` and `secondary`, at least one, each once.
- `sharing`: `private` (the publisher's own services), `organisation` or `everyone`; `private` when left out.
- `props`: a JSON Schema object with ADR 0030's `x-label` and `x-widget`, at most 32 properties and 32 KiB; a required prop must be one of them. The portal draws the block's settings from it with the same schema form it uses elsewhere.
- `events`: what the block may ask the host to do, from the list the host carries out: `ask`, `open-document`, `set-filter`, `open-page`, `notify`, `resize`. A block cannot invent an event. Writes are the host's (ADR 0054); a block never calls the API.
- `states`: the states it draws, from `empty`, `loading`, `error`, `partial`, `disabled`, `filled`.
- `texts`: the block's own words, per language, at most 200 keys per language, 1,000 characters each and 64 KiB in all.

### The declarative tier

- **A template is data.** `spec.template` is `{ version: 1, root, states? }`, where a node is one of 17 elements: `stack`, `row`, `card`, `details`, `heading`, `paragraph`, `list`, `link`, `button`, `tag`, `alert`, `divider`, `icon`, `table`, `keyValue`, `each` and `if` (`BlockTemplate` in `@genai/contracts/block-template`). No expressions, no code, no HTML, no CSS and no address built from parts. `states` holds a node for a declared state, drawn in place of `root`.
- **Every word is a text key.** A text is up to 8 parts: a key in `spec.texts` (with `{name}` arguments, and `key.one` and `key.other` picked by the count when an argument is called `count`), a bound field, the count of a list, or a literal of 1 to 8 characters with no letters. A key must exist in bokmål.
- **A binding reads the field list or a declared prop, nothing else.** A path names a field of `blockFields` in `@genai/contracts`, `props.<key>` of the block's own `props`, or the item alias of an `each` or `table` it stands in. A field of a list's items is read only through an alias; a list stands only where a list is needed and a value only where a value is; a field given in fewer zones than the block's own is refused. `templateReads` gives the canonical paths a template reads, and the host gives the block only those.
- **Links and events are checked twice.** A link goes to an https address with no credentials, a page of the service, or a field of type `url`, and the renderer checks the address again before it draws it, as it checks an `open-page` page name again before it sends the event. A button sends one of the block's declared events: `ask` with a question, `open-document` with the index of a source, `set-filter`, `open-page` or `notify`. The host's `DeclarativeBlock` drops an event the block did not declare.
- **Limits.** 32 KiB as JSON, 200 nodes, 12 deep, 200 paths, `each` and `table` 2 deep with at most 50 items (10 by default), 8 columns, 8 text parts, 20 key and value pairs, conditions 3 deep, and at most 2000 elements drawn once each list repeats its part as often as its `max` allows (`templateDrawn` in `@genai/contracts`). The renderer draws nothing of a template over that budget, so a 4 KiB template cannot draw hundreds of thousands of elements.
- **Shared without review.** A declarative block shared with everyone is not read by anyone before other organisations may pin it, so its free text, its https links and an `ask` whose question differs from its button's label are accepted surface in their assistants; the owner sees them in preview before pinning.
- **The check is linear.** The `blockTemplate` schema runs a pre-pass on the raw value with an explicit stack that refuses an input over the size, node, depth or JSON depth limits before the schema reads it; `checkBlockTemplate` then walks it with an explicit stack and the alias scope as a linked list.
- **The host draws it with Designsystemet.** `Render` in `@genai/ui-blocks/declarative` draws each element with its Designsystemet component, writes data only as text, never as HTML, and keeps the block's own CSS to Designsystemet tokens. A declarative block keeps "data in, events out" by construction: it cannot fetch, and what it does goes to the host's handlers.

### Draft, try and promote

- **A version is saved, tried on test and promoted through the service that pins it.** A block is not deployed on its own: a service's layout pins a version of it, the pin is part of the service draft (ADR 0051) and of the service version, and the version moves from `test` to `prod` with the service by ADR 0004's promote, with a reason and an audit entry. A tester sees the new block on the test hostname (ADR 0064) while `prod` keeps the version it pinned.
- **A layout pins a block by reference.** A placed block in `spec.interface.layout` gains `ref: "<publisher>/<id>@<version>"`, where the publisher is the organisation number of the tenant that published it. A shared block's author never changes someone else's service: a newer version shows as an update the owner takes in a draft.
- **A declarative or code block stands as `block: ref`.** `ref` is a reserved block id, never a built-in one, so a tenant's block called `sources` is never drawn as genki's Kilder. A built-in edition stands as the built-in block it names, as before. `ref` as a block needs a `ref`.
- **A ref is checked against its edition.** It must stand in one of the edition's `zones`, and each of its `settings` must be a prop of the edition, `true` or `false` for a boolean prop and a text within the prop's `enum` when it has one.
- **Pinning has its own route.** `PUT /tenants/{tenant}/services/{id}/draft/blocks/{publisher}/{blockId}` puts an edition in the service's draft, or moves a pin of the same block to it, and `DELETE` takes it out; the draft is started from the latest version when there is none. The version in use changes only when the draft is published and promoted.
- **The interface serves its pinned editions.** `GET /v1/models/{id}/interface` returns `blocks`, the edition of every `block: ref` in the layout keyed by its ref, checked again when read: an edition of the service owner's organisation, or one shared with everyone. Anyone who may use the service reads what its owner placed in it. Nothing else of the publisher's blocks is in it.
- **An organisation sees one list across publishers.** `GET /tenants/{tenant}/blocks` lists its own blocks, genki's built-in blocks and the blocks other organisations shared with everyone, each with only the editions the organisation may use. The portal names an edition by its date, and treats `private` and `organisation` alike, since a tenant is an organisation.
- **Block Studio keeps a working copy before the first save.** Until it exists, saving is publishing a version, which nothing draws before a service pins it.

### Who publishes and shares

- **genki publishes its own blocks** through the same path, shared with everyone. genki's catalogue blocks are the built-in tier; genki may also publish declarative or code blocks, as any publisher does. Only an operator, or the platform's seed, publishes a `built-in` block; anyone else gets `403` `urn:genai:problem:share-operator-only` with the path `spec.tier`, from `POST /definitions/validate` as from `POST /definitions` and the tenant import, so validate and publish agree.
- **One person and the audit log at every level** (proportionate controls): the publisher with `manage-services` publishes `private` and `organisation` blocks after the automatic checks.
- **Sharing with everyone:** a `declarative` block is listed at once after the automatic checks, and an operator may unlist it afterwards. A `code` block is shared with everyone only by an operator, after one Digdir reviewer has read its source and what it reads; anyone else gets `403` `urn:genai:problem:share-operator-only` with the path `spec.sharing`. Every edition shared with everyone gets its own review, so a swapped bundle cannot ride on an earlier approval.

## Why

Sharing and pinning need a thing of their own, as step flows did (ADR 0031, ADR 0050). Inside each service's `spec.interface` a block could not be shared, versioned apart from the service or reused, and every service would carry a copy. As a definition kind it reuses the store, the versions, the reason, the audit log, export and import, and the routes and rights a tenant already has, so nothing new needs securing in the API for it.

The manifest is JSON so a host in any framework can read it, and so React can be replaced later without breaking a published block. Texts as a language map leave room for nynorsk without a new shape. Events from a closed list and no API access keep the rule of ADR 0053 and 0054 that data comes in and writes are the host's, for blocks genki did not write too.

Pinning through the service version means a block reaches `prod` only the way everything else in a service does, through test and a promote, and rolls back with the service.

Turned down:

- **A pull request lane for designers.** It is the cost the current catalogue shows: every block change touches the 1,300-line assembly, and reviews fix data, texts and tokens a manifest could have checked.
- **Blocks inside `spec.interface`.** No sharing, no version of their own, a copy per service.
- **A separate store and routes for blocks.** They would need their own tenancy, rights, audit and export, all of which the definition store already has.
- **Accepting `code` blocks before a host draws them.** A stored block nothing can draw would look published and do nothing; the code tier is accepted since its sandbox is built, once a block origin is set, and the declarative tier since its renderer is.
- **Expressions in a template, or HTML or Markdown from the owner.** Each is a language to secure and a way around the host's theme and accessibility; a closed element set and text keys are enough for cards, lists and tables.
- **Review before listing for every shared block.** Declarative blocks are drawn by the host, so they cannot run code or reach data; review is kept for code blocks, where it buys something.

- A stored Block definition is a contract from its first publish. Changes to its shape are additive.

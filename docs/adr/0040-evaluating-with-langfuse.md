# 0040 Evaluating with Langfuse

Status: accepted, 2026-10-29 (partly built, 2026-10-30; Langfuse judges score runs as adopted building blocks and scores are read per case trace, 2026-10-30; judge cost with the daily USD/NOK rate, 2026-10-30; a run goes to Langfuse only in step with its project's judges, 2026-10-30; a run goes to Langfuse only when it asks, also with a Langfuse judge in use, 2026-11-02; labels from Langfuse with an operator's acceptance, 2026-11-02; judges read through Langfuse 4.72.0's v2 evaluation API, 2026-11-02; Langfuse 4.72.0 only, without the `unstable` API or 4.4.0, 2026-11-12; a Langfuse dataset per test set and test runs in their own environment, 2026-11-02; filters are read, not refused, 2026-11-02; the section "Langfuse judges that block" stays proposed). Proposed 2026-10-22

Amends 0003, 0011 and 0024. Touches 0015, 0021, 0022, 0023 and 0027.

## Context

The platform runs, judges and gates its own evaluations (ADR 0003). Some teams already judge answers in Langfuse, and a proposal asked to let Langfuse run evaluations and experiments while the results and runs stay available in the platform. Langfuse 4.4.0, the version the self-hosted instance runs, scores a trace a few seconds after it arrives, cannot be asked to run a judge on request and announces no new scores. Its trace deletion leaves copies of the text behind. The platform needs 4.72.0, whose v2 evaluation API it reads judges through, and does not support 4.4.0, which lacks that API; the instance is to be upgraded. The behaviour this record relies on was measured against a local Langfuse 4.4.0, and the judges, labels and erasure again against a local 4.72.0.

## Decision

**The platform stays the default and the record.**

- Every eval run is started by the platform, answered by the service under test and recorded as an `EvalRun`. Publishing gates read only the platform's records.
- Langfuse is optional and chosen per judge. Langfuse 4.72.0's v2 API gives a rule no target, only filters. An experiment judge is an enabled rule with one LLM-as-a-judge evaluator, which is active, and the filter `isExperimentItemRootSpan = true`, so it judges each item once, on its root span. Its mapping is the rule's own, or its evaluator's when the rule has none. Each experiment judge in the project of a tenant's connection is a judge building block, `langfuse:<connection>/<rule>`, named after the rule. The tenant takes it in use with "Ta i bruk" and a reason, as any building block. A run of a service the connection covers that is sent to it is scored by every judge the tenant has taken in use from it, beside the platform's own judges, for example `contract`, `retrieval` and `langfuse:kudos/kudos_quotes_covered`.
- A Langfuse judge is advisory. Its scores are recorded on the run's cases and shown in the portal, apart from the run's own metrics, and never block a publish or weaken another gate: a gate whose metric comes from a Langfuse judge is refused when it is saved in Kvalitetskrav (`PUT /tenants/{tenant}/gates/{id}`), and a service definition whose gates include one is refused at publish, naming the rule. Langfuse judges that block are a separate proposal, below.

**Connections per tenant.**

- A tenant has one or more Langfuse connections. Each has an id, a host, a public key, a secret key as a `secret://` reference (ADR 0015), the services it covers, a residency and whether it receives content, and points to one Langfuse project. A service is covered by at most one connection.
- **Residency.** A connection's residency (`norway`, `eu` or `global`, as for models in ADR 0021) covers both where its host stores what it receives and where its judges' models run, since a judge reads the question, the answer and the sources.
  - A new connection to Digdir's instance starts as `global`, and an operator sets its residency once both places are known. For a Langfuse the tenant runs itself, the tenant's declaration is enough, as for erasure (ADR 0011).
  - A run sends to a connection, and may use its judges, only when the service's residency allows the connection's. Otherwise a run that asks to be sent (`trace: true`) is refused before it starts.
  - When measured, the judges on Digdir's instance answered from Sweden Central, so a `norway` service cannot use them.
- **Access on Digdir's instance.** The default host is Digdir's instance. There each tenant has its own Langfuse organisation, which is the only access boundary Langfuse enforces without an enterprise licence.
  - A Digdir operator creates the organisation when the tenant asks, and invites the owner the tenant names.
  - The owner sets up the projects, judges and keys, and invites and removes the tenant's other members.
  - Langfuse accounts are separate from the platform's sign-in and are not tied to Altinn rights. Nothing done in Langfuse decides a publish on its own: Langfuse judges are advisory, and labels made there count only after a person with the labelling right accepts them in the platform.
- A tenant may instead enter its own Langfuse.
- Every call to a connection's host (export, score reads, snapshots, dataset reads, dataset creation and deletes) goes through the isolated egress path of ADR 0015, with the host as the tenant's allow list: HTTPS only, no private or link-local addresses, no access to the platform's network, and limits on response size and time.
- **Eval runs only.** A tenant's connection carries eval runs and their judging, never live answers. The platform-wide exporter (`TRACES_ENDPOINT`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`) carries Digdir's operational traces with metadata only. `TRACES_CONTENT` is honoured only in development mode (`GENAI_DEV_MODE=true`).

**Deferred judges: `evaluator@2`.**

- The evaluator contract becomes `evaluator@2` and replaces `evaluator@1`. An evaluator returns its scores at once or answers `pending`, and the runner collects pending scores later. One contract suite tests both paths.
- A Langfuse judge is a built-in evaluator of this kind. Its identity is `langfuse:<tenant>/<connection>/<rule>@v<version>+<model>`, with the evaluator's version and its model as `<provider>/<model>` from the evaluator's model config, for example `langfuse:dfo/kudos/kudos_quotes_covered@v3+openai/gpt-4.1`. Its metric is `langfuse:<connection>/<rule>`. Langfuse names judges within a project, so two tenants, or two projects of one tenant, can each have a judge called `kudos_quotes_covered` with its own prompt. With the tenant and the connection in the identity, the results and calibration labels of one never count for the other.
- A Langfuse judge must name its model. A judge that falls back to the project's or the organisation's default model is refused, because a default cannot be read through Langfuse's API.
- A judge whose mapping reads a field the platform does not send, such as `tool_calls` or `metadata`, is refused, and so is one that reads into the question or the answer, which go as the platform's parts, or reads at a JSON path other than `$` or a dotted path of plain keys.
- A judge that would leave cases unscored is refused: a rule with sampling below 1, since Langfuse judges only the items it lets through, a rule with a filter outside Langfuse's filter list (below), and an evaluator that is not an LLM-as-a-judge. A rule with more than one evaluator is refused too, since Langfuse runs it while any of them is active, and so are rules that share a name, which Langfuse allows but the judge's id cannot tell apart. A rule whose evaluator is paused does not run in Langfuse: Byggeklosser does not list it and it does not count against a run, but a judge taken in use whose evaluator is paused stops a run that asks to be sent, with Langfuse's `pausedMessage`.
- A judge on a connection that does not receive content is refused, since each case would cost a judge call for a judge that has nothing to judge. When a connection stops receiving content after its judge was taken in use, the portal says so before a run that asks to be sent starts, and such a run does not start.
- A refused judge's building block says why and cannot be taken in use. A judge taken in use that is refused, inactive or gone when a run starts stops a run that asks to be sent before it starts, with the reason.
- **Judges that cannot be read are never read as none.** When the rules or evaluators of a connection's project cannot be read (an HTTP error such as 401, 404 or 5xx, for a listing or for a read by id), a run that asks to be sent is refused: "the judges of the connection … could not be read". `GET /tenants/{tenant}/services/{id}/eval-runs/sending` answers `judges-unreadable` with what Langfuse answered, and Byggeklosser shows one refused block for the connection, `sink-judges:<connection>`, that cannot be taken in use. Langfuse before 4.23.0 has no v2 evaluation API, so it answers 404.
- **In step with Langfuse.** Langfuse runs every active rule in a project on every observation its filters let through, and cannot be asked to run only some of them. So before a run is sent, the platform reads the filters of each enabled rule with an active evaluator and decides, per rule, what it does with the run's cases:
  - **The filters leave the run out:** the rule is skipped. It is not listed for the run and does not refuse it. Examples: a `datasetId` filter naming another test set's dataset, `environment none of [genki-test-runs]`, a `traceName` the platform does not use.
  - **It judges each case once:** it lets the case's root span through and no other span, and has `isExperimentItemRootSpan = true` (or `<> false`). It is a judge of the run, so it must be taken in use and not refused, as above. A judge without a `datasetId` filter reaches every test set.
  - **It would judge every span, or the platform cannot tell:** the run is refused, naming the rule and why. Langfuse runs a rule that lets other spans through on each of them: three times on a case trace with a retrieval and a generation, measured on 4.72.0. A rule that reaches only the root span through `isRootObservation` or `parentObservationId` is refused too, since the platform has not measured that Langfuse gives it the experiment's fields.
- The platform tests each filter the way Langfuse does, against what it knows of one case before the run: the root span exactly, and every other span by what the whole trace shares. Langfuse 4.72.0 takes a closed list of filter columns, each with its value type and operators (any of, none of, all of, =, <>, >, <, >=, <=, contains, does not contain, starts with, ends with, is not empty, is set, is not set, is null, is not null), read from its rule API on 2026-11-02. A column, operator or value type outside that list refuses the run. The platform knows `datasetId` (the test set's dataset), `environment` (`genki-test-runs`), `experimentName` (`<test set> v<version>`), `type` (`AGENT` on the root; `AGENT` for a service the case calls, `SPAN`, `GENERATION`, `RETRIEVER` or `TOOL` below it), `isExperimentItemRootSpan`, `isRootObservation`, `parentObservationId` and `tags` (`tenant:<organisation number>` on the root and none below it, since Langfuse reads tags per span). A run's `experimentId`, its trace name, its root span's name and its `service:` tag hold the draft's id, new for each run, so no list a person wrote names them. A span's `name` below the root depends on what the run does, so a `name` filter alone never leaves a run out. Columns whose value differs per span (`level`, `statusMessage`, `providedModelName`, `promptName`, `promptVersion`, `version`, `release`, `metadata`, `calledToolNames`, `toolCalls`, `userId`, `sessionId`) refuse the run unless another filter leaves it out, and a judge with such a filter is refused, so it cannot be taken in use. Text is compared with letter case, as Langfuse does.
- A run that asks to be sent is refused before it starts while a judge that reaches it is not taken in use or is refused, or a rule refuses it, also with nothing taken in use. `GET /tenants/{tenant}/services/{id}/eval-runs/sending?testSet=<test set>` answers `judges-differ` with the judges to take in use (`notInUse`) and the rules to switch off or filter (`unreadable`), the judges in use that reach the test set (`judges`) and the judges whose filters leave it out (`elsewhere`). The portal shows them in the run dialog, and on the test set when it is shown, with the judges for other test sets collapsed. When Langfuse cannot be read, the test set still shows its dataset and says the judges could not be read. A judge taken in use whose filters leave the test set out takes no part in that run. A run cannot pick some of a connection's judges: the API has no way to name a Langfuse judge for one run.
- At the start of a run the platform takes a snapshot of the Langfuse evaluation rule, its variable mapping, the evaluator version it points to and the named model (`GET /api/public/v2/evaluation-rules/{id}`, `GET /api/public/v2/evaluators/{id}`; the listings `GET /api/public/v2/evaluation-rules` and `GET /api/public/v2/evaluators`, every page by cursor). If any of them differs when the scores are collected, or the rule is gone, disabled, lost its item-root filter, its filters no longer reach the run or its evaluator is paused, those scores are marked `judge changed`.

**What an eval run sends.**

- A run goes to the tenant's Langfuse only when it asks for it with `trace: true`, which the portal shows as a checkbox, unticked by default, also when the service uses a Langfuse judge. Nothing is sent to a tenant's Langfuse without a person asking for that run. A Langfuse judge scores only a run that is sent: a run that is not sent names the judges in use that did not score it (`unsentJudges`), and the portal shows that on the run. Under the checkbox the portal names the judges in use, and when it is ticked, it says before the run starts when the service's residency does not allow the connection's, two connections cover the service, the connection gets no answer text, or the project has judges the platform does not read (`GET /tenants/{tenant}/services/{id}/eval-runs/sending`). A judge in use that has become refused or gone is reported when the run starts.
- A run is one Langfuse experiment (Langfuse's word for a single run), linked to its test set's dataset (below). Each case of each repeat is its own Langfuse trace and experiment item, with the item id `<case>#<repeat>`: the exporter starts a new trace at a case's task, although that task is a sub-task of the run's task.
- The evaluation context (run, case, repeat, split and what the case expects) is recorded beside the case task's input, not in it. The kernel keeps it as its own audit field. The strategy never receives it, and the trace input, the timeline and every other reader of the task's input leave it out. The exporter sends from it only what the judges map.
- Only train and validation cases are sent and, when the run uses Langfuse judges, only those at least one of them can read. A Langfuse judge's score on a case that is not sent is not applicable, never pending, so a run never waits for it.
- Text is sent only on a connection that receives content, and only the fields the run's Langfuse judges map, read from the snapshot of their rules: the question (`input`), the answer (`output`) and the case's `expected.criteria` (`expected_output`), or, for a criteria case without named criteria, its reference answer as `criteria`, as the platform's criteria judge reads it. The item's case, repeat and split go as `experiment_item_metadata`, which is not text. A field no judge maps is not sent, and no error text is sent with a run's traces. Cited sources and retrieved documents are not sent yet, so no judge can map them.

**A dataset per test set.**

- The platform writes datasets to the agency's Langfuse: one per test set of each service a connection covers, named `genki/<service>/<test set>`, such as `genki/klarsprak/klarsprak-brev`. It makes them when the connection is saved and when a test set is saved for a service the connection covers, so each test set has its dataset before its first run. Langfuse not answering then does not stop the save: what it could not make is logged (`langfuse dataset not made`).
- It finds a dataset by its name (`GET /api/public/v2/datasets/{name}`) and creates one only when Langfuse answers that there is none (404 with `LangfuseNotFoundError`; any other 404 is an error) (`POST /api/public/v2/datasets`). It never writes to a dataset that exists: that POST replaces a dataset with the same name, description included. The stable v2 routes work on Langfuse 4.4.0 and 4.72.0 (measured on 2026-11-02).
- The dataset holds no items: the cases stay in the platform, and a run sends only what the judges map, as above. Langfuse links a run to a dataset by its id alone, also with the platform's own item ids (`<case>#<repeat>`), and a judge filtered on `datasetId` judges it (measured on 4.4.0 and 4.72.0).
- The platform keeps each dataset's name and id with the test set and the connection (configuration entry `trace-dataset`, id `<connection>/<service>/<test set>`, with the project's host and public key). The connection lists the datasets of the test sets in the services it covers now, and the test set shows its dataset's name, which an agency puts in a judge's filter in Langfuse to point it at the test set. The platform never changes an agency's judges.
- When a run that asks to be sent starts, the platform looks the dataset up again, and makes it again if it was deleted in Langfuse. It asks only once the run's own checks have passed, so a run refused for its residency or its draft writes nothing to the project, and before it reads the judges, which are decided with that dataset's id. A run whose dataset can be neither found nor made is refused before it starts. Every span of a sent run carries the dataset's id (`langfuse.experiment.dataset.id`).
- The platform cannot delete a dataset: Langfuse answers 405 on both the v1 and v2 routes (measured on 4.4.0 and 4.72.0). So the name holds only service and test set ids, nothing personal, and the dataset stays behind when its test set or connection is removed. The runs' traces are deleted as above.

**Test runs in their own environment.** Every span of a sent run carries the environment `genki-test-runs` (`deployment.environment.name`, which is where Langfuse reads it), the same for every agency. An agency's judges on its live traffic can then leave the platform's test runs out with one filter.

**Digdir's default judges are the platform's judges.** Judges Digdir offers every agency run in the platform, as the platform's own evaluators. A Langfuse judge is one an agency writes itself in its Langfuse project and points at a test set's dataset. Building the default judges is not part of this record's built parts.

**Collecting scores.**

- While scores are pending, the run is `waiting for scores`. The platform reads each pending case's scores from its trace, in pages (`GET /api/public/v3/scores?traceId=…&fields=details`). Reading by `experimentId` filters on a score's own dataset run, which a judge's score on an experiment item does not have, so it returns none (measured on a local Langfuse 4.4.0, 2026-10-30).
- The wait runs inside the eval run's background lease, like its cases. A restart during the wait interrupts the run, as a restart during its cases does today.
- Only scores whose `metadata.job_configuration_id` is the snapshotted rule count. A score with the same name from another rule is ignored.
- The wait lasts at most 5 minutes from when the run's last case was sent. A score still missing then is recorded as missing, and the run shows the judge's result as incomplete with a reason, such as `no score from langfuse:kudos/kudos_quotes_covered for 20 of 84 cases`. The platform never falls back to another judge.
- A boolean score becomes 1 or 0. A numeric score is scaled to the range 0 to 1 with its score config's minimum and maximum. A categorical score, or a numeric one without both bounds, is shown as it came.
- A score is not applicable when a field the judge's mapping reads is empty for the case, or when the connection does not receive content. Langfuse fills a missing variable with empty text and still scores it.
- Scores are written as `kernel.score` events on the case's task (`Kernel.annotate`) and into the `EvalRun`, whose provenance lists the judge's identity. The judge's reason may quote the answer, so it is kept only in the case task's `kernel.score` event and follows the case's retention (ADR 0011); the `EvalRun` keeps the score without it.
- **Judge cost.** Langfuse runs every active experiment judge in the project on each case it receives, and bills each call. So in the same pass, for each case it reads, the platform follows every score on the case's trace to its judge's execution trace (`GET /api/public/v2/observations?traceId=…`, the trace id found as for erasure) and adds up its `GENERATION` calls: their tokens, and Langfuse's cost in USD (`costDetails.total`). Each call counts once. It stores them on the run (`usage.reported`), marked as reported by Langfuse: per judge the run uses, and together for any other judge of the project, such as one switched on in Langfuse during the run, with Norges Bank's USD/NOK rate and its date (`usage.usdNok`) to show kroner. The cost is shown beside the platform's own, only to those who see usage, and does not count against the tenant's quota. Langfuse prices a call only when the model name the call reports matches its price table; otherwise only the tokens are stored and the call is counted as unpriced. A call whose cost cannot be read yet is read again on the next pass and never holds back a score; one still unread when the run ends is counted as such, and the amount is shown as at least that.
- When the run uses Langfuse judges, a case that none of them can read (a field a judge maps, other than the answer, is empty) is not sent, as holdout cases are not, so no judge bills it. When the wait for scores ends, the platform reads every case it sent once more: a judge that scored late is counted, and a judge that was active in the project at the run's start but has not scored a case is counted as unread when the run is saved, so the amount is shown as at least that. A run sent while the project has no active judge waits for no score, so the calls of a judge switched on during it are not counted.
- **The rate.** The worker reads Norges Bank's official USD/NOK rate (`https://data.norges-bank.no/api/data/EXR/B.USD.NOK.SP`) once a day through the egress guard, and at start when none is known, and keeps the latest as a configuration entry (`exchange-rate`, `USD-NOK`). Until a rate is known, the cost is shown in dollars.

**Labels from Langfuse.**

- A tracing connection brings labels back only while its labels switch is on (`labels` on the connection, set by the tenant with `platform.tracing.connection.save`). It is independent of `content`.
- An operator fetches a connection's labels in the console (`POST /operator/quality/sink-labels/fetch`); nothing reads them on a schedule. The platform reads every score with source `ANNOTATION` in the project (`GET /api/public/v3/scores?source=ANNOTATION&fields=core,details,subject,annotation`) and the score config of each (`/api/public/score-configs/{id}`).
- Langfuse 4.72.0 names a judge's scores after its evaluator, not its rule. Each score of a Langfuse judge records that name (`details.scoreName`), and a label is matched by it. When two enabled rules in the project write scores under one name (they run the same evaluator, or evaluators that share a name, which Langfuse allows), a label cannot say which rule it is for: neither gets labels, and the fetch answers `shared` with the name and its rules, which the console shows. Reading the rules for this is part of the fetch, and a fetch that cannot read them stops.
- An annotation whose score config has the name and type of a judge's scores, on the trace of a case a run sent through that connection, becomes a pending calibration label: a sink label (`SinkLabel` in `@genai/eval`, table `sink_labels`) for that judge and case, with the annotation as `humanLabel` and the judge's own score on the same case and repeat, as the run recorded it, as `judgeLabel`. A boolean is good or bad; a number is scaled with its score config's minimum and maximum and split at 0.5, and one whose config has no range is no label; a category is kept as it came. A label on a case the judge did not score is unpaired, counted and never guessed. Annotations on traces the platform did not send, such as holdout cases, cases no judge could read or another system's traces, are ignored. A case sent with an empty answer can be labelled; its label is unpaired. A Langfuse page or score config that cannot be read stops the fetch, so it never takes a label for deleted.
- A label is kept under the judge without its version and model, `langfuse:<tenant>/<connection>/<rule>`, with the identity that scored the case beside it. The evaluator id `langfuse:<connection>/<rule>` has no tenant, so labels never pool under it.
- Labels from Langfuse arrive as pending, one batch per connection and judge. They count only after an operator accepts the batch with a reason (`platform.judge.label.accept`); an operator may also reject it (`platform.judge.label.reject`). Both are written to the audit log. A rejected label comes back only if it is edited in Langfuse.
- An annotation edited in Langfuse comes back as a new pending revision; the accepted one counts until the edit is accepted. One deleted in Langfuse stops counting at the next fetch. Langfuse 4.72.0 changes an annotation's `updatedAt` on every edit, so the revision is its `updatedAt` (measured on a local 4.72.0 on 2026-11-02, where a deleted annotation also left the API at once). In 4.72.0 an annotation made on a trace sits on its root observation, with the trace in `subject.traceId`.
- A Langfuse judge's agreement with its accepted labels is shown beside its scores: Cohen's kappa, the share alike and the number of labels, how many of them another version or model of the judge scored, and the unpaired ones. A new version of a judge takes over the accepted labels of the same tenant, connection and name (ADR 0003), never another tenant's.
- The labeller is stored as a pseudonym per tenant: an HMAC of the Langfuse user id with the tenant's own key (`sink_label_keys`), which is made on first use and never shown. The same Langfuse user is someone else in another tenant.
- Sink labels are stored apart from the console's label queue (`judge_labels`), which stays. Both are append-only.

**Importing a Langfuse dataset.**

- An import reads the dataset as it stood at one time (`GET /api/public/dataset-items?datasetName=…&version=…`), and only into the tenant that owns the connection.
- Every item goes through the candidate review of ADR 0011 (anonymisation, human review, expiry). The import is reviewed as one batch and becomes one new test set version, whose provenance names the dataset and the time. Nothing is kept in sync.
- Imported cases go to train or validation, never holdout, since the items have been visible in Langfuse. The items' `expectedOutput` fields become the cases' `expected.criteria`. The portal's import of test cases from a file is not affected.

**Erasure.**

- The platform records the id of every trace it sends to a sink, and of every judge trace it finds for them. The ids are metadata and are kept until each delete is confirmed.
- When the nightly purge or any other erasure removes a case's task, the platform records the deletion of its traces in the sink as pending, in the database. The nightly purge works through the pending deletes. For each case trace it first finds the judges' execution traces, then deletes them, then deletes the case's trace (`DELETE /api/public/traces/{traceId}`).
  - It finds judge traces through the scores on the case's trace (`metadata.job_execution_id`, whose trace id is the first 32 hex characters of `sha256(job_execution_id)`) and through traces whose metadata names the case's trace (`target_trace_id`), so a judge call that wrote no score is found too.
  - After the deletes it checks that no trace with the case's trace as target remains.
- A failed delete stays pending and is tried again the next night, without holding back the purge in the platform. A delete that keeps failing, for example because the connection's secret was rotated, is reported to operators. Showing the connection as failing to its tenant is not built yet.
- Removing a connection that has received traces first marks every trace sent through it for deletion. While it is being removed it covers no service and nothing is sent to it, and it is gone once the purge has confirmed every delete, so removing a connection never leaves text in the sink. While deletes are owed, its host and project cannot change; a new secret for the same project can be set.
- A connection receives content only when ADR 0011's conditions for content-receiving sinks hold. In development mode a Langfuse on the developer's own machine is exempt from the 7-day rule, for made-up test sets only.

## Langfuse judges that block (proposed separately)

Accepting this record does not let a Langfuse judge block a publish. That needs a decision of its own on these conditions, and the catalog condition has no answer yet:

- **Spend.** The judge's reported cost (see "Judge cost" above) counts against the tenant's quota, and a run does not start once the quota is spent. The platform's own model calls are also metered after each call (ADR 0021), so reported cost is enough as long as every call is priced: a judge whose model Langfuse does not price cannot block. A key per tenant with a budget from the AI Gateway (ADR 0038), set as the project's model connection, is another way.
- **Catalog.** The judge's model is a model in the platform's catalog, so the checks the platform makes on a service's own models (residency, approved models under ADR 0023, model family) apply to it. A model name typed in Langfuse says nothing certain about the deployment behind it.
- **Calibration.** The judge meets ADR 0003's calibration rule on the accepted labels of the same tenant, connection and name, and its model is from another family than every model that wrote the answer.
- **Complete, comparable scores.** Only boolean scores and numeric scores with both bounds can block, and only from an unchanged judge (`judge changed` never blocks). A score still missing after the wait makes the gate fail with its reason, and the gate never averages over the scores that arrived.
- **Holdout.** A gate on the holdout split (`split: holdout`) never uses a Langfuse judge's metric, since holdout cases are never sent.
- **A wait that survives restarts.** The wait for scores is a durable job, so a deploy never loses the scores a gate reads (ADR 0041, durable jobs on pg-boss).

## Why

- Teams get Langfuse's judges, comparison views and annotation queues, while the publishing decision, the run record and the holdout stay in the platform.
- **Advisory first.** Scores from Langfuse judges can show in the platform now. A judge that blocks also needs its cost counted against the quota and its model checked against the catalog. Langfuse reports the cost, but the catalog check has no answer yet, so blocking waits for its own decision.
- **Residency follows the text.** A judge reads the question, the answer and the sources, so where its model runs and where Langfuse stores the trace are places the service's text goes.
- **The tenant and the connection are part of a judge's identity.** Calibration labels pool by tenant, connection and name, and a name alone would let one tenant's labels decide whether another tenant's judge may block.
- **No durable jobs yet.** While Langfuse judges are advisory, a restart during the wait loses only scores that cannot block, and a restart already interrupts a run during its cases. Deletes must survive restarts, but the nightly purge already runs every night on one worker, so pending deletes in the database need no job queue.
- **Operators create organisations.** The organisation is the only boundary between tenants on Digdir's instance. Whether Langfuse 4.4.0 can create organisations through an API, or limit who creates them without a licence, has not been checked. Creating them by hand keeps Digdir in control of who owns each one.
- Langfuse's API cannot delete its raw ingestion files or the judge's input copies, so only a storage lifecycle rule removes them. That is why a sink that receives content must keep them at most 7 days (ADR 0011).
- Turned down:
  - **Langfuse runs the evaluations on its own model connections.** It would judge a prompt and a model, not the service with its search and steps, and the gate would depend on a second source of truth.
  - **Langfuse's experiment runner calls the platform as the task.** The platform would no longer start, record or gate its own runs.
  - **Mirroring test sets into Langfuse datasets.** A second copy drifts. The dataset per test set holds no items for that reason.
  - **A dataset per service or per connection.** A judge could then not be pointed at one test set.
  - **One Langfuse project for every tenant.** Without an enterprise licence every member of an organisation sees all its projects, and an experiment judge scores every experiment in its project.
  - **Judges on runs without text.** A Langfuse judge with no input answers `true` on nothing.
  - **A separate plug-in kind for deferred judges.** That makes two contracts for one idea, while the platform is not in production and can change `evaluator@1`.
  - **Langfuse labels counting at once.** Anyone in a Langfuse organisation can annotate, so labels that decide whether a judge may block need the platform's labelling right.
  - **Mapping Altinn rights onto Langfuse membership.** Langfuse has its own accounts and roles. The platform's rights decide what counts in the platform, such as accepting labels and publishing.
  - **Live answers on a tenant's connection.** It would widen the pending deletes from eval cases to every live answer.
  - **Picking Langfuse judges per run.** Langfuse would still run and bill the others on every case sent, so the platform would show fewer scores than Langfuse made.
  - **Sending every run of a service whose Langfuse judge is in use.** Cases would leave the platform, and judge calls be billed, without a person asking for that run. A judge's results can then have gaps between runs, and each run that is not sent says so.

## Consequences

- Partly built. Built: `evaluator@2` and its contract suite with the `waiting for scores` state in `EvalRun`; the tenant connections through the egress path, with their residency checked when a run starts; the kernel change that records the evaluation context beside the input, with readers that leave it out; per-case traces under a run and the experiment export; the pending sink deletes and their pass after the nightly purge, and removing a connection by deleting first; limiting `TRACES_CONTENT` to development mode; Langfuse judges as building blocks with their snapshot, refusals and identity, their reported cost with the daily USD/NOK rate, the mapped fields they read, the score collector inside the run's lease, `judge changed`, labels from Langfuse with an operator's acceptance and the judge's agreement with them, refusing gates on their metrics at save and at publish, and refusing a run while its project has active judges the platform does not read; a Langfuse dataset per test set, made on save and checked when a sent run starts, with its id on every span, and the environment `genki-test-runs` on test runs; reading the rules' filters per test set, so a judge filtered to a test set's dataset judges it, a rule whose filters leave the run out is skipped, and a rule that would judge every span refuses the run. Not built yet:
  - the dataset import
  - having a new judge version score the labelled cases again (ADR 0003): a Langfuse judge only judges what an experiment sends, so its agreement uses the verdicts earlier versions gave
  - pending sink deletes after an erasure other than the nightly purge
  - showing a connection whose deletes keep failing as failing
- Before agency data goes to Digdir's instance:
  - whose model key an agency's judges use there, and so who pays for their calls, is decided. The cost of each judge call is readable (about USD 0.008 per call on `claude-sonnet-5` at Langfuse's list price, measured on Digdir's instance on 2026-10-29), so Digdir's key with the cost shown per tenant is an option beside each tenant's own key.
  - where the instance stores what it receives is confirmed, so operators can set its connections' residency
  - the judge trace id rule and filtering traces by `target_trace_id` through the public API are verified against the instance's version, so the purge can show that nothing of a case is left. Until then no connection to the instance receives content.
  - the items in [epic 93](https://github.com/digdir/genki/issues/93): the 7-day lifecycle rule on its raw files, confirmed deployment types for its judge models and a data-protection assessment
- Operators create organisations on Digdir's instance by hand. Each organisation's owner manages its members in Langfuse, including removing people who leave the tenant. The platform does not see Langfuse membership.
- Plug-ins registered as `evaluator@1` are refused until they are registered again under `evaluator@2`. The platform is not in production, so no stored registration is migrated.
- It reads judges only through Langfuse's v2 evaluation API (`/api/public/v2/evaluation-rules`, `/api/public/v2/evaluators`), which exists from 4.23.0; 4.31.0 removed the `unstable` API that 4.4.0 offered. The platform does not read the `unstable` API and does not support 4.4.0. Langfuse judges reach production only once Digdir's instance runs 4.72.0; on an older instance a connection's judges cannot be read, and a run that asks to be sent is refused. The local Langfuse the live tests use runs 4.72.0.
- The upgrade from 4.4.0 keeps each rule's id and name. Its evaluator is named after the rule's score name, and rules that agree on template, mapping, score name and pause state share one, whose id is the lowest of their rule ids (Langfuse's migration `20260821121500_backfill_evaluator_v2`). The evaluator keeps the version it had: a judge at version 2 stays at version 2 (measured on a local 4.4.0 upgraded to 4.72.0 on 2026-11-02, where the v2 API showed an experiment rule with the item-root filter beside the dataset filter it had). The dataset filter it keeps is read as above.
- Two Langfuse internals were seen in 4.4.0, and again in 4.72.0, but are not documented: the judge trace id rule, and `target_trace_id` and `job_configuration_id` in a judge trace's metadata, which the public API returns (seen on Digdir's instance on 2026-10-29). Filtering traces by `target_trace_id` through the public API is not yet verified (see "Before agency data goes to Digdir's instance"). Both are checked against each Langfuse version.
- Labels match the exact name of a judge's scores, the evaluator's in 4.72.0, and the platform does not guess. The labels switch's help text says to make the score config with the evaluator's name and type.
- A judge without a `datasetId` filter is not limited to one experiment: it scores every experiment in its project, and so reaches every test set. An agency points a judge at one test set by adding its dataset to the judge's filter, beside `isExperimentItemRootSpan = true`.
- Datasets the platform made stay in the agency's Langfuse after their test set or connection is removed, since Langfuse cannot delete them through its API. An agency removes them in Langfuse's UI if it wants them gone.
- Labelling is an operator right today (ADR 0027). Whether agencies get it is not decided here.
- The portal changes:
  - the Tracing screen manages a tenant's connections, shows each one's residency and has the switch that brings labels back as pending calibration labels, not feedback; the console's quality screen fetches them and accepts or rejects each batch
  - the Quality screen shows Langfuse scores as advisory, apart from the platform's metrics, with not-applicable counts, missing scores, `judge changed`, each case's verdict and reason, and a link to the experiment (`/project/<project>/experiments/results?baseline=<run>`, seen in 4.4.0); with each judge's reported cost and its agreement with its accepted labels
  - Byggeklosser lists each experiment judge with its model, evaluator version, data type and mapped fields, says why a refused one cannot be taken in use, and shows a connection whose judges cannot be read as one refused block
  - a run started in the portal is sent to Langfuse only when its checkbox is ticked, and a run not sent says which judges in use did not score it
- The operator of a Langfuse that receives content must meet ADR 0011's conditions.
- Langfuse hides deleted rows in ClickHouse at once and removes them from disk later. The platform cannot speed that up.
- Every rule gets a test that names it when it is built.

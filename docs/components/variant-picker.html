Variant picker

Lets a person choose which variant of the service answers the next question, when the service offers more than one.

Sits in

Use it when

  • The service has two or more variants a person may pick: the rows of GET /v1/models with _pickable, for one service.

Don't use it when

  • The service has one variant. The block then draws nothing.
  • To choose between services. A variant is never shown as a service or an agent of its own (frontend contract, Services and their variants).

Variants

  • One: a button with no frame and the name of the variant in use, with a list that opens above it.

Where it goes

  • In the question field, in the composer's actions slot, at the end of the row before the send button. Kunnskapsassistenten decided so on 6 October 2026: the choice of who answers sits where the question is written, like the model choice in claude.ai. Not in the conversation's head.

Props

  • variants: { id, title, description? } for each variant, from the platform's id and _variant_title.
  • value: the id of the variant in use. Without it the button says «Standard».
  • onChange: the id the person chose, named as in every block with a controlled choice of one, such as CorpusChoice. The app sends it as model, and keeps it if it should last: kunnskapsassistenten stores it in the browser only when it is not the default, forgets it at «Logg ut», and passes it back as value. A kept id the service no longer offers shows as «Standard». The old names, chosen and onChoose, still work until hosts have moved.
  • headingLevel: «Velg variant» as a heading at this level. None by default: the picker sits in another block's slot, the question field, where a heading would break the page's outline. It names the list either way.
  • color: Designsystemet's data-color for the button and the list. Neutral unless given, as kunnskapsassistenten draws its picker in the question field.
  • className: on the button, for the block it sits in to place it.

Related

Branding

A brand is a Designsystemet theme. The block sits in @layer genai.components, after Designsystemet's layers, follows data-color, data-color-scheme and data-size, and reads every token through its own variable, with the token as the fallback. Set one on any ancestor to change that detail only. None is pinned to a colour family. The list's width is the one value that is not a token: no Designsystemet size is as wide as a line of description.

What is built

  • A Designsystemet Dropdown of buttons under the heading «Velg variant», not an ARIA menu: a menu without arrow keys and typeahead is worse than none. The variant in use has aria-current and a check.
  • The button's name is «Variant: » and what it shows, so voice control still finds it (WCAG 2.5.3) and a screen reader hears what the button changes.
  • The list opens above the button, since the question field is at the bottom; with no room above, Designsystemet opens it below. It scrolls inside the room it has rather than running off a short screen.
  • After a choice, the list closes and focus goes back to the button.
  • A long name ends in an ellipsis, so the button never pushes the send button off a phone. A description is shown only when the app has one.

What we have learned

  • Kunnskapsassistenten's picker listed eight agents, 663 px of list on a phone. The list is capped at the room above the button for that reason.
  • Kunnskapsassistenten says «Agent». The block says «Variant», since the platform offers variants of one service, never separate agents.
  • The platform sends no description per variant today, only the service's purpose, which is the same on every row. So the list shows names only, until it does.

Open questions

  • Is «Variant» a word end users understand, or should the button say something plainer?
  • Should the platform give each variant a description of its own, so a person can tell them apart?

Settings

The reader's own choices, starting with the colour scheme: light, dark, or the same as the operating system. Each choice takes effect at once, so there is no «Lagre».

Use it when

  • The reader should choose light or dark mode, rather than only follow the system.
  • The app has more choices of its own that belong on the same page.

Don't use it when

  • To brand the assistant. The brand is the service owner's, chosen when the assistant is set up, not the reader's. See Branding.

Variants

  • The block: «Innstillinger» with its sections.
  • The colour scheme alone: ColorSchemeToggle, for an app that places it somewhere else.
  • The other choices alone: DisplayLevelChoice and ExperimentSwitches.
  • The links to it: SettingsLinks, for the foot of the navigation panel: «Innstillinger» first, then the app's own pages, such as the pages about the service.

Props

  • colorScheme: 'light', 'dark' or 'auto', as the app keeps it. Without it, «Auto» is chosen.
  • onColorSchemeChange: the scheme the reader chose. The app stores it and sets data-color-scheme on its root. The block shows the app's value, so a choice the app has not taken is not shown as taken.
  • displayLevel and onDisplayLevelChange: how much an answer shows of how it was made, 'standard' or 'detailed'. The section «Svar» is drawn only when the app takes the choice.
  • experiments and onExperimentChange: the trials, each with an id, title, description, whether it is on, and a link (href, hrefLabel) to where it is discussed. The section «Eksperimenter» is drawn only when there are trials and the app takes the change. The event says which trial and whether it is now on.
  • headingLevel: the level of «Innstillinger», 2 by default. Each section's heading is one below. On a page of its own, the app passes 1.
  • children: the app's own sections after the block's, each a SettingsSection with a title.
  • note: a quiet line after every section, such as where the choices are kept, which only the app knows.
  • SettingsLinks: settingsHref, the app's links (href, title, an aria-hidden icon), currentHref for aria-current, onNavigate for the app's router, and assistantName for the list's name, «Innstillinger og om …».
  • color: Designsystemet's data-color for the block, set only when given.
  • colorSchemes, isColorScheme, displayLevels and isDisplayLevel are exported for an app that reads a stored choice.

Branding

A brand is a Designsystemet theme. The block sits in @layer genai.components, after Designsystemet's layers, follows data-color, data-color-scheme and data-size, and reads every token through its own variable, with the token as the fallback. Set one on any ancestor to change that detail only. None is pinned to a colour family. The choice itself is Designsystemet's ToggleGroup, which the block does not restyle: an app changes it with Designsystemet's own --dsc-togglegroup-* variables.

What is built

  • «Innstillinger», then the section «Fargemodus»: a Designsystemet ToggleGroup with «Lys», «Mørk» and «Auto», each with its icon (sun, moon, screen). Words beside the icons, since Designsystemet asks for a tooltip on icon-only items.
  • A toggle group, not a switch: «Auto» is where the reader starts, and must be reachable again after trying the other two. A screen reader hears a group of three radio buttons named «Fargemodus».
  • Data in, events out. The block never stores the choice or touches the page: the app keeps it, sets data-color-scheme, and passes it back in. A value the block does not know shows as «Auto».
  • «Fargemodus» comes first, as the page's main choice: light and dark mode live in the settings, not in the panel's foot (decided 2026-11-06).
  • «Svar»: «Standard» or «Detaljert» as radio buttons, each with a line on what it shows. «Eksperimenter»: a line that all are off until turned on, then a Designsystemet Switch per trial, since each takes effect at once, with a link that opens in a new tab and says so in words.
  • The app's own sections share the look and the heading level of «Fargemodus».
  • SettingsLinks is a named list, not a nav: the panel around it is already the navigation landmark. The page on screen is marked by weight, not colour.

What we have learned

  • Made from kunnskapsassistenten's colour scheme toggle and settings page, with the same words, icons, sizes and spacing. Its tests are ported, but for the ones about storage, which stay with the app.
  • What the app keeps: kunnskapsassistenten stores the choice in the browser, applies it before the first paint from a script file of its own (its Content Security Policy refuses an inline one), and follows a choice made in another tab.
  • How much the answer shows and the experiments are sections of the block, with kunnskapsassistenten's words, so every app need not build them again. What stays the app's: which trials exist, storing every choice, turning the trials off when the reader signs out, and a development section such as kunnskapsassistenten's choice of a pinned or scrolling foot.
  • genki's portal, console and workspace are light only today.

Open questions

  • Should the language choice be a section of the block? genki has one already, LanguageChoice in @genai/i18n/react, but it reads and sets the language itself rather than taking it as data.
  • The brand colour (kunnskapsassistenten#170) is chosen in the app builder, by the service owner, not here.
  • Is a font choice in scope (kunnskapsassistenten#173), and how would it be loaded? Every block already takes a font through its variables.
